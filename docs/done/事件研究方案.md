## 一、背景与动机

### 1.1、现状

目前没有统一的数据库来存储影响金融市场的历史事件及其对证券市场的实际影响，缺乏系统化的事件驱动分析能力。现有的数据分散在不同来源（新闻、行情、宏观指标），无法快速回答“类似事件在历史上如何影响某类资产”的问题，也无法支持 AI 基于历史事件进行预测。

### 1.2、目标

建设一个可运行的系统，实现以下能力：

- 从外部数据源（Tushare、爬虫）采集事件、行情、宏观环境数据，并结构化存储。
- 人工审核事件信息，确保事件分类和关键条件的准确性。
- 自动计算每个事件对指定指数资产（上证指数、科创50、科创100、沪深300）在多个时间窗口（事件前、事件当天、事件后）的市场影响（CAR、方向等）。
- 存储每日市场环境快照，用于分析不同宏观环境下的事件影响差异。
- 提供基于相似事件检索的 AI 预测接口，对新事件输出历史影响统计及预测。
- 系统支持本地定时批处理，每天早间自动运行。

- `events.status`：PG 只存人工处理过的事件——`approved` 已通过、进入影响计算；`ignored` 忽略（保留用于爬虫去重）。待审核草稿存 Redis（`events:pending:{event_id}`），审核通过后写入 PG。

- `assets.market` 预留多市场扩展（美股/韩股等）：`market_data` 结构通用，新增资产记录即可存海外行情；ts 约定为该市场当地交易日，t0 对齐用对应市场的交易日历。V1 仅 CN。

## 三、详细设计

### 3.1 数据采集模块

#### 3.1.1 模块设计

- **职责**：  
  1. 事件采集：使用爬虫从财经快讯源（主源：财联社电报、金十数据快讯；备源：新浪财经 7x24、东方财富快讯）抓取可能影响市场的事件，提取标题、正文、时间、来源，写入 Redis 待审核草稿（`events:pending:{event_id}`）；官方原文链接（央行/统计局/财政部官网）供审核时核对。  
  2. 行情采集：通过 `BaseStockDataProvider` 接口层（基类新增结构化接口 `get_index_data_df`，默认 Tushare Provider 覆写）获取指定指数（上证指数、科创50、科创100、沪深300）的日线数据（开高低收、成交量），collector 仅负责持久化到 `market_data` 表。  
  3. 宏观环境采集：经 Provider 层获取中国宏观指标（如10年期国债收益率——在基类新增宏观接口、AKShare/Tushare 分别覆写）；FRED 等海外源为可选，暂不接入 Provider。

- **接口**：
  - `fetch_events_from_crawler() -> list[dict]`：爬虫返回事件列表。
  - `fetch_market_data(ticker, start_date, end_date) -> pandas.DataFrame`：获取日线行情。
  - `fetch_macro_context(date) -> dict`：获取当日宏观环境指标。

- **数据结构示例**（爬虫事件）：
  ```json
  {
    "title": "中国1月CPI同比上涨2.1%，预期1.9%",
    "content": "国家统计局公布...",
    "source_url": "https://...",
    "announced_at": "2024-02-10 09:30:00+08:00",
    "importance_hint": 5
  }
  ```

#### 3.1.2 三方依赖能力评估

- **Tushare**：需注册获取 token，有积分限制。日线行情和部分宏观数据可用，需确认 token 权限是否足够（`index_daily` 单次调用有 limit 上限，`get_index_data_df` 内部自行分页循环拉取）。  
- **爬虫**：选用 `requests` + `BeautifulSoup`（目标站多为 JSON 接口或轻反爬）；财联社/金十反爬中等，需评估；新浪 7x24 与东财快讯接口宽松。财经日历（金十/东财日历）用于定时触发定期发布类事件（CPI/PMI 等）。  
- **FRED**：如需美国数据，可使用 `fredapi` 库，免费需 API key。  
- **注意**：爬虫抓取的内容仅用于内部研究，需遵守网站 robots.txt 和版权规定。

#### 3.1.3 风险与验证方式

- **风险**：爬虫失效、数据源限流、tushare 积分不足。  
- **验证**：编写单元测试模拟数据源返回；集成测试实际拉取少量数据验证格式。

#### 3.1.4 文件变更清单

- **新建文件**：
  - `AI/eventStudy/collectors/event_crawler.py`：爬虫采集事件并写入 Redis 待审队列
  - `AI/eventStudy/collectors/market_data_collector.py`：经 Provider 层拉取行情并持久化到 `market_data` 表（不直连 Tushare SDK）
  - `AI/eventStudy/collectors/macro_collector.py`：宏观环境采集（经 Provider 层）
  - `AI/eventStudy/collectors/config.py`：配置 Tushare token、爬虫目标等
- **修改文件**：
  - `AI/dataflows/providers/base_provider.py`：新增宏观上下文接口（如 `get_macro_context`）、交易日历接口 `get_trade_cal`（t0 对齐用，预留 market 参数；V1 仅 CN）与结构化行情接口 `get_index_data_df`（返回 DataFrame 而非 Markdown，分页由子类内部处理），均默认 `_not_supported()`

### 3.2 人工审核模块

#### 3.2.1 模块设计

- **职责**：提供简单界面或脚本，展示 Redis 中的待审核事件草稿（`events:pending:{event_id}`），人工确认以下字段：
  - `event_type`、`event_subtype`、`event_condition`（如超预期/符合预期/低于预期）
  - `importance`
  - 如果原文中包含预期值和实际值，可填入；否则不填，只填条件分类。
  - 审核通过：写入 PG `events` 表（`status='approved'`）；忽略：写入 PG（`status='ignored'`，用于爬虫去重）。
  - **影响结果确认**：影响计算自动遍历全部 4 个指数，结果先写入 **Redis** 草稿（`event_impacts:draft:{event_id}`，可设 TTL、过期可重算），PG 表不加 status 字段；审核界面从 Redis 读取并展示各资产 CAR/方向，人工勾选确认落表——**仅勾选的写入 PG `event_impacts` 表**，未勾选的不落表。`event_impacts` 因此只含人工确认过的正式记录，预测与回测直接使用，无需过滤。

- **接口**：
  - `get_pending_events() -> list[dict]`：从 Redis 读取待审核草稿。
  - `approve_event(event_id, review_fields)`：更新事件状态和字段。
  - `ignore_event(event_id)`：忽略事件。
  - 可提供一个基于 Streamlit 的简单 Web 界面。

- **数据结构示例**（审核提交）：
  ```json
  {
    "event_id": 1001,
    "event_type": "宏观数据",
    "event_subtype": "CPI",
    "event_condition": "超预期",
    "importance": 5,
    "expected_value": 1.9,
    "actual_value": 2.1
  }
  ```

#### 3.2.2 三方依赖能力评估

- 如果使用 Streamlit，依赖 `streamlit` 库，轻量易用。  
- 影响结果确认环节依赖 Redis（项目已有，AOF 持久化已开启）读写草稿；其余为数据库操作，无特殊外部 API。

#### 3.2.3 风险与验证方式

- **风险**：人工操作错误导致分类错误。  
- **验证**：审核界面增加二次确认；审核日志写入 Redis（全局列表 `event_review_log`，LPUSH 审核动作 JSON：event_id/操作者/时间/动作/改动字段），仅作追溯保险，不建审计表。

#### 3.2.4 文件变更清单

- **新建文件**：
  - `AI/eventStudy/review/review_app.py`：Streamlit 审核界面
  - `AI/eventStudy/review/review_dao.py`：数据库访问函数

### 3.3 事件结构化与向量化模块

#### 3.3.1 模块设计

- **职责**：对审核通过的事件文本进行向量化，生成 embedding，写入 `events.embedding`（唯一向量存储）。  
- **接口**：
  - `vectorize_event(event_id)`：查询事件标题+内容，生成向量并更新数据库。
- **依赖**：`BAAI/bge-m3` 模型（经 sentence-transformers 加载），输出 1024 维向量，与 `events.embedding` 的 `VECTOR(1024)` 一致。

#### 3.3.2 三方依赖能力评估

- 模型约 2.2GB，下载需要网络（国内可用 hf-mirror.com 镜像），提前下载到本地；CPU 推理每条约 2–5 秒，每日批处理量级可接受。  
- 模型维度与表结构 `VECTOR(1024)` 已统一；如更换模型需同步改表并全库重算向量。

#### 3.3.3 风险与验证方式

- **风险**：模型较大（2.2GB）首次加载慢（进程常驻后一次加载）；维度与表结构不匹配。  
- **验证**：单元测试检查输出维度；抽查向量合理性。

#### 3.3.4 文件变更清单

- **新建文件**：
  - `AI/eventStudy/processing/event_vectorizer.py`：向量化逻辑

### 3.5 市场上下文计算模块

#### 3.5.1 模块设计

- **职责**：每日计算各市场（V1 仅 CN）环境指标，以 JSON 按市场组织写入 `market_context.context`（一行 = 某日全部市场）。

### 3.6 事件影响标注模块（核心）

#### 3.6.1 模块设计

- **职责**：使用事件研究法（市场模型 OLS）计算事件对**全部 4 个目标指数**在多个时间窗口的异常收益（CAR）、方向、显著性；结果先写入 Redis 草稿（`event_impacts:draft:{event_id}`），经人工确认后由审核模块落表到 PG `event_impacts`（该表只含正式记录）。  
- **接口**：
  - `run_event_study(conn, event_id, asset_id, market_asset_id, window_type, estimation_days=120, gap_days=10, pre_event_days=5, post_event_days=5) -> dict`
  - 内部为每个窗口（如 `pre_event_5d`, `event_day`, `post_event_5d`）分别计算 CAR，并写入对应的 `window_type` 记录。
- **市场模型**：  
  使用估计窗口（事件前 `gap_days + estimation_days` 到 `gap_days` 天）的资产收益率与市场指数收益率进行 OLS 回归，得到 α 和 β。  
  事件窗口的异常收益 = 资产实际收益 - (α + β * 市场收益)。  
  CAR = 事件窗口异常收益之和。  
  方向判定：CAR > 0.5% 且 t统计量 > 1.96 为利好；CAR < -0.5% 且 t < -1.96 为利空；否则中性。
- **污染检查**：查询事件窗口内是否有其他重要性 ≥4 的事件，若有则标记 `is_contaminated=True`。
- **交易日对齐（t0 规则）**：盘前（09:30 前）公布 → t0 = 当日；盘中/盘后/非交易日公布 → t0 = 下一个交易日。用交易日历（`get_trade_cal`）确定 t0 并写入 `events.trading_day`；所有窗口（pre_event_5d / event_day / post_event_5d）均相对 t0 在 `market_data` 中切分。
- **数据结构示例**：见前文。

#### 3.6.2 三方依赖能力评估

- 使用 `statsmodels` 进行 OLS 回归，成熟稳定。

#### 3.6.3 风险与验证方式

- **风险**：前视偏差、估计窗口不足、数据缺失。  
- **验证**：使用模拟数据测试；人工抽查历史事件 CAR 是否合理。

### 3.7 AI预测模块（相似事件检索）

#### 3.7.1 模块设计

- **职责**：对新事件（文本），生成向量，使用 pgvector 检索历史相似事件，结合市场环境过滤（可选），输出预测。  
- **接口**：
  - `predict_impact(new_event_text, asset_ticker, window_type='post_event_5d') -> dict`
- **逻辑**（模板匹配 + 向量检索加权融合）：
  1. **确定模板**：新事件的 `event_type` + `event_subtype` + `event_condition`（人工审核确认，或由事件文本确定）。  
  2. **模板匹配（基线预测）**：在 `event_impacts`（该表仅含人工确认的正式记录）中查询该模板下、针对目标资产、指定窗口的全部历史影响记录，统计**平均 CAR、胜率（上涨占比）、样本数量**。  
  3. **向量补充（始终执行）**：无论模板样本多少，都将新事件文本向量化，检索跨模板的语义相似事件 top K（余弦相似度；相似度低于 0.5 的不纳入）补入样本集。  
  4. **合并加权预测**：模板内事件权重 1.0，向量补充事件按相似度 × 折扣（建议 0.5）加权；方向按加权平均 CAR 符号判定（正 → 利好，负 → 利空，近零 → 中性）；幅度 = 加权平均 CAR；置信度基于样本数量与胜率极端程度。  
  5. 返回预测（方向/幅度/置信度）+ 模板统计（平均 CAR、胜率、模板样本数）+ 补充的相似事件列表（含相似度与权重，模板/补充分开报告，保持可解释性）。  
- **两种机制的定位**：模板匹配依赖人工审核的高质量标签，简单直观、可解释性强，但无法处理模板外的细微差别；向量检索自动捕捉语义相似、更灵活，可解释性稍弱。两者结合：模板优先出基线，样本不足或需更精细参考时向量补充。  
- **确定性**：模板匹配与向量补充的规则对 LangGraph 工具（3.10）、REST API（3.8）、离线回测（3.7.3）三者完全一致，保证预测可复现、回测可信。  
- **落库策略**：`predictions` 表仅在两种情况下写入——(1) **显式保存**：人工在审核/预测界面点"保存预测"，或 REST API 带 `save=true` 参数调用（用于事后追踪"预测 vs 实际"）；(2) **离线回测**（3.7.3）批量写入。日常 REST API 与 LangGraph 工具调用只返回结果不落库，避免表膨胀。

#### 3.7.2 三方依赖能力评估

- 使用 `pgvector` 扩展（与业务表同库，向量与事件同事务写入）。事件量为数千条级，暂不建 HNSW 索引，直接全量余弦距离查询（毫秒级）；事件量达数万条后再建索引。  
- 使用 `sentence-transformers` 生成查询向量。

#### 3.7.3 风险与验证方式

- **风险**：相似度阈值不当、样本稀疏、回测前视偏差（检索到未来事件）。  
- **验证**：离线回测，计算方向准确率；回测检索必须过滤 `announced_at < 事件自身时间`，防止未来信息泄漏。

**B4 前视偏差只提了一半** ✅ **已定（2026-08-16）**：两条补充均已写入正文——(1) 3.7.3 回测检索必须过滤 `announced_at < 事件自身时间`；(2) 3.5.1 新增匹配规则：事件的环境快照统一取"事件发生前最近一个已收盘交易日"（盘前/盘中 → 前一交易日；收盘后/非交易日 → 最近已收盘日），禁止当日快照。

**B5 审核 assets 字段无处存储** ✅ **已定（2026-08-16，2026-08-17 修订）**：取消审核时的资产勾选；影响计算**自动遍历全部 4 个指数**，结果先写入 **Redis** 草稿（`event_impacts:draft:{event_id}`，可设 TTL、过期可重算），**PG 表不加 status 字段**；审核界面从 Redis 读取展示各资产 CAR/方向，**人工勾选后落表**——仅勾选的写入 PG `event_impacts`（该表只含正式记录，预测/回测直接使用、无需过滤）。正文（2.1、3.2、3.6、3.7）已同步。2026-08-17 再扩展：事件待审草稿同样走 Redis（`events:pending`），PG 只存人工处理过的事件——统一为 4.1 决策 10"草稿区约定"。

**B6 架构图与 3.7 不一致** ✅ **已定（2026-08-16，2026-08-17 修订）**：保留"模板匹配"。定义：模板 = `event_type` + `event_subtype` + `event_condition`；模板匹配输出该模板历史事件的平均 CAR、胜率、样本数作为基线；**向量补充始终执行（不设 5 条门槛）**——模板内事件权重 1.0，补充事件按相似度 × 0.5 折扣加权（相似度 < 0.5 不纳入），模板/补充分开报告保持可解释性。3.7 与 4.1 决策 8 已同步。

## 五、实现后遗留问题与待决策事项（2026-08-18 实现验收时记录）

### 5.1 ⚠️ 市场层工具循环休眠（bind_tools 缺口）——待决策

**现象**：市场层所有新闻类 Analyst 调用 LLM 时从未 `bind_tools`（`llm.invoke(prompt.format_messages(...))`），LLM 看不到工具定义、不会发出 tool_calls，ToolNode + 条件边路由永远直接走 Msg Clear——包括 3.10 注册的 `search_similar_events` 在内的全部工具实际不会被 Agent 调用。

**性质**：**既有架构问题**（影响 intl/us/kr/cn 4 个新闻分析师的全部既有工具），非本次实现引入。3.10"工具模式"的目标（Agent 自行决定调用事件研究工具）在当前架构下无法达成——工具已注册进工具列表，但不激活。

**修复方案（待用户决策）**：在新闻类 Analyst 节点对 llm 做 `bind_tools(tools)`（tools 由 `market_layer_graph` 传入）。副作用：既有 5 个 intl_news 工具 + 其余新闻分析师工具一并变为可调用，属行为变更，需评估报告质量/延迟影响后执行。

### 5.2 财联社电报接口失效

**现象**：`cls.cn/nodeapi/updateTelegraphList` 返回 404，新版接口 `v1/roll/get_roll_list` 需签名参数（sign），当前版本爬虫不可用。

**影响**：主源之一失效。金十数据快讯正常（已验证 15 条/次），新浪 7x24 / 东财快讯备源可用（默认关闭，env 开启：`CRAWLER_SINA_ENABLED` / `CRAWLER_EM_ENABLED`）。

**处理建议**：V1 接受降级（3.1.3 已将爬虫失效列为风险）；如需恢复财联社，需逆向其签名算法或改用 RSS/第三方镜像。

### 5.3 rate_10y 指标置空（Tushare 自定义端点）

**现象**：Tushare Provider 使用的自定义端点（ts.gyzcloud.top）无 `yield_curve` 接口（报"请指定正确的接口名"），10 年期国债收益率当前置空，`market_context` 仅含 return_20d / vol_20d / amount_20d。

**影响**：市场环境快照缺利率维度（3.5.2 已定义降级路径：指标置空不阻塞）。

**处理建议**：切 AKShare 数据源（`bond_china_yield` 可用）或 Tushare 官方端点积分达标后自然恢复。

### 5.4 金十重要性星级不可用（VIP 字段）

**现象**：金十 `get_flash_list` 免费接口的 `important` 字段恒为 0（星级为 VIP 能力），`importance_hint` 多数为空。

**影响**：爬虫重要性提示失效，重要性靠人工审核填写（审核界面滑杆已覆盖）。

**处理建议**：V1 人工填写；后续可考虑规则打分（标题关键词/数据类别加权）或付费接口。
