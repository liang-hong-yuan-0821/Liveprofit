## 一、背景与动机

### 1.1、现状

- AI 内核每次分析运行（`AI/graph/trading_graph.py` 的 `propagate()`，第 305~310 行）在 `logs/{时间戳}/` 下按 layer → LLM 节点目录（`{seq:03d}_{NodeName}/`）落盘调用日志：
  - dataprovider 调用（`AI/utils/dataprovider_log.py`）：节点目录下 `{seq:03d}_{接口名}/`，含 `req.json`（绑定后完整入参）、`res.md`/`res.json`（出参）、`meta.json`；
  - tushare 端点子日志：DP 调用目录下 `tushare/{seq:03d}_{api_name}/`（req/res/meta）；
  - LLM 调用（`AI/utils/llm_callbacks.py`）：节点目录下 `req.md`（提示词）、`res.md`（输出）、`meta.json`（model/node/seq）；工具调用在 `tools/{seq:03d}_{tool}/`。
- 该目录树目前仅能通过仓库内独立浏览脚本查看，Web 平台前端没有展示入口。
- 平台链路（backend/）已打通：Worker 经 `AnalysisExecutor → TradingGraphAdapter → RealTradingGraphFactory` 执行内核图，进度经 Redis Stream → SSE → 前端。但**平台任务与日志目录之间没有映射**：
  - 内核无条件写 `logs/{时间戳}/`，`build_real_initial_state`（real_graph_factory.py:86）虽携带 task_id/attempt_no，内核不消费；
  - 后端没有读取日志目录的端点；`logs/` 目录与 `var/runs/{task_id}/{attempt}/` 产物归档互不相干；
  - 任务详情页（`frontend/src/modules/analysis/pages/task-detail/AiTaskDetailPage.tsx`）只有阶段时间线（市场/板块/个股三档文案），看不到 dataprovider 入参出参。
- 现状证据：`logs/2026-09-06_093159/`（平台任务运行时产生）与 `var/runs/33ded201-.../2/`（产物）并存且无关联。

### 1.2、目标

任务详情页新增「执行调用日志」区块，把内核运行期调用日志完整搬进 Web 平台：

1. 每个平台任务的日志写入**确定性任务目录** `logs/tasks/{task_id}/{attempt_no}/`，API 可直接定位，无需扫描发现；
2. 新增 REST 端点返回该目录的完整树（layer → 节点 → DP 调用 req/res + tushare 子调用 + 工具调用 + LLM 提示词/输出 + meta），供前端渲染；
3. 任务详情页按 layer → 节点 → DP 调用（req/res + tushare 子调用）→ 工具调用 → LLM 提示词/输出 → meta 的嵌套展开结构展示，**运行中每 5s 轮询实时"生长"，终态停止轮询**（终态回看静态可用）；
4. CLI 运行（`main.py` 直接跑内核）行为完全不变（仍写时间戳目录）。

### 2.1 数据模型设计

日志目录树（磁盘，内核已定义的格式，本方案不改变内部格式）：

| 路径（相对任务目录） | 内容 | 写入者 | 说明 |
|------|------|--------|------|
| `{layer}/` | 层目录 | 内核 | market / sector / stock / screening，固定执行序 |
| `{layer}/{seq:03d}_{NodeName}/` | LLM 节点目录 | llm_callbacks | 如 `sector/001_Sector_News_Analyst/`；seq 为全局 LLM 调用序号 |
| `{layer}/{seq:03d}_{NodeName}/req.md` | LLM 提示词 | llm_callbacks | on_llm_start 写入 |
| `{layer}/{seq:03d}_{NodeName}/res.md` | LLM 输出 | llm_callbacks | on_llm_end 写入，含 content 与 tool_calls 摘要 |
| `{layer}/{seq:03d}_{NodeName}/meta.json` | `{model, node, run_id, seq, content_length, tool_calls?}` | llm_callbacks | 如 `{"model": "gpt-4o", "node": "Sector News Analyst", "seq": 1}` |
| `{layer}/{seq:03d}_{NodeName}/{seq:03d}_{接口名}/` | DP 调用目录 | dataprovider_log | 节点目录内独立计数，如 `001_get_stock_data/` |
| `…/req.json` | DP 完整入参 | dataprovider_log | `_bind_req` 绑定含默认值，如 `{"symbol": "000001.SZ", "start_date": "2026-08-01"}` |
| `…/res.md` 或 `res.json` | DP 出参 | dataprovider_log | str 结果 → res.md（markdown 契约）；非 str → res.json |
| `…/meta.json` | `{name, desc, seq, ts, res, error?}` | dataprovider_log | `res` 为实际结果文件名；`error=true` 时 res.json 为 `{"error": ...}` |
| `…/tushare/{seq:03d}_{api_name}/` | tushare 端点子调用 | wrap_tushare_api | 仅 tushare 数据源；`req.json={"api_name","fields","params"}`；`res.json` DataFrame 归一为 `{columns, shape, records, row_count, truncated}`；meta 含 `probe`（连通性探测）、`error?` |
| `{layer}/{seq:03d}_{NodeName}/tools/{seq:03d}_{tool}/` | 工具调用 | ToolCallbackHandler | `req.json` + `res.txt` |
| `reports/` | 运行报告文件 | `_write_reports` | 本方案不读取（报告走报告 API） |

新增配置（backend `CoreSettings`）：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `execution_logs_root` | `Path` | `Path("logs")` | 执行日志根目录；相对路径按 `PROJECT_ROOT`（backend/bootstrap/settings.py:19，项目仓库根）解析为绝对路径 |

API DTO（新增，见 3.2.1）字段以 OpenAPI 导出为准。

## 三、详细设计

### 3.1 内核日志目录注入（AI/）

#### 3.1.1 模块设计

**目录选择逻辑**（`AI/graph/trading_graph.py` 第 305~310 行替换）：

```python
# ---- 本次运行的日志目录 ----
platform_dir = str(init_state.get("platform_log_dir") or "").strip()
if platform_dir:
    log_dir = Path(platform_dir)
else:
    run_ts = datetime.now().strftime("%Y-%m-%d_%H%M%S")
    log_dir = Path(f"logs/{run_ts}")
log_dir.mkdir(parents=True, exist_ok=True)   # 新增：平台多级目录（logs/tasks/{uuid}/{n}）提前建
self.llm_handler.set_log_dir(log_dir)
self.tool_handler.set_log_dir(log_dir)
```

- 提取纯函数 `resolve_run_log_dir(init_state: dict, now: datetime | None = None) -> Path` 到模块级，便于单测（propagate 内调用它）。`now` 参数注入仅为测试时间戳确定性，实际调用不传。
- `platform_log_dir` 为**平台保留 state key**：CLI/既有测试的 init_state 不含此 key → 行为与现在完全一致（时间戳目录 + 不提前建目录的行为差异可忽略：提前 mkdir 一个空目录对既有测试无影响，`list_runs` 匹配 `_RUN_RE` 的时间戳目录即使为空也会被列出——与现状一致，现状空 run 目录也可能存在）。
- 其余下游不改：`_write_reports(final_state, log_dir)`（报告文件）与 `step_gate.enable(log_dir)`（调试步进检查点）自动落进任务目录；`_log_state` 与 log_dir 无关（写 `results/{ticker}/analysis_logs/state_log.json`，trading_graph.py:502-508），保持现状。

**Worker 侧注入**（`backend/modules/analysis/infrastructure/real_graph_factory.py`）：

```python
def build_real_initial_state(task, execution_logs_root: Path | None = None) -> dict:
    ...
    if execution_logs_root is not None:
        init_state["platform_log_dir"] = str(
            execution_logs_root / "tasks" / str(task.task_id) / str(task.attempt_no))
```

- `execution_logs_root` 为 None 时（fake/测试路径）不注入 → 内核回退时间戳目录，测试不受影响。
- 目录命名：`{root}/tasks/{task_id}/{attempt_no}/`。attempt_no 参与路径——重试（RETRYING→新 attempt）各 attempt 日志独立目录，互不覆盖；端点按任务当前 `attempt_no` 读取（3.2.3）。
- 接线（`backend/workers/wiring.py` `get_worker_executor` 第 103~105 行）：

```python
adapter = TradingGraphAdapter(
    _graph_factory,
    initial_state_factory=lambda task: build_real_initial_state(
        task, execution_logs_root=resolve_execution_logs_root(settings.core)),
)
```

- `TradingGraphAdapter.execute` 已透传 initial_state_factory（trading_graph_adapter.py:37），无需改动。
- 配置新增：`backend/bootstrap/settings.py` CoreSettings 加 `execution_logs_root: Path = Path("logs")`（env 前缀 `LIVEPROFIT_`，环境变量 `LIVEPROFIT_EXECUTION_LOGS_ROOT`）。
- **相对路径解析单一出口**：`backend/bootstrap/settings.py` 新增模块级函数 `resolve_execution_logs_root(core: CoreSettings) -> Path`——相对路径按 `PROJECT_ROOT`（settings.py:19，仓库根）解析为绝对路径，**不按 `Path.cwd()`**（artifact_root 的 cwd 先例（wiring.py:96）对同一进程内多路径无影响，但本功能的写入方（worker 进程）与读取方（API 进程）是两个进程，CWD 可能不同，cwd 解析会导致 worker 写入目录与 API 读取目录分叉、端点恒空）。wiring 注入（本节）、execution_logs 路由（3.2.1）、删除清理（3.2.1）**三处统一调用该函数**，禁止各自解析；单测断言"两进程各调一次结果一致"。

### 3.2 执行日志读取与 API（backend/）

#### 3.2.1 模块设计

**新 schema** `backend/api/schemas/execution_logs.py`（Envelope 复用现有）：

```
ExecutionLogsDTO:
  task_id: str
  attempt_no: int
  available: bool                    # 任务日志目录是否存在且可读；false 时 layers 为空
  generated_at: datetime             # 树构建时间
  layers: list[ExecutionLayerDTO]

ExecutionLayerDTO:
  name: str                          # "market" / "sector" / "stock" / "screening" / 未知层名
  nodes: list[ExecutionNodeDTO]      # 按目录名排序（seq 前缀）

ExecutionNodeDTO:
  dir: str                           # 相对任务目录，如 "sector/001_Sector_News_Analyst"
  seq: int | None                    # 目录名前三位；解析失败为 null
  node: str | None                   # meta.json 的 node（LLM 节点名）
  model: str | None                  # meta.json 的 model
  meta: dict | None                  # meta.json 原样（含 tool_calls 摘要）
  llm_req: ExecutionFileDTO | None   # req.md
  llm_res: ExecutionFileDTO | None   # res.md
  tools: list[ExecutionToolDTO]      # tools/ 子目录，按名称排序
  dp_calls: list[ExecutionDpCallDTO] # 新格式目录 + 旧格式平铺 json，按名称排序

ExecutionDpCallDTO:
  dir: str | None                    # 新格式目录相对路径；旧格式为 null
  name: str                          # 接口名（meta.name 或目录/文件名推导）
  desc: str | None
  seq: int | None
  ts: str | None
  error: bool                        # meta.error
  legacy: bool                       # 旧格式平铺文件
  req: dict | None                   # req.json；旧格式 payload.req
  res: ExecutionFileDTO | None       # res.md/res.json；旧格式 payload.res（dict → kind="json"）
  tushare: list[ExecutionTushareDTO]

ExecutionTushareDTO:
  dir: str
  name: str                          # api_name
  seq: int | None
  ts: str | None
  probe: bool
  error: bool
  req: dict | None                   # {api_name, fields, params}
  res: ExecutionFileDTO | None       # res.json（DataFrame 归一结构或 {"error":...}）

ExecutionToolDTO:
  dir: str
  name: str                          # 工具名（req.json 的 name，缺省取目录名）
  req: dict | None
  res: ExecutionFileDTO | None       # res.txt

ExecutionFileDTO:
  path: str                          # 相对任务目录的文件路径
  kind: "md" | "json" | "txt"        # 按扩展名
  content: str | dict | None         # kind=md/txt → str；kind=json → 解析后 dict
                                     # 解析失败/超限截断时 → null
  parse_error: bool                  # json 解析失败（content=null 时区分原因）
  truncated: bool                    # 超过内容上限，content=null
  total_bytes: int                   # 原始文件字节数（截断时前端展示"查看完整内容"）
```

**截断策略**（两级上限，常量定义在读取模块）：

- 单文件内容上限 `EXECUTION_LOG_CONTENT_MAX_BYTES = 100 * 1024`（100KB）。超限 → `content=null, truncated=true, total_bytes=实际大小`，前端走 content 端点拉全量。JSON 内容不做"截一半的 JSON"（截断 JSON 无意义）。
- **整树聚合上限** `EXECUTION_LOG_TREE_MAX_BYTES = 5 * 1024 * 1024`（5MB）：树构建按 layer → node → DP/tools/tushare/LLM 的遍历顺序累计已内嵌内容字节数，累计超限后后续**内容文件**一律 `content=null, truncated=true, total_bytes=实际大小`（truncated 语义统一为"内容未内嵌，可经 content 端点拉全量"）。**截断范围仅限 ExecutionFileDTO 承载的内容文件**（res/llm req/res/tushare res/tool res）：req.json、meta.json 等裸 dict 字段**不计入树级累计、永不树级截断**（req 为调用入参、本功能核心，大小天然小）。单文件 100KB 上限对所有落盘文件一致生效：req/meta 超限时该裸字段返回 null（DTO 无 truncated 位，防御性兜底，实际不可达）。
- 依据（评审实测）：全市场 run 的 stock_loop 逐票 invoke 同一编译子图（stock_loop.py:92），LLM 全局 seq 不清零，所有票的 LLM/DP/tools 日志累积进同一 attempt 目录——数百至上千文件、最坏数十 MB 属真实可达；仅靠单文件截断（每文件仍 100KB × 上千文件）挡不住。聚合上限把单次树响应封顶在 ~5MB。

**新读取器** `backend/modules/analysis/application/execution_logs.py`（纯函数，无 DB/IO 框架依赖）：

- `build_execution_logs_tree(run_dir: Path, *, max_file_bytes: int = 100*1024, max_total_bytes: int = 5*1024*1024) -> ExecutionLogsTree`（返回可序列化 dict，router 层转 DTO）。
- 目录枚举**复用 `AI.logviewer.logs_reader`** 的 `list_layers/sort_layers/list_nodes/list_dp_calls/list_tushare_calls/list_tools/read_json/read_text/parse_legacy`（backend 已有延迟导入 AI 的先例 real_graph_factory.py:66；logs_reader 为纯 Python 模块、无 UI 框架依赖，仅依赖 AI.utils.step_gate 常量）。不允许后端复制一份树遍历逻辑。
- **依赖改动：`logs_reader` 的 `_SEQ_DIR_RE`（logs_reader.py:23 现为 `\d{3}_.+`）需放宽为 `\d{3,}_.+`**——内核目录名前缀是 `f"{seq:03d}"`（llm_callbacks/dataprovider_log），seq 为全局/父目录计数，超 999 后自然变 4 位（如 `1000_Sector_News_Analyst`，全市场逐票循环累积调用次数的真实场景），`\d{3}_` 会把溢出目录在 list_nodes/list_dp_calls/list_tools/list_tushare_calls 中静默漏列（这些函数用 `_SEQ_DIR_RE.fullmatch(p.name)`，logs_reader.py:69/80/94/110）。只放宽数字段、保留 `_.+` 尾段，与既有 3 位目录完全兼容，磁盘格式不动。
- 内容读取规则：
  - req/res 等文件按扩展名分流：`.md/.txt` → `read_text` 得 str；`.json` → `read_json`，失败时 `content=null, parse_error=true`；
  - 单文件超限先于解析判断（按 `stat().st_size`，不读全量）；
  - 旧格式 DP（`list_dp_calls` 返回 `("legacy", path)`）：`parse_legacy` 的 `{name, desc, req, res}` 映射进 ExecutionDpCallDTO（`legacy=true, dir=null`）；
  - 缺失文件 → 对应字段 null（运行中未写完是正常态，前端渲染"未生成"）。

**新路由** `backend/api/routers/execution_logs.py`：

1. `GET /api/v1/analysis-tasks/{task_id}/execution-logs`
   - 经 `request.app.state.analysis_services` 查任务（复用 bundle，任务不存在 → 404 `TASK_NOT_FOUND`，复用现有异常映射）；
   - run_dir = `resolve_execution_logs_root(settings.core) / "tasks" / str(task_id) / str(task.attempt_no)`（解析函数见 3.1.1，与 worker 写入侧同一函数）；
   - 目录不存在/不可读 → 200 `available=false`（PENDING 尚未建目录是正常态，不是错误）；
   - 返回 `Envelope[ExecutionLogsDTO]`。
2. `GET /api/v1/analysis-tasks/{task_id}/execution-logs/content?file=<relpath>`
   - 全量文件内容端点（截断文件的"查看完整内容"）；
   - 路径校验：`file` 非空、以 `/` 分隔的相对路径、`(run_dir / file).resolve()` 必须位于 `run_dir.resolve()` 内（防路径逃逸）、扩展名 ∈ `{.json,.md,.txt}`；任一失败 → 422 `VALIDATION_ERROR`；
   - 单文件上限 10MB（超限 → 422）；响应 `Envelope[ExecutionFileDTO]`（content 全量、truncated=false）；
   - 目录/文件不存在 → 404 `RESOURCE_NOT_FOUND`。
3. `execution_logs_url` 派生进 TaskDTO 与 TaskCreatedData（`backend/api/schemas/tasks.py` + `analysis_tasks.py` 的 `_to_task_dto`/创建响应），与 events_url/report_url 对称。

#### 3.2.3 风险与验证方式

- **并发读写**：worker 写日志（非原子 write_text）与 API 读可能撞上半写文件 → 复用 logs_reader 的容错（坏 JSON → None → `parse_error=true`），前端按"解析失败"展示原文（content 端点可重试）。属可接受降级。
- **attempt 语义**：端点按任务**当前** attempt_no 读目录。RETRYING 时旧 attempt 目录保留但不可见（新 attempt 目录尚不存在 → available=false）。删除任务时清掉整个 task 目录，无泄漏。
- **响应体量**：全市场 run 的 stock_loop 逐票累积（stock_loop.py:92）可达数百至上千文件、最坏数十 MB——由两级上限封顶：单文件 ≤100KB（truncated 走 content 端点）+ 整树聚合 ≤5MB（超限部分统一 truncated）。正常单股/少量票任务单次树响应约几百 KB，5s 轮询可接受；最坏全市场长 run 的 5s×≤5MB 轮询有压力，**增量拉取（mtime 指纹 / since 参数）明确列为 v1.1 兜底项**，v1 接受全量轮询（本地单人应用，可接受上限内的偶发大响应）。
- **路径安全**：content 端点无用户可控根（run_dir 由 task_id 服务端构造），file 参数双保险校验（resolve 前缀 + 扩展名白名单）。
- **跨进程路径一致性**：`resolve_execution_logs_root` 保证 worker 写入与 API 读取解析到同一绝对路径（PROJECT_ROOT 基准，不依赖进程 CWD）；该目录本方案无其他消费方，无额外环境变量联动约束。

#### 3.3.1 模块设计

```ts
export function useExecutionLogsQuery(taskId: string, enabled: boolean, terminal: boolean) {
  return useQuery({
    queryKey: queryKeys.analysisTask.executionLogs(taskId),
    enabled,
    queryFn: async (): Promise<ExecutionLogsDTO> =>
```

**终态翻转补拉**（防尾部丢失）：任务终态翻转前，最后一次日志轮询可能早于内核末次落盘（res.md/meta 后写），若终态即停轮询，现场用户可能永远缺最后 ≤5s 的尾巴。`AiTaskDetailPage` 加 effect：`terminal` 由 false→true 翻转的瞬间对 executionLogs queryKey 做一次 `invalidateQueries`（翻转后 refetchInterval 已为 false，失效触发最后一次主动 refetch，随后缓存冻结）。

**新组件** `frontend/src/modules/analysis/pages/task-detail/ExecutionLogsPanel.tsx`：

- 结构：`Card`「执行调用日志」，副标题显示 `generated_at` 与运行中"每 5 秒自动刷新"提示；`available=false` 显示 EmptyState（"暂无执行日志：任务尚未开始写入或本次运行未产生日志"）；加载/错误走既有 LoadingState/ErrorState 模式。
- 层级展开（按内核落盘时序）：
  - layer 级 Collapsible（`sort_layers` 顺序：market → sector → stock → screening → 未知层字母序）；
  - node 级 Collapsible，标题 `{dir 尾段}（{node} · {model}）`；
  - 节点内部固定顺序：DP 调用列表（含 tushare 嵌套展开）→ LLM req（提示词）→ tools → LLM res（输出）→ meta；
  - DP 调用条目标题：`{dir 尾段}　{name} — {desc}`；`error=true` 加警示徽标；req 渲染格式化 JSON；res 按 kind 渲染（md/txt 纯文本 pre-wrap、json 格式化）；
  - `truncated=true` 的文件显示"内容过大（{total_bytes} 字节），查看完整内容"按钮 → 调 content 端点（React Query 一次性 fetch 或本地 state）展开全量；
  - `parse_error=true` 显示"解析失败"占位，内容经 content 端点查看原文；
  - 缺失文件（null）显示"未生成（调用可能未完成）"。
- 展开策略（运行中"生长"体验）：**默认全部收起，但自动展开"最后一个有内容的 node"**（其所属 layer 同步展开）；数据刷新后自动展开目标随最新 node 前移（用 key 为 node dir 的受控展开集合实现）；终态加载不再自动展开（保留用户已展开状态）。网页上下文中全展开体积过大，生长聚焦在最新节点。
- **新基础组件** `frontend/src/shared/ui/collapsible.tsx`：按项目既有约定（前端平台技术方案：shadcn/ui + Radix UI，组件源码由项目维护）封装 **`@radix-ui/react-collapsible`**——`Root/Trigger/Content` 导出 + header 样式封装，与 `dialog.tsx` 的封装模式一致（Radix 原语 + `cn` 工具 + CSS 变量）。Radix Collapsible 的 per-item `open`/`onOpenChange` 受控态与本方案的"展开集合以 dir 为 key + userCollapsed 记录"1:1 对应，自动展开随数据刷新直接改受控状态即可。
  - **不用 Accordion 的理由**：日志面板的展开项是多个**相互独立的嵌套折叠**（layer → node → DP 调用 → tushare，各自独立开合、程序化自动展开"最新 node"），Accordion 的 value 数组模型面向分组联动场景，嵌套独立控制反而绕；Collapsible 单例受控语义更贴合。键盘可达性（Enter/Space 切换）由 Radix 原语自带。
- 渲染内容不需要 markdown 库（项目无 markdown 依赖，`res.md` 按纯文本 + `whitespace-pre-wrap` 展示，JSON 用 `<pre>{JSON.stringify(v, null, 2)}</pre>`）。
- **接入页面**：`AiTaskDetailPage.tsx` 在 `TaskProgressTimeline` 之后、报告区之前挂 `<ExecutionLogsPanel taskId={taskId} terminal={terminal} />`（运行中与终态都显示；404 时整页不渲染，无需处理）。轮询与 SSE 事件解耦（各自独立刷新，不互相触发）。
- 大 JSON 渲染保护：内容字符串超过约 200KB 时不进 `JSON.stringify`（truncated 已挡住 >100KB 的 case；content 端点全量内容折叠在用户点击展开的 Collapsible 内，仍渲染）。

## 四、已确认决策 / 待确认问题

- **已确认决策**（2026-09-06，用户拍板）：
  1. 展示粒度 = **完整时序**：layer → 节点 → DP 调用（req/res + tushare 子调用）+ 工具调用 + LLM 提示词/输出，完整覆盖内核调用时序结构；
  2. 刷新方式 = **实时生长**：运行中每 5s 轮询，终态停止；
  3. 日志目录 = **任务独立目录 `logs/tasks/{task_id}/{attempt_no}/`**，**不做**仓库内日志浏览脚本的适配（2026-09-06 用户二次确认：由"扩展浏览脚本"改为不扩展）。后果：调试步进模式的页面确认流程对平台任务不可用（检查点确认入口只在浏览脚本内），CLI 运行不受影响。
- **本方案自行决定的工程取舍**（如有异议请指出）：
  1. 内容两级上限：单文件 >100KB 截断 + 整树聚合 >5MB 时树序靠后的内容文件统一 truncated（全市场长 run 下靠后调用需点"查看完整内容"），两者均走 content 端点拉全量；
  2. 运行中轮询 v1 为全量拉取（5s），增量拉取（mtime 指纹 / since 参数）列为 v1.1 兜底，最坏全市场长 run 的轮询压力 v1 接受；
  3. 日志自动过期清理 v1 不做（仅随任务删除清理），后续可挂 Dispatcher reconcile；
  4. 前端自动展开聚焦"最后有内容的节点"而非全展开（网页上下文全展开过长）。
