一、背景与动机

1.1、现状

Liveprofit 是以 Python 命令行入口为主的多智能体投研系统：

main.py 直接创建 TradingAgentsGraph，构造初始 State 后同步调用 propagate()，尚无统一 Web API。

AI/graph/trading_graph.py 已实现市场 → 板块 → 个股的 LangGraph 编排；全市场模式会继续顺序处理候选股票，再由仓位管理模块收口。

TradingAgentsGraph 支持 progress_callback，可输出市场层、板块层、个股层的阶段进度，能够作为任务事件的统一来源。

AI/dataflows/ 已封装 AKShare/Tushare Provider、Redis/MongoDB/File 缓存和交易日历校正；API 层不得重复实现数据拉取或交易日规则。

AI/eventStudy/api/main.py 已提供 POST /predict 和 GET /health，但尚未纳入统一任务、报告与运行观测体系。

docker-compose.yml 已具备 PostgreSQL + pgvector、Redis、MongoDB；事件研究的正式数据已在 PostgreSQL 中维护。

分析结果目前主要写入 logs/、results/，缺少任务、报告历史、本地自选/组合与运行追踪的正式数据模型。

TradingAgents-CN 说明：Web 平台应将 HTTP 控制面与耗时 AI 推理分离，用独立 Worker 承载长任务，并以 SSE 输出进度。其 FastAPI 分层、生命周期管理、队列和流式事件模式可借鉴；BackgroundTasks 与独立队列并存、双 Worker 路径、MongoDB 主库及配置来源混杂等问题不应复制。

1.2、目标

在不重写 AI/ 分析内核的前提下，建设仅供个人使用的本地后端平台，使其能够：

接收单股或全市场分析任务，稳定执行并保存任务状态、报告和错误摘要；

将现有 LangGraph 的阶段回调映射为可断线续读的 SSE 事件；

统一封装事件研究预测接口，避免维护两套算法逻辑；

提供自选股、组合与历史报告的本地持久化能力；

为后续盘前/盘后调度、告警和本地运行观测保留扩展点。

事务、消息与副作用规则：

Application Service 是数据库事务边界；多 Repository 写操作在同一 session/transaction 中完成。API/SSE 进程使用 async SQLAlchemy/async Redis 的异步应用服务；Dramatiq Worker/Dispatcher 使用同步 SQLAlchemy/Redis 的 Worker 应用服务外观，它们复用同一领域状态机、Command/Result、表结构和条件更新语义，但绝不跨线程、跨进程或跨 event loop 传递 Session/Redis client。同步 TradingAgentsGraph.propagate() 只在 Worker 的 Actor 线程运行；Router、Repository、Actor 均不得自行提交事务。

任务创建时必须在同一 PostgreSQL 事务写入 analysis_tasks(PENDING) 与 task_outbox(PENDING)。Dispatcher 仅在短事务中以 FOR UPDATE SKIP LOCKED + 条件更新把 Outbox 抢占为 DISPATCHING 并写入分发租约；提交事务后才调用 Broker，随后以分发租约条件确认 PUBLISHED。因此“Broker 已接收但确认 PG 前崩溃”会产生预期内的至少一次重复消息，由 Worker 的条件领取消除重复执行。

每次 Worker 领取都生成 lease_token；心跳、进度、完成、失败和取消必须携带该 token。Worker 必须在独立心跳单元中按 heartbeat_interval 续租，续租条件为 task_id + attempt_no + lease_token + RUNNING；续租失败即失去 fencing 权限，执行器不得保存报告或推进终态。过期 attempt 无权覆盖当前 attempt 的状态或报告。

Dramatiq 仅处理消息传输级短暂重投；业务级重试由 TaskService.fail_or_retry() 唯一决策：它在同一事务把 RUNNING(attempt n) 迁移为 RETRYING(attempt n+1)、清空旧租约字段并创建 (task_id,n+1) Outbox。此迁移不发布、不持久化、不回放任何重试专用 SSE 事件。只有 Dispatcher 确认该新 Outbox 后才迁移 QUEUED(attempt n+1) 并发布其新的 queued 业务事件；failed 仅在不可重试或耗尽时 FAILED 已提交后发布。

Redis Stream 仅记录可回放的六种业务事件 queued/started/progress/completed/failed/cancelled；reset、heartbeat 是仅有的两种非持久化控制帧，不分配 Stream ID，不能推进客户端游标。写 Stream 失败不回滚 PostgreSQL。若 PostgreSQL 已终态而对应业务终态帧缺失，SSE Router 必须通过 TaskEventService 基于已提交的 Task/Report 数据幂等补写对应的 completed、failed 或 cancelled 业务事件后再回放；若 Redis 仍不可用则不发送任何替代 SSE 事件并关闭连接，由客户端的 REST 回退获知状态。

任何外部 I/O（Dramatiq、Redis Stream、AI/Provider、文件系统）不得在未提交的业务事务中执行；可靠传递的信息使用 Outbox 或持久化 artifact manifest。

2.4、可靠任务执行与运行隔离

分析任务采用 Transactional Outbox + 租约 fencing + Redis Stream，明确处理数据库提交、消息投递和 Worker 崩溃之间的空窗；它不是简单的“先写 PG 再发 Redis”。

sequenceDiagram
    participant FE as React 前端
    participant API as FastAPI
    participant PG as PostgreSQL
    participant D as Outbox Dispatcher
    participant B as Dramatiq Broker
    participant W as Analysis Worker
    participant AI as TradingAgentsGraph

    FE->>API: POST /api/v1/analysis-tasks + Idempotency-Key
    API->>PG: 同一事务写 task(PENDING) + outbox(PENDING)
    API-->>FE: 202 Accepted + task_id
    D->>PG: 短事务 SKIP LOCKED 抢占 Outbox 为 DISPATCHING + dispatch lease
    D->>B: 事务提交后 send(task_id, attempt_no)
    D->>PG: 以 dispatch lease 确认 outbox=PUBLISHED; task=QUEUED
    W->>PG: 条件领取 QUEUED，生成 lease_token
    W->>AI: 新建 RunContext + Graph，并启动独立心跳后执行 propagate()
    AI-->>W: 阶段进度 / 结果
    W->>PG: 以 lease_token 校验并保存报告/迁移终态
    W->>B: 无（Broker 不保存业务真相）
    W->>PG: 可重试错误：同一事务置 RETRYING、递增 attempt_no 并写新 Outbox；不可重试/耗尽：置 FAILED
    W->>PG: FAILED 提交后才由 TaskEventService 发布 failed；新 attempt 的 queued 必须在 Outbox 确认投递后发布

任务投递、租约与幂等协议：

analysis_tasks 增加 idempotency_key、input_hash、attempt_no、lease_token、lease_expires_at、heartbeat_at、next_retry_at、cancel_requested_at；非空 idempotency_key 唯一。相同 key 且相同 input_hash 返回原任务；相同 key 但不同输入返回 409 IDEMPOTENCY_KEY_REUSED。key 限制为 1–128 个 URL-safe 字符，并按任务保留期清理。相同输入去重是否启用由产品配置决定，不能隐式合并不同任务。

新增 task_outbox：以 (task_id, attempt_no) 唯一，保存 message_type、最小 payload、status(PENDING/DISPATCHING/PUBLISHED/FAILED/CANCELLED)、dispatch_lease_token、dispatch_lease_expires_at、retry_count、next_attempt_at、published_at 和 trace context。任务创建或业务级重试均在同一事务写入对应 attempt 的 Outbox；Dispatcher 是业务消息的唯一发布者。超时的 DISPATCHING 可由其他 Dispatcher 接管。

Worker 领取消息时仅允许条件更新当前 attempt_no 相等且状态为 QUEUED 的任务；每次领取生成新的 lease_token。默认 lease_ttl=120s、heartbeat_interval=30s，均为配置项且 heartbeat_interval < lease_ttl / 2。旧 attempt 的 heartbeat、完成、失败、取消均因 attempt 或 token 不匹配而拒绝写入。

Dramatiq 仅处理进程崩溃等消息传输级短暂重投。可重试业务错误统一由分析模块计算 next_retry_at，在同一事务递增任务 attempt_no 并生成新的 Outbox；旧 attempt 不发布 failed。禁止两套重试策略叠加。

CANCEL_REQUESTED 与所有终态任务不得再被 Dispatcher 投递；Dispatcher 对已领取但在发送前被取消的 Outbox 直接标记废弃。到达 Broker 的历史消息必须通过 task_id + attempt_no + 状态条件领取过滤。未运行取消由 finalize_pending_cancellation() 原子废弃对应 Outbox 并置为 CANCELLED；运行中取消为协作式，Worker 在图阶段边界检查，但不承诺中断正在进行的 LLM 请求。

AI 运行隔离与产物归档：

每个 task_id + attempt_no 都有独立 RunContext：trace_id、交易日、脱敏 config_snapshot、model_snapshot、provider_snapshot、core_version 和 artifact_dir。

首期一个 Worker 进程同一时刻只运行一个 AI 图任务；扩容只通过增加独立 Worker 进程/容器完成，并受全局 LLM 并发限制约束。每次执行必须新建 TradingAgentsGraph，禁止缓存或跨任务复用其可变 State/callback handler。

平台产物根目录固定为 var/runs/{task_id}/{attempt_no}/。首期保留与限额：完整 State 与原始文本默认保留 90 天；单任务 max_artifact_bytes_per_task=100 MB、单文件 10 MB；产物卷全局高水位 20 GB（可配置），回收按最旧优先（LRU）并跳过仍有有效租约的目录；清理后保留结构化摘要，受影响 Report section 置 UNAVAILABLE。通过可注入 RunArtifactSink 保持 CLI 既有 logs/、results/ 行为不变；平台模式先写入 var/runs/.staging/{task_id}/{attempt_no}/{lease_token}/，逐文件执行大小/脱敏/允许扩展名校验，写入 manifest.json（task_id、attempt_no、lease_token、文件清单、checksum、core_version）并完成文件与目录同步。校验通过后仅允许在同一挂载卷/同一文件系统内以 os.replace 原子发布到最终目录；若最终目录已存在，仅 checksum 与 manifest 完全一致时视为幂等成功，否则视为 fencing 冲突，绝不覆盖。文件系统与 PostgreSQL 不存在跨资源原子提交：发布成功后才由持有当前 lease 的 TaskService.complete_task() 在同一数据库事务保存报告和 manifest 引用；DB 提交失败或进程在两者之间崩溃可能留下未引用的最终目录，任务不得置为成功。清理/reconciliation 作业在宽限期后删除无数据库 manifest 的 staging 及未引用最终目录，不删除仍有有效 lease 的目录；数据库 manifest 指向缺失文件则告警并把报告读模型降级为 UNAVAILABLE，不伪造内容。前端只获取受控引用，不获取本地绝对路径。

SSE 基于 Redis Streams。仅六种业务事件以 Stream ID 去重，客户端可用 ?after=<stream_id> 显式续读；服务端优先使用 Last-Event-ID，其次使用 after。heartbeat、reset 是仅有的非持久化控制事件，不分配 Stream ID、也不影响续读游标。每个任务 Stream 配置 stream_maxlen、stream_retention_seconds，由定期 XTRIM MINID 执行时间保留；请求游标早于最早保留 ID 时服务端发送一次固定字段的 reset 控制事件后关闭连接。若 PG 已终态却缺少对应 Stream 业务终态事件，Router 先按已提交状态幂等补写相应 completed、failed 或 cancelled 后再回放；补写失败只关闭连接，让客户端按 REST 轮询规则对账。

任务状态机：

PENDING → QUEUED → RUNNING → SUCCEEDED
   │        │         │
   └────────┴─────────┴→ CANCEL_REQUESTED → CANCELLED
RUNNING(attempt n) ───────→ RETRYING(attempt n+1 + outbox PENDING) → QUEUED(attempt n+1)
RUNNING(attempt n) ───────→ FAILED

PENDING：PG 事务已经提交但尚未确认投递到 Broker；Dispatcher 扫描对应 Outbox 直到确认发布或任务被取消。

QUEUED：Broker 已确认接收 (task_id, attempt_no)，等待 Worker。

RUNNING：Worker 以任务当前 attempt 原子抢占成功，记录 worker_id、lease_token 和开始时间。

RETRYING：仅用于数据源网络故障、LLM 限流、Redis 暂时不可用等临时错误。fail_or_retry() 在同一事务将任务由当前 RUNNING(attempt n) 置为 RETRYING、递增 attempt_no 为 n+1、计算 next_retry_at 并写入 (task_id, n+1) 的 task_outbox(PENDING)；此阶段不发布 failed。Dispatcher 确认新 Outbox 已投递后才迁移 RETRYING → QUEUED 并发布 queued(attempt_no=n+1)。

FAILED：输入、配置、不可恢复 Provider/LLM 错误或重试耗尽。仅在数据库已提交该终态后发布 failed；failed 从不表示“本次 attempt 可重试”。

CANCEL_REQUESTED：本地界面请求取消。对于 PENDING、QUEUED、RETRYING，finalize_pending_cancellation() 在一个事务中废弃当前/待发布 Outbox 并迁移为 CANCELLED，由取消 API 与 Dispatcher 扫描共同调用；对于 RUNNING，Worker 在 Agent 阶段回调和外部调用间隙检查取消标志，对不可中断的在途 LLM 调用待返回后停止后续图推进，再携带 lease token 迁移为 CANCELLED。

2.6、API 契约与前后端协作边界

统一前缀 /api/v1。FastAPI Pydantic Schema 和版本化 OpenAPI 是 REST DTO/API Client 的唯一契约源：CI 生成并校验 backend/openapi/openapi.v1.json，前端据此生成 TypeScript DTO/API Client。SSE 采用独立的传输协议（业务帧 id/event/data、无 ID 控制帧 event/data、游标与保留策略）和由 Pydantic 定义、同样纳入 OpenAPI 的 payload Schema；EventSource transport 不由 REST 生成器生成。前端不得手写后端 TaskStatus、AnalysisLayer、TaskEventType、Task 或 Report DTO；只维护 UI ViewModel 和展示常量。既有事件研究 /predict 暂时保留，新路径通过适配层复用其底层算法；预测端点是同步响应的受控容量操作，不进入分析任务 Outbox。

Report 顶层包含 schema_version、report_version、generated_at 和 sections；每个区块以 AVAILABLE ｜ UNAVAILABLE ｜ NOT_REQUESTED 明确状态，避免用”字段缺失”混淆未请求、数据缺失和执行失败。每个 section 字段为 {block: market|sector|stock|decision, status, title?, summary?, content?, charts?, unavailable_reason?, retryable?}；顶层另含 task 元信息、data_sources: [{label, source, as_of}] 与可选 risk_note；区块内容字段来源见 §3.1.5 的 DTO 区域映射。report_version 仅用于响应可追溯，首期不提供版本选择参数或 UI。

SSE wire format 的 event 严格且仅允许八种值：六种业务事件 queued、started、progress、completed、failed、cancelled 与两种控制事件 reset、heartbeat。六种业务帧固定为 id/event/data，均持久化到 Redis Stream、分配 id，其 payload 必须含 task_id、attempt_no、occurred_at、字面量 schema_version: "v1"；failed 只能在数据库终态 FAILED 已提交后发送。RETRYING 是仅经 Task REST DTO 暴露的状态：重投只创建新 attempt Outbox，确认投递后以新 attempt_no 的 queued 重新进入 SSE 流。reset、heartbeat 是只发送 event/data、无 id 的控制事件例外，均不持久化、不分配 Stream ID：reset.data 固定且仅为 {task_url, earliest_event_id, occurred_at, schema_version: "v1"}；heartbeat.data 固定为 {connection_id, sent_at, schema_version: "v1"}。前端用命名事件监听器接收后统一映射为 { id: lastEventId, eventType: eventName, payload: JSON.parse(data) }；eventName 即 SSE 的 event 字段，payload 不重复 id/event。服务端游标优先级为 Last-Event-ID > after > 0-0，仅以业务 Stream ID 回放；游标裁剪时服务端只发送一次 reset 后关闭连接，客户端清空局部事件窗口并读取 REST 状态。

市场读接口的成功响应必须包含 source、as_of、source_updated_at、freshness_status(FRESH｜STALE｜UNAVAILABLE)、market_timezone；返回对象另以 availability_status 或 Problem Details 区分资产禁用、休市、上游失败及无热点，前端不得依据字段缺失猜测状态。

热门概念：GET /api/v1/market-data/concepts/hot?market=CN&as_of=2026-09-04&interval=1d&from=2026-08-01&to=2026-09-04&cursor=&limit=20

market、interval、from、to、limit 必填；as_of 可选，省略时读取最新已完成热点快照。cursor 为不透明游标，limit 上限 30（首期 top_n=30）；所有概念的 bars 与请求 interval/range 对齐。

成功响应为 {as_of, algorithm_version, result_status, items, source, source_updated_at, freshness_status}，下一页仅位于 envelope meta.next_cursor；每个 item 为 {concept_code, concept_name, rank, hotness_reason, period_return, daily_changes?: [{date, change_pct}]（近 10 个交易日逐日涨跌幅，来源板块层热点 TOP 矩阵，供卡片展开）, updated_at, bars[]}。hotness_reason、rank 与 algorithm_version 是唯一热点解释来源。

没有满足条件的热点时返回 200 + items: []、result_status=NO_HOT_CONCEPTS，不是错误；有结果固定为 result_status=OK。热点响应不复用资产目录的 availability_status；快照过期可返回 STALE 并展示旧快照与时间；上游失败返回 503，前端不能改用静态概念名单。

宏观信息：GET /api/v1/macro-information?cursor=&limit=20&market=CN&topic=

cursor 不透明、limit 必填且受上限约束，market 和 topic 可选。data 仅返回 {items}，下一页仅位于 envelope meta.next_cursor；每项为 {id, title, occurred_at, market_tags, macro_topic, summary, source, related_assets, research_status, event_id?: int（关联已审核事件 ID，有则返回，供事件研究预填）}。

仅返回 review_status=APPROVED 的投影；无结果返回 200 + 空 items，前端展示“暂无可展示的事件研究宏观信息”。查询失败使用 Problem Details，不从预测响应或报告文本拼装列表。

2.6.2 AI 投研看板、任务列表、创建任务与幂等键

AI 投研看板：GET /api/v1/analysis-dashboard

看板是面向 /ai 的只读聚合投影，不能由前端扫描 Cursor 任务列表、逐个请求报告后拼装；接口统一返回 envelope，响应不含 SSE 事件、任务请求参数、租约/Outbox、artifact 路径或报告全文。

data 固定为 {pending_actions, active_tasks, recent_conclusions, generated_at}。三个数组各自有固定、服务端可测试的最大条数（首期 pending_actions=10、active_tasks=10、recent_conclusions=5），并按 updated_at DESC, id DESC（结论按 completed_at/报告生成时间）稳定排序；数组为空是正常业务结果。

pending_actions 只包含两类需要行动的事实：终态 FAILED 任务，或 SUCCEEDED 任务中 Report.sections.<name>.status=UNAVAILABLE 的区块。字段为 kind: FAILED_TASK ｜ REPORT_SECTION_UNAVAILABLE、task_id、task_type、ticker、effective_trade_date?、updated_at、error_code、error_summary、unavailable_blocks?: [{block: market|sector|stock|decision, reason?: str}]、retryable。kind=FAILED_TASK 时 error_code/error_summary 必填、unavailable_blocks 为 null；kind=REPORT_SECTION_UNAVAILABLE 时 unavailable_blocks 非空（同一任务多区块不可用聚合为一条，不重复出现）、error 字段为 null。不得把 RETRYING、CANCELLED、NOT_REQUESTED、字段缺失或普通报告读取中的瞬时网络错误写入待处理。

active_tasks 只包含 PENDING ｜ QUEUED ｜ RUNNING ｜ RETRYING。字段为 task_id、task_type、ticker、effective_trade_date?、status、attempt_no、updated_at、next_retry_at?；不携带阶段日志，任务进度继续仅由详情 SSE 提供。

recent_conclusions 只包含具备可阅读报告的 SUCCEEDED 任务。字段为 task_id、task_type、ticker、effective_trade_date?、completed_at、conclusion_summary（≤200 字）、risk_flag（bool）、risk_hint?、has_report（bool）、updated_at。conclusion_summary 与 risk_flag/risk_hint 必须在 ReportService 保存版本时从结构化 artifact 明确投影并落库，看板接口只读；无法形成可靠摘要时 conclusion_summary=null，前端只显示任务元信息和详情入口，不截取报告正文。

任务列表：GET /api/v1/analysis-tasks?cursor=&limit=&status=

cursor 为可选、不透明的 keyset 游标；首次请求省略或传空。limit 为可选正整数，默认 20、范围 1..100。status 为可选任务中心筛选值：all（默认）返回全部任务状态，active 映射 PENDING ｜ QUEUED ｜ RUNNING ｜ RETRYING ｜ CANCEL_REQUESTED，succeeded 映射 SUCCEEDED，failed 映射 FAILED，cancelled 映射 CANCELLED。未知参数、超出范围的 limit 或非法 status 值统一返回 422 INVALID_TASK_FILTER。

排序严格固定为 updated_at DESC, id DESC；id 是 updated_at 相同情况下的稳定 tie breaker。游标编码最后一条记录的 (updated_at, id)，后续页只取严格位于该元组之后的记录；不得以 offset、前端时钟或可变排序替代。所有页均以 envelope meta.next_cursor 给出续页游标；最后一页为 null。

3.1.2、bootstrap 组合根与跨切面详细设计

设计要点

使用 FastAPI + Pydantic v2 定义路由和 Schema；路由只作协议转换，业务编排在 Service 层完成。

使用 pydantic-settings 统一加载 .env 与部署环境变量；启动时校验 DATABASE_URL、REDIS_URL、YOHO_API_KEY、数据源 Token 等必填项。

生命周期拆为 init_logging、init_postgres、init_redis、validate_settings、shutdown_resources，避免超长 lifespan。

使用 ContextVar 注入 X-Trace-ID，API、任务和 Worker 日志均携带相同 trace_id。

不实现账号、密码、JWT、Refresh Token、Cookie 会话、角色权限或资源所有权校验；API 与前端均按单人本地运行假设设计。

任务创建采用 Redis 滑动窗口限流和幂等键，避免浏览器重复点击投递多项同类任务；客户端每次新的用户提交意图生成 UUID Idempotency-Key，同一意图的网络/提交重试必须复用该 key，新提交必须生成新 key。服务端以 key 绑定首个请求的规范化 input_hash：同 key 同 hash 返回原 202 创建结果，同 key 不同 hash 返回 409 IDEMPOTENCY_KEY_REUSED。

首期仅 loopback local-only，无 LAN：非容器开发时 API 监听 127.0.0.1；Compose 内 API 以 uvicorn --host 0.0.0.0 --port 8000、Nginx 以 0.0.0.0:80 监听，只有 frontend 以 127.0.0.1:${FRONTEND_HOST_PORT}:80 映射给宿主机，API 使用内部 expose，Redis/PostgreSQL/Mongo/Worker 均不配置宿主 ports。这是容器网络通信需要，不是可信私网或认证边界；LAN 访问属于未来独立方案，必须同时定义认证、TLS、CORS 和 audit，不能复用无认证接口。

跨 Service 约束：

TaskService 是任务状态机的唯一写入口；Worker、Dispatcher、恢复作业和取消 API 都必须调用它，禁止绕过 Service 直接更新 analysis_tasks.status。

ReportService 是 analysis_reports 的唯一写入口；保存成功后再由 TaskService 将任务置为 SUCCEEDED，两者必须在同一数据库事务中完成。

TaskEventService 不改变 PostgreSQL 状态；它只将已发生的事实以事件形式推送给前端。即使 Redis 故障，任务仍以数据库状态正确结束。

自选与组合在同一 investment_workspace 模块内，但仍是两个独立聚合：WatchlistService 与 PortfolioService 不得互调 Repository 或共享 revision；仅共享无持久化行为的 InstrumentRef 值对象。首期不建立 OperationHistoryService 或同步操作历史依赖；排障使用结构化日志与 trace。

组合 Router

任务状态迁移的唯一责任：

create_task                    创建 task(PENDING) + outbox(PENDING)，不迁移任务状态
confirm_outbox_published       PENDING/RETRYING → QUEUED（仅 dispatch lease 确认 Broker 发布后，提交后发布对应 attempt 的 queued）
claim_for_execution             QUEUED(current attempt) → RUNNING（校验消息 attempt 与当前 attempt_no，并生成 lease_token)
request_cancel                  RUNNING → CANCEL_REQUESTED；未运行任务委派到 finalize_pending_cancellation
finalize_pending_cancellation  PENDING/QUEUED/RETRYING/CANCEL_REQUESTED（无运行 lease）→ CANCELLED
complete_task                   RUNNING → SUCCEEDED
fail_or_retry                   RUNNING(attempt n) → RETRYING(attempt n+1)+outbox(PENDING)，或 → FAILED；仅后者提交后发布 failed
mark_cancelled                  CANCEL_REQUESTED → CANCELLED（必须持有当前 lease）
recover_expired_leases          过期 RUNNING(attempt n) → RETRYING(attempt n+1)+outbox(PENDING)，不发布 failed；过期 DISPATCHING/PENDING 投递补偿由 Dispatcher 扫描

任何 Service 收到不满足前置状态的请求时不静默覆盖：查询类返回当前状态；写入类返回明确的领域冲突错误，由 API 映射为 409 Conflict，Worker 记录重复消息并安全退出。

3.1.4、analysis Worker 与实时事件适配器详细设计

适配器设计

选择 Dramatiq + Redis Broker 作为分析任务执行框架，而非手写 Redis List 或 FastAPI BackgroundTasks。

原因：

多 Agent 分析持续数十秒到数分钟，API 必须可独立扩容且不被计算阻塞；

Dramatiq 提供独立进程消费、重试和中间件扩展，避免双 Worker/双任务路径；

任务状态和最终报告写 PostgreSQL，Broker 不承担业务真相；

TradingAgentsGraph.propagate(init_state, progress_callback) 已提供接入点，无需侵入各 Agent。

Worker 执行器职责（同步图 / 同步 Worker 固定模型）：

liveprofit-worker 首期固定 Dramatiq --processes 1 --threads 1；Actor 线程调用同步 Worker Service 的 claim_for_execution() 原子抢占任务，无法抢占、attempt 过期或任务已终态则安全退出；扩容只能增加独立 Worker 进程/容器，并受全局 LLM 并发限制。

Actor 线程独占调用 TradingGraphAdapter.execute() 创建图、构造初始 State 并同步执行 propagate()；不得在 API asyncio loop 或 Worker event loop 中运行该阻塞调用。

抢占后创建 LeaseHeartbeat 守护线程：每个 tick 都由独立 sync SessionFactory 调用 renew_lease()，不与 Actor/进度回调共享 Session 或 Redis client；默认 30 秒 tick、120 秒 TTL。任何 tick 返回 false 或到达 task deadline 都置 thread-safe stop flag，Actor 只能在 progress_callback、图节点/外部 I/O 返回边界协作停止，不能承诺中断在飞 LLM 调用。

Actor 线程将 progress_callback(message) 映射为 {sequence, phase, message, occurred_at}，使用其专属同步 TaskEventStreamPort Adapter 写入 Redis Stream；回调前读取 stop flag 和 CANCEL_REQUESTED，发现后调用 mark_cancelled()。心跳、图执行和进度发布均不共享 Session。

成功时先停止并 join 心跳线程、确认仍持有 fencing 权限，再将 AnalysisArtifact 连同 attempt_no、lease_token 传给 complete_task()，在同一事务保存报告并置为 SUCCEEDED；失去租约则放弃 artifact、事件和终态写入。

失败时停止心跳并分类异常，携带 attempt_no、lease_token 调用 fail_or_retry()：可重试错误只提交 RETRYING、递增 attempt_no 并创建下一 attempt Outbox，不发布任何 SSE；新 Outbox 确认投递后由 Dispatcher 发新的 queued。不可重试或重试耗尽才提交 FAILED 并发布 failed。业务异常已被 fail_or_retry() 处理后 Actor 正常返回，禁止叠加 Dramatiq 业务重试。

Worker 本身不直接更新任务/报告表，也不自行决定状态迁移。

SSE 事件白名单严格且仅包含下表八种。六种业务事件均以 id/event/data 写入 Redis Stream；两种控制事件只发送 event/data。任何其他 event 值（包括重试或终态补偿专用事件）均属于协议错误，禁止发布、持久化、回放或由前端注册。

Dispatcher 入口 backend.workers.dispatcher:main 是唯一常驻调度模型：启动先执行一次过期租约恢复，再循环执行 dispatch_due(now, dispatch_batch_size)，按 recovery_interval_seconds 再次恢复租约，空闲时按 dispatch_poll_interval_seconds 加抖动退避。可启动多个 Dispatcher，依赖 SKIP LOCKED + dispatch lease 协调；收到 SIGTERM/SIGINT 后停止新一轮领取、完成当前短事务并退出，未确认的 dispatch lease 由到期接管。Scheduler 若未来引入，只创建业务任务，不承担 Outbox/recovery。

docker/nginx.conf 的 SSE 专用反代契约如下。proxy_read_timeout 必须大于 SSE heartbeat 间隔并保留容错（首期 75s 对应服务端空闲心跳不高于 30s）；禁止 gzip、proxy cache 和 response buffering，确保 Redis Stream 帧逐条到达浏览器。

location ~ ^/api/v1/analysis-tasks/[^/]+/events$ {
    proxy_pass http://api:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Request-ID $request_id;
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    chunked_transfer_encoding on;
    proxy_read_timeout 75s;
    proxy_send_timeout 75s;
    add_header X-Accel-Buffering no always;
}

location /api/ {
    proxy_pass http://api:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Request-ID $request_id;
}

location / {
    try_files $uri $uri/ /index.html;
}

3.2.2、统一 REST Schema 与错误映射

所有 /api/v1 成功 JSON（含 POST、PATCH、PUT 和 DELETE）返回 {data, meta}；meta 至少包含 request_id、schema_version: "v1"，Cursor 列表额外仅在 meta.next_cursor 返回不透明续页游标。删除固定 200，data 为 {deleted: true, resource_id}，不使用 204。

Router 将模块领域错误映射为 RFC 7807 Problem Details，固定包含 code、request_id、retryable；404、参数/业务校验 422、状态/版本冲突 409、受控容量 503/504 均不得泄露堆栈、Token、Provider 原始异常、租约或 artifact 内部路径。

TaskDTO.events_url 与 report_url 是必填只读相对 URL，必须由 data.id 派生；列表只输出 TaskListItemDTO 允许字段。所有请求/响应 DTO、枚举、Problem Details 和 SSE payload 由 Pydantic Schema 导出为 backend/openapi/openapi.v1.json，前端禁止重写同名领域类型。

五、已确认决策 / 待确认问题

5.1、已确认决策

后端以 Python/FastAPI 为主，复用现有 LangGraph、AKShare/Tushare 与事件研究模块；不引入 Node/Java 作为 AI 核心后端。

PostgreSQL + pgvector 是正式数据主库；Redis 负责任务 Broker、实时事件和缓存；MongoDB 保持既有可选缓存定位。

长任务使用独立 Dramatiq Worker + Redis Broker，不使用 FastAPI BackgroundTasks 作为主执行路径。

进度使用 SSE 与 Redis Streams，支持断线补读：queued/started/progress/completed/failed/cancelled 是带 Stream ID 的业务事件；reset/heartbeat 是无 ID 控制事件。可重试异常只迁移 RETRYING、递增 attempt 并写新 Outbox，确认投递后发布新的 queued；failed 仅在数据库进入 FAILED 后发布。

采用模块化单体：同一仓库中 API 与 Worker 可以独立部署，暂不拆分微服务。
