## 一、背景与动机

### 1.1、现状

**功能一（轮动期追高/低吸分析）缺口：**

- 板块轮动预测分析师（`AI/sectorAgents/analysts/sector_rotation_analyst.py`）已具备主线识别、新晋热点、退潮预警、情绪周期判定和明日预测能力，但其分析框架是"围绕主线展开"的——第一步主线识别之后，后续步骤默认存在可跟踪的主线。当市场处于**轮动期（无明确主线）**时，分析师缺少针对性的输出结构：不会主动区分哪些板块适合追高、哪些适合低吸。
- 板块新闻分析师模板（`AI/templates/sector/sector_news_analyst.md`）速览块已有 `主线状态: <有主线(名称)/快速轮动/无方向>` 字段，但仅有判定、无轮动期的可操作战术输出。
- 整个系统没有任何图表能力：logviewer（`AI/logviewer/app.py`）报告 tab 仅用 `st.markdown`/`st.json`/`st.code` 三分支渲染 `logs/{ts}/reports/` 下的 md/json/其他文件（`_render_reports`，[app.py:172](AI/logviewer/app.py#L172)）；`pyproject.toml` 依赖中无任何图表库（matplotlib/plotly 均不在 `.venv` 中）。用户无法一眼看到"各个板块的情况"。

**功能二（政策新闻占位）现状：**

- `get_industry_policy_news(curr_date)` 是明确标注的**一期占位**（[interface.py:448](AI/dataflows/interface.py#L448)），恒返回 `"数据不可用：暂无行业政策新闻聚合数据源。"`，板块新闻分析师 prompt 中的「产业政策/行业新闻」章节（[sector_news_analyst.py:47](AI/sectorAgents/analysts/sector_news_analyst.py#L47)）实际为空壳，分析师只能靠 LLM 知识推断。
- 事件研究系统（`AI/eventStudy/`）已有现成的事件流基础设施：爬虫（财联社电报 + 金十数据快讯为启用源，新浪 7x24/东财快讯为默认禁用备源）→ Redis 待审草稿（30 天 TTL，带 AI 预填 `ai_suggestions`，分类体系含「产业政策」）→ 人工审核 → PG `events` 表（`approved/ignored`）。这条流当前只服务于事件研究（相似事件检索/预测），**未被板块层消费**。
- 审核通过的事件天然带 `event_type`/`importance` 字段，待审草稿带 `ai_suggestions` 预填——两者合并即可为板块新闻分析师提供"近期产业政策/重大行业新闻"的真实输入。

### 1.2、目标

**功能一**：板块层发现无明确主线、处于轮动期时，输出**适合追高组**与**适合低吸组**两个战术分组（每组含板块名、入选逻辑、操作提示、风险、置信度）；同时生成**行业 + 概念近 10 日逐日涨跌幅热力图**（交互式 HTML，同一页面上下两图），在 logviewer 运行报告 tab 中展示各板块情况。

**功能二**：`get_industry_policy_news` 从占位变为真实实现——从事件研究系统的事件流（PG approved + Redis pending 合并）读取近 N 日产业政策/重大行业新闻，注入板块新闻分析师 prompt，由 AI 逐条分析**利好什么、利空什么**，并沉淀为报告「政策/事件催化」章节。

**非目标**（明确不做）：不新增板块层第 4 个分析师节点；不改事件研究系统的爬虫/审核流程（只读消费）；不做板块新闻的事件影响量化（CAR 归因）；不做图像渲染进 LLM prompt（图表仅供人看）。

## 二、架构设计

```
Sector Layer (sector_layer_graph，不新增节点)
├── Sector News Analyst      ← policy_news 注入内容变为真实事件流
│     （dataflow.get_industry_policy_news → eventStudy.integration.industry_news）
├── Sector Tech Analyst      （不变）
└── Sector Rotation Analyst  ← 轮动期追高/低吸分组（prompt+模板扩展）
      │                        ← 第 4 数据块（行业基本面，供低吸判断）
      └── charts.py 生成热力图 → logs/{ts}/reports/charts/sector_daily_heatmaps.html
                                  （行业 + 概念上下两子图，缺一侧数据时单图）
                                    ↑
                    logviewer 报告 tab（.html 渲染分支，st.components.v1.html）

事件研究系统（已有，只读消费）
爬虫 → Redis 待审草稿(ai_suggestions) → 人工审核 → PG events(approved/ignored)
                              └──────────────┬──────────────┘
                                      合并去重过滤格式化
```

数据流向汇总（接续关系）：

1. 事件流：PG `events` 表（`approved`，`event_type='产业政策' OR importance≥4`）+ Redis `events:pending:*`（`ai_suggestions` 同类过滤）→ `industry_news.fetch_recent_industry_events()` 格式化 str → `interface.get_industry_policy_news()` → `sector_news_analyst` prompt 的 `policy_news` 参数 → LLM 分析利好/利空 → `sector_news_report` → logviewer。
2. 热力图数据：`interface.get_industry_daily_returns_matrix(days=10)` + `interface.get_concept_daily_returns_matrix(days=10, top_n=30)`（新）→ provider 结构化 dict → `charts.generate_sector_heatmaps()` → HTML 文件（行业 + 概念子图）→ logviewer `.html` 渲染分支。
3. 追高/低吸：rotation node 4 块数据（轮动矩阵/概念涨幅/连板梯队/行业基本面）→ LLM 按新 prompt 判定主线状态 → 轮动期输出追高组/低吸组 → `rotation_prediction_report`（速览块同步新增字段）。

### 2.1 数据模型设计

本方案**不新增/不修改任何 `AgentState` 字段**。涉及的跨模块结构：

| 结构 | 字段 | 类型 | 写入者 | 说明 |
|------|------|------|--------|------|
| `get_industry_daily_returns_matrix` / `get_concept_daily_returns_matrix` 返回值 | `source` | `str` | Provider | `"tushare"` / `"akshare"`（口径标注） |
| | `dates` | `list[str]` | Provider | 升序交易日，`YYYYMMDD`，最长 10 |
| | `names` | `list[str]` | Provider | 行业名 / 概念名，行序与 pct_matrix 对应（provider 获取序，未排序） |
| | `pct_matrix` | `list[list[float\|None]]` | Provider | 逐日涨跌幅（%），`None`=当日该板块无数据 |
| 热力图文件 | `logs/{ts}/reports/charts/sector_daily_heatmaps.html` | 文件 | `charts.py` | 自包含 plotly HTML（inline JS），行业 + 概念两子图（缺一侧数据时单图） |
| 事件流输出 | 格式见 3.3.1 | `str` | `industry_news.py` | 以 `#` 开头=数据可用；不可用串不以 `#` 开头 |

结构化返回契约（沿用于事件研究方案的实现偏差记录③）：新增结构化接口不支持/失败时返回 `None`（不返回 `_not_supported()` 的 str，避免破坏 dict/DataFrame 消费方）。图表模块收到 `None` 即静默跳过（无图，不影响分析）。

## 三、详细设计

### 3.1 轮动期追高/低吸分析（扩展板块轮动预测分析师）

#### 3.1.1 模块设计

**System prompt 变更**（`_ROTATION_SYSTEM_PROMPT`）：

- 第一步「主线识别」改为「**主线判定**」，输出二选一结论：
  - **明确主线**：连续多天上榜 + 涨停家数走扩 + 连板高度上升（沿用现有判定依据）→ 后续按现有框架输出主线梯队预测；
  - **轮动期（无明确主线）**：上榜板块分散、无连续上榜主线、涨停家数均值低、多板块竞争且高度压制 → 进入轮动期战术分组。
- 新增「轮动期战术分组」步骤，**仅当主线判定为轮动期时输出**，每组 2-5 个板块，每个板块必须包含：板块名、入选逻辑（引用具体数据证据，如"连续 3 日上榜但涨停家数未走扩"）、操作提示（追高/低吸的具体条件）、风险、置信度（高/中/低 + 一句话依据）：
  - **适合追高组**判定依据：涨停家数走扩中、连板高度抬升、连续上榜但未形成唯一主线、行业资金仍在流入（行业基本面块参考）；
  - **适合低吸组**判定依据：趋势未破坏的回调（曾上榜、排名回落但未掉出视线）、行业主力资金未撤离（资金流参考）、蓄势上升（TOP N 外排名持续爬升）、情绪周期冰点/修复期的低位板块。
- 主线明确时明确要求**不输出**分组（避免把主线梯队和战术分组混在一起）。
- 「## 已获取的数据」章节追加第 4 个占位段「### 行业基本面\n{industry}」，并在 `prompt.partial(...)` 中接线 `industry=_block_content("industry")`（与现有 3 个占位同处注入，[sector_rotation_analyst.py:177-183](AI/sectorAgents/analysts/sector_rotation_analyst.py#L177-L183)）。**此接线是数据流闭环的必须环节**——缺它则行业基本面块被拉取、参与 `#` 门控与短路判定，但内容永不进入 LLM prompt，"追高组判定依据（行业资金仍在流入）"没有数据来源。

**第 4 数据块（行业基本面）**：

- `_BLOCK_LABELS` 追加 `("industry", "行业基本面")`；`calls` 追加：

  ```python
  "industry": lambda: "\n\n".join([
      dataflow.get_industry_sector_performance(days=10),
      dataflow.get_sector_fund_flow(days=5),
  ]),
  ```

- 可用性判定沿用现有契约（可用以 `#` 开头）：两函数均为双数据源 6 接口方法之一、同 provider 家族，实际同可用/同不可用；拼接后首块为 `#` 开头即整块可用，第二块内部的不可用串自然展示给 LLM（`数据不可用：...` 行）。首块不可用而次块可用时整块判不可用——两函数同源，此组合实际不会发生，不做特殊处理（在代码注释注明）。
- **部分可用降级规则扩展**（与现有规则同风格）：缺失行业基本面 → 追高/低吸分组仍可输出（基于其余块），置信度上限"中"；与其他块缺失规则同时触发时取更严格的一档。

**输出模板变更**（`AI/templates/sector/sector_rotation_analyst.md`）：

- 速览块（`## 〇、轮动预测速览` 的 ``` 代码块，标题与块结构**保持不变**，保证 `_extract_rotation_prediction` 的正则提取继续命中）追加 3 行：

  ```
  主线状态: <明确主线(名称) / 轮动期(无明确主线)>
  追高组: <板块名|逻辑|风险>  ← 仅轮动期输出；主线明确时写 无（主线明确）
  低吸组: <板块名|逻辑|风险>  ← 同上
  ```

- 新增章节「三、主线判定与轮动期战术分组」（主线判定的证据链；轮动期时输出追高组/低吸组明细，主线明确时写"主线明确，不输出分组"）；原「三、新热点与蓄势板块」→ 四，「四、退潮预警」→ 五，「五、情绪周期判定」→ 六，「六、明日预测 TOP3-5」→ 七，「七、跨体系交叉验证」→ 八。正文中原章节引用（如"见第六节"类措辞）同步改号。
- 数据可用性规则块追加：行业基本面块缺失时的降级说明（见上）。

**State / 提取逻辑**：`sector_rotation_analyst.py` 的 `node` **结构不变、仅增量变更**（`_ROTATION_SYSTEM_PROMPT`、`_BLOCK_LABELS`、`calls`、prompt partial 接线、热力图调用点）；`_extract_rotation_prediction` 与返回字段均不变。

### 3.2 板块涨跌幅热力图（行业 + 概念，plotly + logviewer 渲染）

#### 3.2.1 模块设计

**新接口 ×2**（按 CLAUDE.md Data Provider 强制规则：先基类 → Tushare 优先 → AKShare 补充，两 provider 签名完全一致）：

- `BaseStockDataProvider.get_industry_daily_returns_matrix(days: int = 10)` 与 `get_concept_daily_returns_matrix(days: int = 10, top_n: int = 30)`：默认返回 `None`（结构化接口不支持约定，见 2.1）。
- **行业矩阵** `TushareProvider` 实现：抽取 `get_industry_sector_performance` 内部的行业日线拉取循环为私有方法 `_fetch_industry_daily_series(days) -> (performance_list, daily_closes)`（现有 `daily_closes` 复用逻辑上移，两公共方法共用，**不新增 API 调用**）；矩阵生成复用 `daily_matrix_utils.daily_pct_from_closes` + `master_dates_from_series`（与文本逐日章节同源同口径，`DAILY_COLS=10`）。**必须**先 `_sort_asc_by_trade_date` 升序归一（CLAUDE.md 降序坑规则），单测含降序输入回归用例。`None` 元素：某行业缺某日时该格为 `None`。
- **行业矩阵** `AKShareProvider` 实现：同样抽取 `_fetch_industry_daily_series`（复用 `_detect_date_column`/`_detect_close_column`、`_call_with_timeout`、连续失败中断逻辑），矩阵生成同上。
- **概念矩阵** `TushareProvider` 实现：**复用现有 `_collect_concept_daily_snapshots`**（`get_concept_daily_top_gains` 与 `get_concept_board_heat_rank` 已共用，含 `_DC_CONCEPT_DAILY_CACHE` 共享缓存），**TOP N 选取与概念热度接口同口径——复用其现有逻辑：按当日涨幅预筛 TOP30 + 热度公式（涨跌幅×0.6+量变化率×0.4）排序，行集合与概念热度 TOP30 逐日章节完全一致**（默认 top_n=30）；矩阵生成复用 `daily_matrix_utils`（与概念热度 TOP30 逐日章节同源同口径）。
- **概念矩阵** `AKShareProvider` 实现：抽取 `get_concept_board_heat_rank` 内部的批量 `stock_board_concept_hist_em` 拉取为私有 helper（TOP N 同口径：热度公式涨跌幅×0.6+量变化率×0.4 排序取前 N），矩阵生成同上。

**新文件 `AI/eventStudy/integration/industry_news.py`**（事件研究模块内新增 integration 能力，与既有 `langgraph_tool.py` 同目录）：

- 常量（模块级，env 可覆盖）：

  ```python
  DEFAULT_DAYS_BACK = parse_int_env("EVENT_STUDY_INDUSTRY_NEWS_DAYS", 7)   # 回看窗口（自然日）
  MAX_PER_SOURCE = parse_int_env("EVENT_STUDY_INDUSTRY_NEWS_PER_SOURCE", 20)  # 单源条数上限
  MAX_TOTAL = parse_int_env("EVENT_STUDY_INDUSTRY_NEWS_MAX_TOTAL", 30)     # 合并后总条数上限
  MIN_IMPORTANCE = parse_int_env("EVENT_STUDY_INDUSTRY_NEWS_MIN_IMPORTANCE", 4)  # 纳入阈值
  ```

- 核心接口：

  ```python
  def fetch_recent_industry_events(curr_date: str, days_back: int = None) -> str:
      """近 N 日产业政策/重大行业新闻（PG approved + Redis pending 合并）。

      curr_date: 'YYYY-MM-DD'（分析交易日，即 state["trade_date"]）。
      返回 Markdown 章节（可用时以 "#" 开头）；PG/Redis 全不可用时返回不以
      "#" 开头的不可用串（对齐板块层门控契约风格）。
      """
  ```

- **时间窗口（t0 纪律）**：`win_start = curr_date - days_back`，`win_end = curr_date + 1 天`（**右开区间**，Asia/Shanghai tz-aware）——包含分析日当天的全部事件（晚间分析时当日事件已全知），**排除未来事件**，与项目 T-1/T+0 数据纪律一致。
- **PG approved 分支**：

  ```sql
  SELECT title, content, event_type, event_subtype, event_condition,
         importance, announced_at, source_url
  FROM events
  WHERE status = 'approved'
    AND announced_at >= %s::timestamptz AND announced_at < %s::timestamptz
    AND (event_type = '产业政策' OR importance >= %s)
  ORDER BY importance DESC, announced_at DESC
  LIMIT %s
  ```

  连接用 `AI/eventStudy/db/connection.py::get_connection()`（自带会话时区 Asia/Shanghai），`finally: conn.close()`。PG 连接/查询异常 → `logger.warning` 记录原因，该源记为空并置 `pg_unavailable` 标志。
- **Redis pending 分支**：`AI/eventStudy/review/review_dao.py::get_pending_events()` 取全部草稿 → Python 过滤：`announced_at`（ISO8601）落在窗口内 **且**（`ai_suggestions.event_type == '产业政策'` 或 `int(ai_suggestions.get("importance") or 0) >= MIN_IMPORTANCE` 或 `int(importance_hint or 0) >= MIN_IMPORTANCE`）→ 按 `int(ai_suggestions.get("importance") or importance_hint or 3)` 降序、`announced_at` 降序 → 截前 `MAX_PER_SOURCE` 条。**None 兜底为显式要求**：实测爬虫草稿 `importance_hint` 常为 `None`（金十无星级、财联社级别未映射）、`ai_suggestions` 常为 `{}`，`None >= 4` 与 `max(None, int, 3)` 均抛 TypeError——过滤与排序一律用 `int(... or 0)` / `... or 3` 兜底（沿用 `review_app.py:84` 的既有口径）。Redis 不可用 → 空 + `redis_unavailable` 标志——**该标志由 `config.is_redis_available()` 显式探测**，不依赖 `get_pending_events` 的返回值（其返回 `[]` 无法区分"草稿为空"与"Redis 不可用"）。`get_pending_events` 对坏 JSON 已静默跳过（其自身契约），本模块不再兜底。
- **合并去重**：归一化 key = 标题前 20 字符（strip 空白）；**approved 优先**（人工审核过优先保留，pending 同 key 丢弃）→ 时间降序 → 截前 `MAX_TOTAL` 条。
- **格式化输出**（可用时以 `#` 开头）：

  ```markdown
  # 近期产业政策/重大行业新闻（近 {N} 日，共 {M} 条；来源：事件研究系统）

  ## 已审核事件（{m1} 条）
  - [MM-DD HH:MM] ★★★★★ 《标题》 [产业政策] {来源}
    摘要（≤100 字，无摘要写"（无摘要）"）

  ## 待审核快讯（{m2} 条，AI 预填分类，未经人工确认）
  - [MM-DD HH:MM] ★★★☆☆ 《标题》 [产业政策/AI预填]
    摘要…

  > 事件流来自事件研究系统（PG approved + Redis pending 合并去重）。
  > 单源截断提示：已审核事件按重要性截前 20 条（如有截断）。
  ```

  - 星级 = `importance`（1-5）→ ★ 串；待审事件重要性取 `ai_suggestions.importance` 或 `importance_hint`（缺省 3）。
  - 单边不可用时输出对应注记行：`> PG 事件库不可用（原因），仅含待审快讯。` / `> Redis 草稿区不可用（原因），仅含已审核事件。`
