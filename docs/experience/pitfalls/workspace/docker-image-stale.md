# Docker 验证镜像不随代码演进，旧镜像把旧语义状态写进生产

**一句话**：跨多日任务中早先构建的「验证镜像」不要有长期复用预期——代码演进后旧镜像仍能启动并通过健康检查，但会用旧语义污染共享状态（本例：把错误覆盖摘要写进生产 Redis），只有容器整栈验收能暴露。

## 表象

市场数据自动补齐 T9 容器验收（2026-10-02）时，复用 9-24 构建的 worker 验证镜像启动 dispatcher/market-worker 容器。容器健康、API 正常返回，但 `GET refresh-status` 中 `CN_STOCK_DAILY` 变成 expected 5652 / `CATALOG_INCOMPLETE`，与宿主（同代码同数据库）返回的 5568 FRESH 不一致。

## 根因

- 镜像构建于 9-24，其后代码有两次演进（9-24 当天的「股票主目录」覆盖语义修正 + 10-02 量化生命周期的停牌语义升级）。旧镜像内的 Dispatcher 每 5 分钟重算覆盖摘要并写入**生产 Redis 的资源状态键**，而当前 API 进程按设计读取这份共享状态——旧语义摘要通过共享 Redis 污染了当前系统的对外状态。
- 单纯看容器「启动成功 + 健康检查通过 + 日志无报错」完全发现不了：旧代码自洽运行，只是语义旧。
- 容器内 `db.instrument.db` 模块常量的默认连接回退 `127.0.0.1`（容器内不可达），也只在直连复算时暴露——宿主 `.env` 的 PG_* 回退在容器里不是可用的连接路径。

## 正确姿势

- 容器整栈验收前**按当前 HEAD 重建全部镜像**（或至少核对镜像构建提交与 HEAD 的业务代码差异），不沿用隔日验证镜像。
- 验收不只查健康检查：用容器内 API 实际查询与宿主同一份业务状态，核对关键数值一致（本例六组覆盖计数）。
- 验证镜像名带构建日期/提交标记（如 `:verification-head`），与 compose 服务名区分，避免 `:latest` 静默复用。
- 容器内直连复算（`docker exec` 跑与宿主相同的只读查询）是区分「代码问题」与「镜像陈旧」的最快手段。

## 关联

- 容器内市场连接解析要求见 [市场数据自动补齐方案](../../../requirements/archive/市场数据自动补齐/plan.md) §4.6.1-6（实施时显式注入统一解析后的 psycopg DSN，保留旧 PG_* CLI fallback，禁止容器内回落 localhost）。
- 类似「共享状态被旧版本写入」的教训：本任务 Redis 只承担可重建状态，旧摘要被新代码重算自愈，没有造成持久数据损坏——若共享状态是持久事实则后果完全不同。
