## 一、背景与动机

### 1.1 现状

板块轮动预测分析师（[sector_rotation_analyst.py](../../AI/sectorAgents/analysts/sector_rotation_analyst.py)）目前只有**一张数据**：

- `get_concept_rotation_ranking(days=5, top_n=10)` — Tushare 打板专题 `limit_cpt_list` 的 5 日逐日 TOP10 矩阵，按**涨停家数**排名（THS 题材分类），含连板高度。

缺失两个关键维度：

1. **概念板块的"涨幅"本身**：现有矩阵只按涨停家数排名，看不到概念板块的逐日涨幅排名。概念涨幅 TOP20 是识别主线/新热点的直接证据。
2. **全市场连板梯队与情绪周期数据**：现有矩阵只有板块级连板高度，没有全市场梯队结构（2板X只/3板Y只/…）、晋级率、炸板率——这些是判断市场情绪周期位置（冰点/修复/高潮/退潮）的核心指标，市场层技术分析师 prompt（[cn_tech_analyst.py](../../AI/marketAgents/analysts/cn_tech_analyst.py) L71）也要求"涨停梯队高度与连板数量 → 判断情绪周期位置"，但板块层一直没有对应数据。

### 1.2 目标

轮动预测分析师拿到**三张数据**（其余分析师不动）：

| 数据 | 窗口 | 内容 | 分类体系 |
|------|------|------|----------|
| 打板题材轮动矩阵（现有，窗口延长） | 5→**10 日** | 逐日 TOP10 涨停家数 + 连板高度 + 强度分级 | THS 题材 |
| **概念逐日涨幅 TOP20（新增）** | **10 日** | 每一天概念板块涨幅前 20 | 东财 EM 概念 |
| **连板梯队（新增）** | **20 日** | 每日涨停总数/最高板/各连板档家数 + 晋级率 + 炸板率 | 全市场个股 |

LLM 可据此判断情绪周期位置、主线持续性、新热点扩散效应，支撑"明日轮动预测"和"大盘适配度"。

## 二、架构设计

**不改变图谱结构**：轮动预测分析师仍是直连边（无工具循环），数据在 node 内直接调 dataflow 一次性拉取。改动集中在数据层（2 个新 provider 方法）+ 分析师 prompt + 模板。

```
数据层 dataflows/
├── base_provider.py          +2 方法签名（默认 _not_supported）
├── tushare_provider.py       +2 实现（dc_index 逐日 / limit_list_d 逐日）
├── akshare_provider.py       +1 实现（连板梯队，stock_zt_pool_em+zbgc_em）
├── limit_ladder_utils.py     新建：梯队归一化/晋级率/格式化 纯函数（双 provider 共享）
└── interface.py              +2 包装函数（hasattr dispatch）

分析师层 sector_rotation_analyst.py
└── node 内 3 次 dataflow 调用 + 门控改造 + prompt 扩展
模板层 sector_rotation_analyst.md
└── 新增梯队情绪周期章节 + 部分可用数据规则
```

无新增 State 字段（不做跨层传递，仅轮动分析师内部消费）。

### 2.1 数据模型设计

不涉及共享状态变更（无新 State 字段）。共享格式化模块的中间数据结构：

```python
# 每日梯队记录（两 provider 各自归一化后交给共享模块）
{"date": "20260807", "zt_total": 45, "ladder": {2: 8, 3: 4, 5: 1},   # ladder 不含首板；首板 = zt_total - sum(ladder)
 "open_broken": 6,      # 开板回封家数（Tushare: open_times>0；AKShare: 炸板次数>0，可 None）
 "zb_total": 12}        # 炸板家数（AKShare zbgc 股池；Tushare 无 → None）
```

## 三、详细设计

### 3.1 数据层 — `get_concept_daily_top_gains(days=10, top_n=20)`

#### 3.1.1 模块设计

- 接口签名：`get_concept_daily_top_gains(days: int = 10, top_n: int = 20) -> str`
- 基类：`_not_supported("逐日概念涨幅TOP20（仅 Tushare 支持 dc_index 按日快照）")`
- Tushare 实现：
  - 逐日回退采集：从今天向前 probe（`max_probe = days * 3` 兜底周末节假日），每日调 `dc_index(trade_date=d, idx_type="概念板块", fields="ts_code,name,pct_change,turnover_rate,up_num,down_num")`，成功收集 `days` 个交易日后停止；单日失败跳过并继续
  - 复用 `_get_dc_concept_index` 的缓存思路：把现有单快照缓存扩展为**按日 dict 缓存**（`_DC_CONCEPT_INDEX_CACHE = {date_str: df}`，上限 ~30 条防膨胀），现有调用方（名单接口/成分股接口）行为不变
  - 每日按 `pct_change` 降序取 TOP20 → 输出逐日矩阵 + 跨日上榜统计（帮助 LLM 判断持续性）
  - 输出格式（Markdown）：

    ```
    # 近 10 日东财概念板块逐日涨幅 TOP20 矩阵
    | 日期 | TOP20 概念板块（涨幅%） |
    |------|------------------------|
    | 20260807 | AI眼镜(+13.0%)、机器人(+10.8%)、… |
    …
    ## 跨日上榜统计
    | 概念板块 | 上榜次数 | 最近上榜日期 | 最新涨幅 |
    ```

- AKShare：不实现（`stock_board_concept_name_em` 仅当日快照，无历史逐日横截面接口；逐板块历史拉取 400+ 次调用不可行）

#### 3.1.2 三方依赖能力评估

- **Tushare `dc_index(trade_date, idx_type="概念板块")`：已实测 ✓**（2026-08-20 用真实 token 探测 20260807 → 返回 1031 行，含 `pct_change`，top3 涨幅 13.03%/10.84%/8.31%）。10 个交易日 = 10~15 次调用
- 现有代码已使用该接口（`get_concept_board_heat_rank` 的 dc_index 快照），无新权限依赖

#### 3.1.3 风险与验证方式

- 风险：单日无数据（新概念板块数波动、盘中）→ 跳过该日并在输出标注缺数据日；全部失败 → 返回 "近 N 个交易日无概念板块快照数据。"
- 验证：单元测试（mock `_api_call` 返回合成 DataFrame）+ 真实探测（已做过一次，实现后重跑一次完整 10 日拉取）

### 3.2 数据层 — `get_limit_up_ladder(days=20)`

#### 3.2.1 模块设计

- 接口签名：`get_limit_up_ladder(days: int = 20) -> str`
- 基类：`_not_supported("连板梯队（Tushare limit_list_d / AKShare stock_zt_pool_em）")`
- **Tushare 实现**：逐日回退采集 `limit_list_d(trade_date=d)`（同 probe 模式），过滤 `limit == 'U'`（涨停）：
  - 梯队：按 `limit_times` 分组计数（NaN/0 → 首板 1），`zt_total` = 涨停总数，最高板 = max(limit_times)
  - 开板回封：`open_times > 0` 的涨停家数（口径见下方脚注）
  - 每日记录归一化为共享记录 `{date, zt_total, ladder, open_broken, zb_total: None}`，保留当日 `{ts_code: limit_times}` 映射供晋级率计算
- **AKShare 实现**：逐日 `stock_zt_pool_em(date)`（连板数列）→ 梯队；`stock_zt_pool_zbgc_em(date)` → 炸板家数。注意 zbgc 接口**仅支持最近 30 自然日**，超期抛 ValueError → 当日 `zb_total=None` 并继续（梯队照常）
- **共享模块 `limit_ladder_utils.py`**（纯函数，双 provider 复用，单测目标）：
  - `calc_promotion_rates(day_records)`: 晋级率 = 今日 L 板且昨日 L-1 板（精确 ts_code 匹配）/ 昨日 L-1 板家数；L=2 的分母为昨日首板家数。产出 1→2、2→3…逐日矩阵
  - `calc_break_rate(day_records)`: 炸板率。AKShare 口径 = 炸板家数/(涨停+炸板)；Tushare 无炸板池 → 用开板回封率 = open_broken/zt_total（脚注说明两口径差异）
  - `format_ladder_matrix(day_records, promo, break_rates)`: 输出 Markdown

  输出格式（Markdown）：

  ```
  # 近 20 日连板梯队与情绪数据
  ## 每日连板梯队
  | 日期 | 涨停总数 | 首板 | 2板 | 3板 | … | 最高板(家数) | 开板回封 | 炸板数 | 炸板率 |
  ## 晋级率矩阵（精确个股匹配）
  | 日期 | 1→2 | 2→3 | 3→4 | … |
  > 口径脚注：晋级率 = 今日L板且昨日L-1板家数 / 昨日L-1板家数；…
  ```

#### 3.2.2 三方依赖能力评估

- **Tushare `limit_list_d(trade_date)`：已实测 ✓**（20260819 → 166 行、18 列，含 `limit_times`(1.0/2.0/3.0…)、`open_times`、`limit`('U'/'D')，当日 36 只涨停）。与 `limit_cpt_list` 同为 2000 积分档，现有权限已覆盖
- **AKShare `stock_zt_pool_em(date)`：源码确认 ✓**（`stock_feature/stock_ztb_em.py`，date 参数，含"连板数""炸板次数"列）
- **AKShare `stock_zt_pool_zbgc_em(date)`：源码确认 ✓**（date 参数，但**仅最近 30 自然日**，超期抛 ValueError → 降级处理）

#### 3.2.3 风险与验证方式

- 风险：`limit_times` 可能为 NaN/0 → 归一为首板；20 个交易日约 28 自然日，AKShare 炸板池 30 日窗口基本覆盖但边界日可能缺失 → 标注"炸板数据不可用（超出30日窗口）"
- 验证：共享模块纯函数单测（合成记录，覆盖晋级率精确匹配/NaN/无昨日数据边界）+ 真实探测（limit_list_d 已实测；实现后完整拉一次 20 日）

### 3.3 分析师层 — `sector_rotation_analyst.py`

#### 3.3.1 模块设计

- node 内改为 3 次 dataflow 调用：
  ```python
  rotation_matrix = dataflow.get_concept_rotation_ranking(days=10, top_n=10)   # 窗口延长
  concept_top    = dataflow.get_concept_daily_top_gains(days=10, top_n=20)     # 新增
  ladder         = dataflow.get_limit_up_ladder(days=20)                       # 新增
  ```
- **门控改造**：现逻辑是 rotation_matrix 不可用即短路占位。改为：**三者全不可用 → 占位短路（行为同现状）；至少一组可用 → 正常分析，缺失数据块以 `(数据不可用：<原因>)` 占位注入 prompt**
- prompt 扩展（system prompt + 模板）：
  - 两个新数据段：`### 东财概念逐日涨幅 TOP20 矩阵（近10日）`、`### 全市场连板梯队与情绪数据（近20日）`
  - 分析框架新增**第五步：情绪周期判定**——基于涨停总数趋势、最高板高度、晋级率、炸板率判断当前情绪周期位置（冰点/修复/高潮/退潮），作为"大盘适配度"和明日预测置信度的依据
  - 主线识别步骤补充：概念涨幅 TOP20 的上榜持续性（EM 体系）与 THS 轮动矩阵交叉验证（沿用现有跨分类体系规则：方向性参考，不做一一对应）
  - 现有强度分级/轮动分类逻辑不变

#### 3.3.3 风险与验证方式

- 风险：prompt 变长（新增约 2~3k 字数据块）；部分可用场景下 LLM 可能忽略缺失标注 → 在"数据可用性规则"中明确要求
- 验证：集成测试（真实 LLM + 真实 Tushare，仿 test_sector_news_analyst 风格）跑通出报告

## 四、已确认决策 / 待确认问题

### 已确认决策（用户已拍板）

1. 两组新数据仅喂**轮动预测分析师**（新闻/技术分析师不动）
