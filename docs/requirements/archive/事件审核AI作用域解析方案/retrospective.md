## 做对了什么（可复用）

- **方案评审 B1 的修复路径选择**：评审发现 force 谓词恒真会死循环后，弃版本标记方案改「前端 draft_ids 分片驱动」——循环有界由构造保证而非运行时收敛证明，且「重新预填全部」语义每次点击都诚实。评审推荐选项与最终落地选项不同，但选择理由写进了 decisions/plan，两轮核验均 PASS。
- **评审数字先行**：动方案前先实测 Redis 328 条草稿的 scope 分布（145 缺字段 / 162 market / 21 sector+stock），让「作用域都是市场」的机制归因有数据支撑，回填方案据此定稿。
- **名称→代码解析的分层设计**：LLM 只做语义判断与名称提取、代码由字典表确定性生成（用户拍板「LLM 不补代码」），幻觉风险在代码层面被结构性地挡住，比「存在性初筛兜底」更靠前。

## 踩了什么坑（教训）

- **CR 两轮才收净的两类新代码缺陷**：① `_unique_contains_map` 归属循环未去重输入名称——重复名称让同一行被多次计数，破坏「恰好 1 行」唯一性判定（恰好命中会误判为多行命中）；② Python `in` 与 ILIKE 的大小写语义不等价——归属判定需 `casefold` 对齐。两类都属「批量化改造时把逐条语义翻译错了」——逐条→批量的优化必须逐条核对语义等价（计数口径、大小写、通配符语义）。
- **force 收敛设计的两次返工**：mark_stale 方案在每轮请求时剥标记会让上一轮已重填的草稿再次失效（自己推演出的死角），最终 draft_ids 分片才成立——状态标记类收敛设计要推演「标记写入与读取在同一循环内交错」的路径。
- **给已被替代的旧界面做双链路改造是过度设计**：Streamlit 审核页已被平台集成版替代（API契约.md 7.3 写明「平台集成版替代 Streamlit review_app」），方案仍把它的 UI 对称展示/分片进度列入设计（评审 m7/m8 推波助澜），实现后被用户拍板撤销。**做方案时先核对旧界面的生命周期状态**——已被替代的入口只保证「AI 侧能力自动兼容、零 UI 改动」，不为其加功能。

## 下次改进

- 批量化改造（逐条查询 → 批量查询）时，先把语义等价点列成清单（计数口径/大小写/通配符/重复项/空集），每点配一个测试再动代码。
- 前端表格新增固定宽列时，先估算固定列总和与目标屏宽的差，超过即同时调弹性列的 minmax 下界——本任务的标题列塌缩本可在 08e9c34f 提交时避免。
