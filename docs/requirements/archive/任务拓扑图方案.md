## 一、背景与动机

### 1.1、现状

- AI 内核是 LangGraph 三层子图编排（`AI/graph/trading_graph.py`）：顶层 `Market Layer → Sector Layer → Stock Layer/Screening → END`，每层子图内封装具体节点（market 4 个 Analyst、sector 3 个、stock 12 个：4 分析师 + Bull/Bear Researcher + Research Manager + Trader + Risky/Safe/Neutral Analyst + Risk Judge），含辩论/风险条件循环边。
- 任务日志已按确定性目录落盘：`logs/tasks/{task_id}/{attempt_no}/{layer}/{seq:03d}_{NodeName}/`（`NodeName = _sanitize(图节点名)`，如 `CN News Analyst` → `001_CN_News_Analyst`，见 `AI/utils/llm_callbacks.py` 的 `_sanitize`）。backend 已有 execution-logs 树端点，详情页 [ExecutionLogsPanel.tsx](../frontend/src/modules/analysis/pages/task-detail/ExecutionLogsPanel.tsx) 以嵌套折叠树渲染全部调用日志。
- **缺失**：详情页只有"三档文案时间线"和扁平日志树，看不到流水线形状——任务跑到哪一层哪个节点、哪个节点出错、辩论循环走了几轮，都要在折叠树里上下翻找。
- 现状证据：`TaskProgressTimeline`（task-detail/TaskProgressTimeline.tsx）仅 market/sector/stock 三档；日志面板按 layer→node 树展开，无图结构。

### 1.2、目标

任务详情页新增「执行拓扑」区块：

1. 用 echarts graph 展示本次任务的**静态图拓扑**（三层 + 层内主节点；tools_*、Msg Clear 辅助节点折叠进主节点），结构来自 LangGraph 图定义本身（不手写第二份拓扑）；
2. 拓扑节点上**叠加本次运行状态**：未执行 / 已执行 / 执行中 / 出错（运行中每 5s 刷新"生长"，终态静态回看）；
3. **点击节点弹出面板**，展示该节点本次运行的全部调用日志（复用 execution-logs 树数据，零新内容端点）；
4. 内核零改动：拓扑提取模块为只读新模块，不触碰运行路径。

## 二、架构设计

```
API 进程（backend/）                                    前端（frontend/）
──────────────────────                                 ─────────────────────
GET /api/v1/analysis-tasks/{task_id}/graph-topology    GraphTopologyPanel（echarts graph）
  ├─ 任务查询（404 TASK_NOT_FOUND）                      ├─ 固定网格布局（row=层, order=层内序）
  ├─ AI/graph/topology.build_topology(                  ├─ 状态着色（灰/蓝/琥珀/红）+ 图例
  │      tuple(task.selected_layers))                   ├─ 运行中 5s 轮询，终态停
  │    └─ dummy 依赖编译三层子图                          ├─ 点击节点 → NodeLogsDialog（Radix Dialog）
  │       → get_graph() → 折叠辅助节点 → 主节点/边        │    └─ 复用 execution-logs 树数据（同 query 缓存）
  ├─ scan_run_status(run_dir, terminal, failed)        └─ 未执行节点弹窗显示空态
  │    └─ logs_reader 枚举 + _sanitize 匹配
  │       → 每节点 dirs / status / invocation_count
  └─ Envelope[GraphTopologyDTO]
```

- 本方案不改变现有架构：worker/内核执行路径零改动；拓扑提取只发生在 API 进程（backend 已有延迟导入 AI 的先例，real_graph_factory.py:66）。
- 数据链路复用 [任务执行调用日志方案](任务执行调用日志方案.md) 的全部现成设施（确定性日志目录、logs_reader、execution-logs 树 DTO、前端 useExecutionLogsQuery 缓存）。

### 2.1 数据模型设计

**API DTO**（新增 `backend/api/schemas/graph_topology.py`，Envelope 复用现有）：

| 字段 | 类型 | 说明（含真实取值示例） |
|------|------|----------------------|
| `GraphTopologyDTO.task_id` | str | 任务 id，如 `"33ded201-9f3a-4b5e-8c1a-123456789abc"` |
| `GraphTopologyDTO.attempt_no` | int | 当前 attempt，如 `2` |
| `GraphTopologyDTO.available` | bool | run 目录是否存在且可读；false 时 nodes 仍为静态结构、status 全 not_executed |
| `GraphTopologyDTO.generated_at` | datetime | 组装时间（ISO 8601） |
| `GraphTopologyDTO.nodes` | list[TopologyNodeDTO] | 全量主节点（含未执行） |
| `GraphTopologyDTO.edges` | list[TopologyEdgeDTO] | 全量主边 |
| `TopologyNodeDTO.id` | str | `"{layer}:{label}"`，如 `"stock:Bull Researcher"`（label 在层内唯一，空格原样保留） |
| `TopologyNodeDTO.label` | str | 图节点显示名，如 `"Bull Researcher"`、`"Screening"` |
| `TopologyNodeDTO.layer` | str | 所属层目录名，如 `"market"` / `"sector"` / `"stock"` / `"screening"` |
| `TopologyNodeDTO.row` | int | 行号（= 层执行序）：market=0、sector=1、stock=2、screening=2；screening 任务中 stock=3 |
| `TopologyNodeDTO.order` | int | 层内主节点序（DFS 前序），如 stock 层 `Bull Researcher=4`、`Risk Judge=11` |
| `TopologyNodeDTO.status` | enum | `"not_executed"`（无日志目录）/ `"executed"` / `"running"`（非终态且含全局最大 seq 目录）/ `"error"` |
| `TopologyNodeDTO.invocation_count` | int | 匹配到的节点日志目录数（LLM 目录 = LLM 调用次数 + 预测目录 = 纯代码节点的 DP 落盘；辩论循环/逐票循环会产生多个 LLM 目录），如 `3` |
| `TopologyNodeDTO.dirs` | list[str] | 相对任务目录的节点目录路径，按名（seq）排序，如 `["stock/005_Bull_Researcher", "stock/007_Bull_Researcher"]` |
| `TopologyEdgeDTO.source` | str | 源节点 id，如 `"stock:Bull Researcher"` |
| `TopologyEdgeDTO.target` | str | 目标节点 id，如 `"stock:Bear Researcher"` |
| `TopologyEdgeDTO.kind` | enum | `"direct"`（普通边）/ `"conditional"`（条件边，虚线）/ `"loop"`（screening→stock 逐票循环边，虚线+标注） |
| `TopologyEdgeDTO.parallel` | bool | 存在反向边（如 Bull↔Bear 互指），前端画弧线避免重叠，如 `true` |

**TaskDTO 对称字段**：`graph_topology_url`（如 `"/api/v1/analysis-tasks/{task_id}/graph-topology"`），与 execution_logs_url 对称，TaskCreatedData 同步；当前前端不消费（client 按路径生成），保留 API 对称性。

**状态推导规则**（单点定义在 `scan_run_status`，逐条可测）：

0. 节点目录分两类：**LLM 目录** = 含节点级 `meta.json` 的目录（on_llm_start 最先写 meta，llm_callbacks.py:209）；**预测目录** = 无节点级 meta.json 的目录（dataprovider_log 为纯代码节点按 `llm_seq + 1` 预测序号创建，dataprovider_log.py:184——其 seq 与 stock 循环第一只票首个 LLM 目录**必然并列**，故必须区分）；
1. `available=false`（run 目录不存在）→ 全部 not_executed；
2. 节点匹配：layer 目录下 `list_nodes` 得 `{seq:03d}_{NodeName}` 目录，剥掉 `^\d+_` 前缀后与 `_sanitize(label)` 相等即匹配（如 `001_CN_News_Analyst` ↔ `"CN News Analyst"`）；`_sanitize` 直接复用 `AI/utils/llm_callbacks.py` 的私有函数（同一仓库、内核已 import 链内的纯函数，不复制第二份）；label 为**图节点全名**（含 " Analyst" 后缀，如 `"CN News Analyst"`，不是短名 "CN News"）；
3. `error` = 该节点任一目录（含预测目录）下 `list_dp_calls` 中任一 DP 目录 `meta.json` 的 `error=true`，**或**（任务终态 FAILED 且该节点含全局最大 seq 的 **LLM 目录**且该目录无 `res.md`）——后者覆盖 LLM 调用中途失败（on_llm_error 不落盘，llm_callbacks.py:301）的场景；该兜底只作用于 LLM 目录，预测目录不参与，防止并列 seq 下 Screening 假 error；
4. `running` = 任务非终态且该节点含全局最大 seq 的 **LLM 目录**（跨全部 layer 只在 LLM 目录集合内取 seq 前缀最大值；纯预测目录不参与，防止并列 seq 下 Screening 假 running）；
5. 其余有目录（LLM 目录或预测目录）→ `executed`；
6. `invocation_count = len(dirs)`（LLM 调用次数 + 纯代码节点的预测目录数，语义为"该节点本次产生的日志目录数"）；未匹配任何拓扑节点的目录（旧 run 遗留）忽略，不影响结果。

## 三、详细设计

### 3.1 AI 内核拓扑提取模块（`AI/graph/topology.py` 新建）

#### 3.1.1 模块设计

**职责**：以图定义本身为唯一事实来源，产出折叠后的静态拓扑。只读模块，不 import 进内核运行路径（仅 backend 延迟导入）。

**dummy 依赖构建**（已通读三个 builder 源码确认可行：`build()` 只接线、不调用 LLM）：

- `_Dummy` 类：`__getattr__` 返回 no-op 函数（`lambda *a, **k: ""`）——兜底"工厂函数在 build 时触碰 llm 属性"的场景；`toolkit=None`（`_get_tools` 的 `getattr(self.toolkit, tn, None)` 对 None 返回默认值 None）；
- **注意**（2026-09-08 评审确认）：market 的 `_get_tools` 对 `intl_news` 会**无条件** append `search_similar_events`（market_layer_graph.py:147-153，与 toolkit 无关，仅 try/except 包 import）——dummy 编译图中 International News Analyst 的 `tools_intl_news` ToolNode + 条件边**恒存在**（其余新闻类节点 tools 为空、直接边）。这不影响折叠视图（工具循环折叠进主节点），但 dummy 编译不是"全无 ToolNode"；
- 三层子图：
  - `MarketLayerGraph(_Dummy(), None).build()`（market_layer_graph.py:63）；
  - `SectorLayerGraph(_Dummy(), None, enable_structured_list=has_screening).build()`（sector_layer_graph.py:43；该参数只影响工厂闭包，不影响结构）；
  - `StockLayerGraph(_Dummy(), _Dummy(), None, None, None, None, None, None, _Dummy(), {}).build()`（stock_layer_graph.py:63；conditional_logic 用 `_Dummy` 使 `should_continue_debate` 等属性读取返回 no-op 函数，编译不调用）。

**提取与折叠**（`_extract_primary(graph)`，纯函数）：

1. `graph.get_graph()` → DrawableGraph；从 nodes 取节点名，从 edges 取 `(source, target, conditional)`；
2. 主节点过滤：排除 `__start__`/`__end__`、`Msg Clear *` 前缀、`tools_*` 前缀；
3. 辅助节点折叠：从每个主节点出发沿边 BFS，途经辅助节点直到下一主节点，产出主节点邻接表；路径上任一条边 conditional=true 则折叠边 conditional=true（实际只可能出现在首段 Analyst→Msg Clear 的条件边）；**路径回到源主节点（工具循环：Analyst →(cond) tools_x → Analyst）不产出自环边**——这正是"工具循环折叠进主节点"的语义，丢弃该路径即可；
4. `order` 分配：从 START 可达的首个主节点出发 DFS 前序（折叠邻接表、按插入序访问），visited 跳过循环回边——确定性输出（label 为图节点全名，含 " Analyst" 后缀）：market `International Event Extraction Analyst(0) → International News Analyst(1) → CN News Analyst(2) → CN Tech Analyst(3)`；sector `Sector News Analyst(0) → Sector Tech Analyst(1) → Sector Rotation Analyst(2)`；stock `Stock Tech Analyst(0) → Social Analyst(1) → News Analyst(2) → Fundamentals Analyst(3) → Bull Researcher(4) → Bear Researcher(5) → Research Manager(6) → Trader(7) → Risky Analyst(8) → Safe Analyst(9) → Neutral Analyst(10) → Risk Judge(11)`；
5. `parallel` 标记：折叠邻接表中 source→target 与 target→source 同时存在——只含 Bull↔Bear 双向辩论边；Risky→Safe→Neutral→Risky 是单向条件环（stock_layer_graph.py:183-197，无反向边），**不**标记 parallel。

**顶层组合**（`build_topology(selected_layers: tuple[str, ...]) -> Topology`，`functools.lru_cache` 缓存）：

- 镜像 `trading_graph._build_graph`（trading_graph.py:173-278）的连线逻辑，不实例化 TradingAgentsGraph（避免 LLM/API key 依赖）：
  - 层序列：`market → sector → (screening | stock) → END`；`"position"` 无图影响（不在层序列内）；
  - screening 模式：`stock` 不进顶层链，改为从 `Screening` 节点引一条 `kind="loop"` 虚线边到 stock 层首个主节点（Stock Tech Analyst），stock 层节点 row=3——对应 propagate 的逐票循环（trading_graph.py:394 `run_stock_loop`）；
  - 层间边：L 层最后主节点 → L+1 层首个主节点（如 `market:CN Tech Analyst → sector:Sector News Analyst`）；
  - 未知 layer 值：忽略（不影响结构；防御性兼容）。
- 返回 `Topology`（plain dict 结构：nodes=[{id,label,layer,row,order}]、edges=[{source,target,kind,parallel}]），backend 直接消费。

#### 3.1.2 三方依赖能力评估

- **langgraph 1.2.10**（uv.lock 实测版本）：`CompiledStateGraph.get_graph()` 是官方可视化 API（`draw_mermaid` 同源），返回 DrawableGraph（nodes/edges）。
  - **风险与兜底**：1.2.10 的 DrawableGraph 节点 `id`/`name` 属性名、Edge 的 `source`/`target`/`conditional` 字段、`__start__`/`__end__` 命名**实现第一步实测钉住**（单测固定期望值即锁定）；若 Edge 无 `conditional` 标记，兜底从 `graph.builder.branches`（`{起始节点: [branch]}`，branch.ends 为条件目标）推导条件边集合；两路均不可用才退化为本模块内静态条件边表（Bull/Bear/Risky/Safe/Neutral 出边，共 10 条），并在模块 docstring 标注退降原因。
- dummy 构建可行性：已通读三 builder 源码确认（本节 3.1.1）；无其他外部依赖。

#### 3.1.3 风险与验证方式

- 工厂函数在 build 时深读 llm 属性 → `_Dummy.__getattr__` 返回 no-op 函数兜底；若某工厂在 build 时调用 LLM 方法，测试立即失败（no-op 返回 `""`，不抛错即通过）——属可控暴露。
- 图定义变更（新增分析师/改连线）→ 提取自动跟随，`tests/graph/test_layer_topology.py` 的节点/边清单断言失败提醒同步更新，无静默漂移。
- lru_cache 线程安全（functools 内置锁）；编译成本 ~几十 ms（纯接线），API 进程首次请求一次性。
- 验证：单测 `tests/graph/test_layer_topology.py`（见 3.4 测试表第 1 行；命名与既有 `tests/graph/test_graph_topology.py`——顶层编排图节点集测试——区分）。

#### 3.1.4 文件变更清单

- **新建文件**：
  - `AI/graph/topology.py`：`_Dummy`、三层子图 dummy 构建 + `_extract_primary` 折叠/排序 + `build_topology` 顶层组合（lru_cache）；
  - `tests/graph/test_layer_topology.py`：节点/边清单断言 + 顶层组合 4 变体 + 缓存命中（对应 3.4 测试表第 1 行）。
- **修改文件**：无（内核运行路径零改动）。

### 3.2 backend 拓扑端点（`backend/`）

#### 3.2.1 模块设计

**新 schema** `backend/api/schemas/graph_topology.py`：2.1 节 DTO（Pydantic，Envelope 复用）。

**状态扫描纯函数** `backend/modules/analysis/application/graph_topology.py`（无 DB/IO 框架依赖，仿 execution_logs.py）：

```python
def scan_run_status(run_dir: Path, topology, terminal: bool, failed: bool) -> dict[str, dict]:
    """拓扑节点 id → {dirs, status, invocation_count}；规则见 2.1 状态推导。
    run_dir 不存在/不可读 → 全部 not_executed（available=False 由 router 判定）。"""
```

- 枚举复用 `AI.logviewer.logs_reader` 的 `list_layers`/`list_nodes`/`list_dp_calls`/`read_json`（纯 Python 模块，execution_logs.py 已有同款复用先例）；
- 节点目录名 → label 匹配复用 `AI.utils.llm_callbacks._sanitize`（私有函数直接 import，模块 docstring 注明依赖理由，防内核侧重构时误删）。

**新路由** `backend/api/routers/graph_topology.py`：

`GET /api/v1/analysis-tasks/{task_id}/graph-topology`

1. 经 `request.app.state.analysis_services` 查任务（复用 bundle）→ 不存在 404 `TASK_NOT_FOUND`（复用现有异常映射）；
2. `topology = build_topology(tuple(task.selected_layers))`（lru_cache 命中，实际每变体编译一次）；
3. `run_dir = resolve_execution_logs_root(settings.core) / "tasks" / str(task_id) / str(task.attempt_no)`（与 worker 写入侧同一解析函数，见任务执行调用日志方案 3.1.1）；目录不存在 → `available=false`（PENDING 尚未建目录是正常态）；
4. `terminal = is_terminal(task.status)`、`failed = task.status == FAILED`（复用现有状态判定）；

## 四、已确认决策 / 待确认问题

- **已确认决策**（2026-09-08，用户拍板）：
  1. 拓扑粒度 = 三层 + 层内主节点（tools_*、Msg Clear 等辅助节点折叠进主节点）；
  2. 拓扑来源 = 静态拓扑（LangGraph 图定义）+ 本次运行状态叠加（未执行/已执行/执行中/出错）；
  3. 点击交互 = 弹出面板展示该节点日志；
  4. 渲染 = echarts graph（不新增 React Flow 等图库）。
- **本方案自行决定的工程取舍**（如有异议请指出）：
  1. 拓扑提取用 dummy 依赖编译真实层图 builder（图定义单一事实来源），不手写第二份拓扑表；
  2. screening 任务：stock 层以「逐票循环」虚线边挂 Screening 之后（内核图定义无此边，属运行语义的可视化补充）；
  3. 弹窗复用 execution-logs 树数据（同 query 缓存），不新增按节点过滤的内容端点；
  4. 出错判定 = DP meta.error 或（FAILED 终态 + 全局最大 seq 的 LLM 目录无 res.md），LLM 失败无落盘标记（llm_callbacks on_llm_error 仅打控制台日志）故用后者兜底；
  5. TaskDTO 加 `graph_topology_url` 对称字段（当前前端不消费）；
  6. stock 循环多实例弹窗按调用次序列出、无 ticker 标签（v1 已知限制）；
  7. 纯代码节点日志盲区（v1 已知限制）：Screening 空池/空清单早退（screening_node.py 早退不调 dataflow）时零日志目录 → 节点恒显"未执行"；FAILED 任务无任何节点级错误时（首个 DP 前崩溃等）以面板任务级提示兜底，不承诺消除盲区。
