# 关键决策记录

## 2026-09-24 股票日线目标与单板块兜底

- 股票上市事实由 `market.instrument` 的 `stock_basic` 全状态目录负责；`sector_member` 仅表示分类，可能包含未上市 IPO，不能把目录外代码加入日线分母。目录内缺状态/日期仍阻断以防漏算已上市标的。
- 停牌以 `suspend_d(trade_date=目标日)` 返回的同日 S 类型为可信事实；R 为复牌，旧 `suspend_date` 参数被代理忽略，不再使用。
- `dc_daily` 单板块目标日缺有效行时才查东财原始 K 线；核对代码、日期及必需数值后写既有 `sector_daily`。两源均无 OHLC 时保留缺口，不用 `dc_index` 快照反推价格。
- 目标日 FRESH 与较早 `HISTORY_GAP` 各自呈现；覆盖已刷新后不继续展示旧 PARTIAL/FAILED 任务结论。

## 2026-09-23 不为可重建运行状态新增表（覆盖初稿存储选择）

- 背景：用户明确“非必要不增新表”，质疑初稿 refresh_state/refresh_job 两张 PG 表的必要性。
- 选项：PG 持久任务，或现有 Redis 存可重建状态、现有行情表存事实。
- 结论：取消新增表、字段和迁移；采用 Redis + 已有 Dramatiq Broker 的专用队列。PG session advisory lock 只用于现有连接上的实际执行互斥，不建表。
- 理由：本功能无永久审计需求；Redis 状态丢失可从真实行情重建，幂等补采可接受。原方案为可恢复的运行状态提供了不必要的持久表结构。
- 边界：短期任务历史、冷却次数可能随 Redis 数据丢失而消失；PG 与 Redis 不作跨库原子提交，靠定期核验恢复；长任务防重不只依赖 Redis TTL。

## 2026-09-23 自动补齐方向

- 背景：指数与板块只到 9 月 21 日，22 日上午采集后未在收盘后补跑。
- 选项：前端直接强制采集，或前端触发检查、后端按交易日统一准入。
- 用户确认：采用后者方向，先编写技术方案。
- 理由：避免盘中/休市误触发、多个页面重复采集和长请求阻塞。

## 2026-09-23 技术初稿默认值（历史记录，存储方案已被上条覆盖）

- 背景：板块耗时远大于指数，旧定时入口没有接入新平台；现有 AI Worker 为单线程。
- 选项：API 后台线程、共享 AI 队列、独立采集 Worker。
- 初稿推荐：既有 Dispatcher 统一准入/重试，独立 Market Worker 领取 PG 持久任务，公共 PG 执行锁保护全部采集入口。
- 理由：页面请求短、AI 分析不被采集占用、进程重启后任务可恢复。
