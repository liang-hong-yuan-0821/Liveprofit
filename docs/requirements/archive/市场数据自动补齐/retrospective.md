## 做对的

- **方案把「数据组定向补齐」和「页面刷新」解耦**：从旧 `collect_incremental` 的全量连带采集，变成六组独立目标日/窗口覆盖判定 + 有界重试，页面保留旧数据并在入库后精准失效。生产上真实缺口（US 指数、BK0165.DC）都被自动兜住，没有回到人工补采。
- **停牌必须独立可信源**：误用 `suspend_date` 的教训（代理忽略筛选返回 5000 条截断）推动官方参数 + 本地 S/R 校验，后续量化任务又升级为 `suspension_scope='full_day'` 多源证据——覆盖读模型与采集跳过口径始终统一，没有把「无行情」当「正常空」。
- **失败必须显式**：旧采集「摘要无 error 即成功」的坑被逐单元核验取代；子进程无结果退出从 PG 复核事实；本机网络 ACL 拒绝不再被当成可退避的上游空结果。

## 代价与教训

- **任务时间跨度大、交接依赖文档**：9-23 实施至 10-02 收尾期间，测试目录整体迁移（`tests/` 新布局 + tests.run 运行器）、量化任务演化停牌语义并加大量不可变触发器——恢复实施时 §4.6.3 的旧命令路径全部失效，且 contract 共享 fixture 被新触发器拦截（35 项 setup ERROR）、e2e spec 与 9-24 重写后的组件脱节。修复本身不难，但**共享测试基建的语义变化应在变更任务内同步所有消费方**，而不是留给后续任务接手时踩。
- **容器镜像与代码版本必须绑定**：T9 当时只构建了 worker 验证镜像，隔了 8 天后该镜像相对 HEAD 已是旧语义，容器整栈一度把错误摘要（5652/CATALOG_INCOMPLETE）写进生产 Redis 状态。镜像构建与代码提交不同步时，容器验收本身会暴露这种不一致——这次是验收拦下来的，也说明**验证镜像不该有长期复用预期**。
- **组件重写后 e2e 未重跑**：9-23 通过的两项 e2e 在 9-24 组件打磨（FRESH 隐藏旧任务文案、离线文案、重试按钮形态）后已脱节，一直无人发现，直到恢复收尾重跑才暴露。组件行为变化应把 e2e 纳入同一变更的必跑范围。
- **Redis 只做可重建状态**得到验证：停平台、换镜像、状态被旧语义污染后，重新核验 PG 即可自愈——设计假设成立。

## 对后续的建议

- 任务文件夹的「下一步/状态」要写清环境与版本前提（如镜像构建日期、测试目录布局版本），跨多日恢复时先核对 HEAD 与证据记录的差异（本次 9-24 证据对 HEAD 已过期，因量化任务改过共享文件）。
- 共享 fixture / 触发器 / 语义升级的任务，收尾时用 `tests.run --related` 或按模块把共同消费方跑一遍，而不是只跑自己模块。
- 历史缺口（V11）按来源可得性另行治理，不混入近 3 日自动补齐口径。
