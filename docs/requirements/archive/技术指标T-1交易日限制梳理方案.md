## 一、背景与问题现象

`AI/dataflows` 通过 `interface.py` 统一转发到 `TushareProvider` / `AKShareProvider` 两个数据源。

排查发现：部分接口内部依赖 Tushare 的 `trade_date` 精确匹配查询（如 `daily`、`daily_basic`、`index_daily`、`shibor_lpr`、`moneyflow`），这些接口有一个共同限制——

> **Tushare 的日频数据通常在当日收盘后（约 18:00-20:00）才完整入库。在非交易日（周末/法定节假日）或交易日盘中/收盘前调用，都拿不到"当日"数据，实际能拿到的最新数据是 T-1（上一交易日）。**

问题的严重之处在于：目前调用链路**直接把外部传入的 `trade_date`/`curr_date`（通常是"今天"）透传给这些接口**，没有任何交易日校正逻辑。一旦：

- 分析日期落在周末/节假日，或
- 当天是交易日但在收盘前调用（例如盘中或早盘触发分析任务）

就会出现两种表现：

- **A 类（强校验）**：接口内部按 `trade_date` 做精确匹配查询，查不到时直接返回 `"N/A"` / `"未获取到...数据"` / `"获取失败"`，分析报告出现明显空洞

- **B 类（隐性滞后）**：接口不强制校验日期，静默返回数据源当前能查到的"最新一天"（实际是 T-1），不报错但也不提示，分析报告里会不知情地使用滞后一天的数据

> **A/B 类判定标准**：本质区别在于接口的**查询方式**，而非表面上"是否报错"——
>
> - **A 类 = 精确日期匹配查询**（如 `trade_date=xxx`、`date=xxx` 等值查询）：命不中即无数据可返回，只能显式失败
> - **B 类 = 区间/最新快照查询**（如 `start_date~end_date` 区间查询、或取最新一行快照）：命不中时会自动退化到最近可用的一行数据，静默返回、不报错
>
> 查询方式的差异决定了两类问题只能采用不同的修复策略（详见 4.2 / 4.3）：A 类必须在查询前做日期校正以避免命不中；B 类无法/无需改变查询逻辑，只能在返回结果中补充真实数据日期作为提示。

全项目未发现任何"交易日历/工作日校正"相关的工具函数（已用 `grep` 确认无 `trade_cal`/`is_trading_day` 等实现），说明这是一个尚未被处理的系统性缺口。

### 2.3 关键结论

- **风险最高的是 `cn_tech_analyst.py`**：它在同一个节点里连续调用 `get_china_market_overview`、`get_market_breadth`、`get_market_fund_flow` 三个工具，全部依赖 `state["trade_date"]` 透传，且当前数据源为 Tushare 时（`LIVEPROFIT_DATA_SOURCE` 默认值），三者都可能因未到收盘时间或非交易日而拿不到当日数据。

- `StockstatsUtils`（个股技术指标）和 `get_china_daily_basic`（每日指标）虽然限制最严格（直接返回 N/A），但目前**未被任何 Toolkit 实际绑定使用**，属于潜在风险而非当前活跃 bug；一旦后续启用这两个工具，问题会立即暴露。

- akshare 数据源整体比 tushare 数据源"更宽容"（不强校验日期，静默取最新快照），但代价是**用户不知道数据实际对应哪一天**，存在"悄悄使用过期数据"的风险。

## 三、根因分析

1. **数据源特性**：Tushare 的 `daily`、`daily_basic`、`index_daily`、`moneyflow`、`shibor_lpr` 等接口均以官方交易日历为准，且当日数据需等收盘后由 Tushare 侧批处理入库，通常在 18:00-20:00 之后才稳定可查。

2. **调用链路缺陷**：`trade_date`（分析基准日期）由最外层调用方（如 CLI/API 入口）设置，一路透传到 `interface.py → provider`，中间**没有任何环节做"是否为已收盘的交易日"的校正**。

3. **接口契约不一致**：`BaseStockDataProvider` 约定"不可用时返回数据不可用，不抛异常"（见 `base_provider.py` 头部注释），但各接口对"取不到数据"的处理方式不统一——有的返回明确的失败文案（A 类），有的静默退化到最近可用数据（B 类），导致同样的"T-1 问题"在不同接口上表现完全不同，上层 LLM/Analyst 无法一致地感知和处理。

4. **板块层结构性缺口**：板块层的核心接口（`get_sector_technical_screening`、`get_sector_horizon_screening`、`get_industry_sector_performance` 等）**不接收 `curr_date` 参数**，内部硬编码使用 `datetime.now()` 作为数据锚点（见 `akshare_provider.py:1090`、`tushare_provider.py:799`）。这意味着即使市场层的日期校正生效，板块层的分析也无法与历史日期对齐。

5. **LLM 注入日期的不确定性**：`cn_tech_analyst.py:109` 只将 `current_date` 注入 system prompt，**不通过代码注入工具参数**。LLM 需要在 tool call 中自行补上 `curr_date` 参数。这意味着如果 LLM 忘记传参或传错，工具可能使用默认值或报错（详见 5.6）。

## 四、修复设计

### 4.1 新增公共交易日历工具

新建 `AI/dataflows/utils/` 包（含 `__init__.py`），在其中创建 `trading_calendar.py`，基于 Tushare `trade_cal` 接口 + 本地文件缓存（参考现有 `data/central_bank_calendar.json` 的落地方式），提供三个核心函数：

```python
def is_trading_day(date: str, exchange: str = "SSE") -> bool:
    """判断给定日期是否为交易日

    Args:
        date: 日期字符串，格式 YYYY-MM-DD
        exchange: 交易所代码，默认 SSE（上交所）。支持 SSE / SZSE / HKEX

    Returns:
        True 表示该日期是交易日
    """

def get_last_trading_day(date: str, exchange: str = "SSE") -> str:
    """获取 date 当天或之前最近的交易日

    Args:
        date: 参考日期，格式 YYYY-MM-DD
        exchange: 交易所代码，默认 SSE

    Returns:
        最近的交易日，格式 YYYY-MM-DD。
        如果 date 本身就是交易日，返回 date。
    """

def get_available_trade_date(target_date: str, exchange: str = "SSE") -> str:
    """综合交易日历 + 当前时间，返回实际可用的最新数据日期

    这是 A 类接口日期校正的主要入口。规则：
    1. 如果 target_date 是历史日期（< 今天），不做时间判断，仅校验是否为交易日：
       - 是交易日 → 返回 target_date
       - 不是 → 返回上一个交易日
    2. 如果 target_date 是今天：
       a. 是交易日 且 当前时间 >= 收盘截止时间（默认 15:30）→ 返回 target_date
       b. 是交易日 但 当前时间 < 15:30 → 返回上一个交易日
       c. 不是交易日 → 返回上一个交易日

    Args:
        target_date: 目标日期，格式 YYYY-MM-DD
        exchange: 交易所代码，默认 SSE

    Returns:
        实际可用的数据日期，格式 YYYY-MM-DD
    """
```

#### 4.1.1 缓存策略

- **缓存文件**：按年分文件，存储到 `AI/dataflows/data/trade_cal_{year}.json`
- **文件格式**：`{"2026": ["2026-01-02", "2026-01-03", ...], "2027": [...]}`
- **刷新策略**：查询某年时，若缓存文件不存在或已过期（超过 1 年），从 Tushare `trade_cal` 拉取全年数据并写入缓存；若缓存存在且有效，直接读取
- **缓存预热**：首次初始化时拉取当年 + 下一年数据

#### 4.1.2 三级降级策略

`trade_cal` 接口可能因 Tushare token 过期、超时、频率限制等原因不可用。降级链路：

| 优先级 | 方案 | 说明 |
|--------|------|------|
| 1 | Tushare `trade_cal` + 本地文件缓存 | 主方案，按年缓存 |
| 2 | AKShare `tool_trade_date_hist_sina()` | 备选数据源，返回交易日列表 |
| 3 | 纯周末跳过（weekday-only） | 最终兜底：只排除周六日，不处理法定节假日。此时在日志中标注 `"节假日未校正，使用 weekday-only 降级"` |

降级时记录 warning 日志，并在后续 LLM prompt 中标注数据源降级情况。

#### 4.1.3 多交易所扩展

`exchange` 参数预留，初始实现默认 `"SSE"`。后续如需港股分析（`get_hk_market_overview`），传入 `exchange="HKEX"` 即可复用同一套逻辑。

#### 4.1.4 时区与数据就绪时间

所有日期判断统一使用 `Asia/Shanghai` 时区（`zoneinfo.ZoneInfo("Asia/Shanghai")`），避免服务器部署在不同时区导致的偏差。当前项目中 `datetime.now()` 假设服务器本地时间（`default_config.py` 无时区配置），交易日历模块需显式处理时区。

数据就绪截止时间通过环境变量 `TUSHARE_DATA_READY_HOUR` 配置，默认值 `20`（即 20:00），对应 Tushare 批处理入库的典型完成时间。仅用于"今天是否是今天"的快判——如果当前时刻 >= 当天 20:00（Asia/Shanghai），且当天是交易日，则认为当天数据已就绪。

#### 4.1.5 数据存在性重试（比纯日历校正更可靠）

交易日历只能判断"交易所是否开市"，**无法判断 Tushare 是否已完成当天数据的入库**（可能有延迟）。因此，在 A 类接口中，日期校正后仍需在数据查询时做**有限步数的数据存在性回溯**——这和 `get_concept_board_heat_rank`（`tushare_provider.py:631-649`）已有的模式一致，应当统一抽象：

```python
def with_trade_date_retry(fn, date: str, max_steps: int = 3) -> tuple[str, str]:
    """对精确日期查询做有限回溯，直到查到数据或达到步数上限

    从 date 开始向前回溯（每次回到上一个交易日），调用 fn(date) 直到返回非空。
    最多回溯 max_steps 步。

    Returns:
        (result, actual_date): 查询结果和实际命中数据的日期
    """
```

- 回溯步数上限 `max_steps=3`（可配置），防止无限回溯
- 如果回溯 3 步仍为空，返回空结果 + 标注"近 3 个交易日均无数据"
- 已有先例：`get_concept_board_heat_rank` 的回溯循环（`tushare_provider.py:631-649`），本方案将其抽象为公共工具

#### 4.1.6 容错策略：fail-open

当交易日历完全不可用（三级降级全部失败），采用 **fail-open** 策略：原样返回输入日期，记录 `logger.warning`，不做校正。

理由：
- 不做校正的行为 = 当前现状，不会比现在更差
- fail-closed（拒绝运行）会导致整个分析链路中断，影响面过大
- 日志中的 warning 提示运维人员关注数据源配置

### 4.2 A 类修复策略：日期校正在哪里注入

#### 4.2.1 架构决策

有三种可选注入点。推荐 **State 层入口统一校正（方案 C）为主 + interface 层防御性校验（方案 A）为辅**：

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| A | `interface.py` 每个函数内部 | 精准，每个接口独立校正 | 侵入性大，重复代码多 |
| B | Provider 内部 | 各数据源自治 | Tushare/AKShare 行为差异大，难以统一 |
| **C（推荐）** | Graph State 层入口 | 一次校正，全局生效，不侵入数据层 | 对"使用原始日期做计算"的场景需保留原始日期 |

#### 4.2.2 推荐方案细节

**Step 1 — State 层入口校正**

在 `trading_graph.py` 的 `propagate()` 入口处（`trade_date = init_state.get("trade_date", "")` 之后）调用 `get_available_trade_date(trade_date)`，得到 `effective_date`：

```python
# trading_graph.py propagate() 中，line 242 之后
from AI.dataflows.utils.trading_calendar import get_available_trade_date

raw_date = init_state.get("trade_date", "")
effective_date = get_available_trade_date(raw_date) if raw_date else ""
if effective_date != raw_date:
    logger.warning(f"日期校正: {raw_date} → {effective_date}")

# 将原始日期和有效日期都写入 state
init_state["trade_date"] = effective_date        # 兼容现有代码
init_state["requested_trade_date"] = raw_date     # 新增字段，用于透明度标注
```

**Step 2 — State schema 更新**

在 `AI/stockAgents/utils/agent_states.py` 的 `AgentState` 中新增字段：

```python
requested_trade_date: Annotated[str, "原始请求日期（校正前）"]
```

`trade_date` 字段保持兼容（值变为校正后的日期）。

**Step 3 — LLM Prompt 同步更新**

所有使用 `state["trade_date"]` 的 analyst 节点，prompt 中同时传入原始日期和有效日期。以 `cn_tech_analyst.py` 为例：

```python
# cn_tech_analyst.py node() 中
current_date = state["trade_date"]                 # 校正后的有效数据日期
requested_date = state.get("requested_trade_date", current_date)  # 原始请求日期

# prompt 中增加日期说明
if current_date != requested_date:
    date_note = (
        f"⚠️ 分析请求日期为 {requested_date}，"
        f"但该日为非交易日或数据尚未更新，实际可用数据日期为 {current_date}。"
        f"请在报告中标注'数据日期: {current_date}'。"
    )
else:
    date_note = ""
# 将 date_note 注入 system prompt
```

此更新需覆盖所有使用 `trade_date` 的 analyst：
- `cn_tech_analyst.py`（A 股技术）
- `us_tech_analyst.py`（美股技术）
- `kr_tech_analyst.py`（韩股技术）
- `cn_news_analyst.py`（A 股新闻）
- `us_news_analyst.py`（美股新闻）
- `kr_news_analyst.py`（韩股新闻）
- `international_news_analyst.py`（国际新闻）
- `international_event_extraction.py`（国际事件）

**Step 4 — interface.py 防御层（纵深防御）**

> ⚠️ **关键约束：日期校正必须在缓存查询之前执行。** 如果缓存查询在前、校正在后，则一个非交易日的错误结果会被缓存并持续返回，即使后续日期校正逻辑生效也无法绕过缓存。当前 `interface.py` 的缓存模式为 `cache.load_* → provider call → cache.save_*`（见 `interface.py:78-91`），必须将日期校正插入到 `cache.load_*` 之前。

即使 State 层已校正，在 `interface.py` 的 A 类关键接口中仍加入防御性校验，防止绕过 State 的直接调用：

```python
# interface.py get_market_breadth 中
def get_market_breadth(curr_date: str) -> str:
    from AI.dataflows.utils.trading_calendar import get_available_trade_date
    corrected = get_available_trade_date(curr_date)
    if corrected != curr_date:
        logger.warning(f"get_market_breadth: curr_date 自动校正 {curr_date} → {corrected}")
    prov = _get_provider()
    if hasattr(prov, 'get_market_breadth'):
        return prov.get_market_breadth(corrected)  # 使用校正后的日期
    return "当前数据源不支持市场宽度数据，请切换到 akshare。"
```

同样处理 `get_china_market_overview`（interface.py:149）和 `get_market_fund_flow`（interface.py:645）。

**Step 5 — 强制 LLM 显式传日期参数**

确保关键工具的 `curr_date` 参数**无默认值（必填）**，迫使 LLM 在 tool call 中显式传值。检查 `agent_utils.py` 中 `@tool` 包装函数的签名：

```python
# agent_utils.py Toolkit 中 — 确保无默认值
```

### 4.3 B 类标注策略：静默 T-1 的接口如何提示用户

B 类接口（akshare 的 `get_market_breadth`、`get_market_fund_flow`、板块层接口等）使用"取最新一行"语义，**不应改变其查询逻辑**，但需要在返回结果中显式标注数据的实际日期。

#### 4.3.1 标注格式

统一在返回文本顶部追加日期提示行，格式为：

```
> ⚠️ 数据日期: YYYY-MM-DD（请求日期为 YYYY-MM-DD 时请留意）
```

当数据日期与请求日期一致时，可省略括号内的提示（仅显示 `> 数据日期: YYYY-MM-DD`）。

#### 4.3.2 具体改动点

以 `akshare_provider.py` 为例：

**`get_market_breadth`（line 696）**：

```python
# 当前
latest = df.iloc[-1]
lines = ["# 市场宽度（情绪温度计）\n"]
lines.append(f"- 上涨家数: {latest.get('上涨家数', 'N/A')}")

# 改进后
latest = df.iloc[-1]
data_date = latest.get('日期', '未知日期')
lines = [f"# 市场宽度（情绪温度计）\n"]
lines.append(f"> ⚠️ 数据日期: {data_date}\n")
lines.append(f"- 上涨家数: {latest.get('上涨家数', 'N/A')}")
```

**`get_market_fund_flow`（line 726）**：同理，从 `stock_hsgt_fund_flow_summary_em()` 的返回 DataFrame 中提取实际日期字段。

**`get_margin_trading_balance`（line 668）**：同理，从 SSE/SZSE 返回的最新一行中提取日期。

**板块层接口（`get_sector_technical_screening` 等）**：由于内部硬编码 `datetime.now()` 而非接收 `curr_date`，标注实际数据日期尤为重要——用户需要知道数据对应的是哪一天。

#### 4.3.3 为什么不在 interface 层统一标注

因为只有 provider 层知道返回数据的实际日期——akshare 的 DataFrame 返回中日期字段名各不相同（`日期`、`date`、`trade_date` 等），需要各接口根据自己的数据源字段来提取。interface 层只能做通用包装，无法精准提取。

#### 4.3.4 板块层长期方案

板块层接口（`get_sector_technical_screening`、`get_sector_horizon_screening`、`get_industry_sector_performance`）当前**不接受 `curr_date` 参数**，内部硬编码 `datetime.now()`。这意味着 State 层的日期校正对板块层无效。建议分两步走：

- **短期**（当前方案）：在 B 类标注中补充实际数据日期，让用户和 LLM 知道数据的确切日期
- **长期**（P2）：为板块层接口新增 `curr_date` 参数，使其与分析日期对齐。需修改的文件：
  - `interface.py` — 接口签名增加 `curr_date`
  - `akshare_provider.py` / `tushare_provider.py` — 用 `curr_date` 替换 `datetime.now()`
  - `agent_utils.py` — `@tool` 包装函数增加 `curr_date`
  - `sector_tech_analyst.py` — prompt 中传入 `current_date`

## 五、边界条件与特殊场景

### 5.1 历史日期分析

当 `curr_date` 是已过去的日期（如"分析 2026-07-15 的市场情况"），不应该做"今日盘中"的时间判断——2026-07-15 的数据早已入库。`get_available_trade_date()` 需要区分"是否是今天"：
- `target_date < today`：仅校验是否为交易日，不做时间判断
- `target_date == today`：交易日 + 收盘时间判断

### 5.2 期指交割日计算（不受影响）

`interface.py:596` 的 `get_futures_expiry_calendar` 使用纯数学计算（每月第三个周五），**不依赖交易日历**。此接口不应被日期校正影响，使用原始 `requested_trade_date` 进行计算。

### 5.3 Stockstats 的"非交易日"判断（建议优化匹配逻辑）

`stockstats.py:84-87` 在 DataFrame 中做精确日期匹配（`stock["date"] == curr_date`），非交易日返回 `"N/A: 非交易日 (周末或节假日)"`。

如果上游 `curr_date` 已被校正为有效交易日，这里的"非交易日"分支就不会触发，stockstats 可以正常工作。但有两个理由建议同时优化 stockstats 自身的匹配逻辑：

1. **纵深防御**：stockstats 是独立工具，可能被绕过 State 层直接调用（`get_stockstats_indicators_report` 在 `agent_utils.py:95` 是独立的 `@tool`）
2. **更合理的语义**：将精确匹配（`==`）改为"最近可用"匹配（`<= curr_date` 的最新一行），并在结果中标注实际数据日期。这样即使上游日期校正未生效，stockstats 自身也能容错

```python
# 当前（stockstats.py:84）
matching = stock[stock["date"].dt.strftime("%Y-%m-%d") == curr_date]

# 建议优化
candidates = stock[stock["date"] <= pd.Timestamp(curr_date)]
if not candidates.empty:
    matching = candidates.iloc[[-1]]  # 取 <= curr_date 的最新一行
    actual_date = matching["date"].dt.strftime("%Y-%m-%d").values[0]
    if actual_date != curr_date:
        logger.info(f"Stockstats 日期校正: {curr_date} → {actual_date}")
else:
    matching = pd.DataFrame()  # 空，触发下方的 N/A 返回
```

> 注意：由于 stockstats 通过解析 Tushare 文本输出构建 DataFrame，其日期字段格式依赖 Tushare 返回格式。此改动需要在 `_parse_tushare_output`（`stockstats.py:52-78`）中同步验证日期解析的健壮性。

### 5.4 `get_concept_board_heat_rank` 的 `datetime.now()` 问题

`tushare_provider.py:631` 使用 `datetime.now()` 而非 `curr_date` 做回溯锚点——这导致历史回放无法精确复现。如果未来需要支持回测，建议统一改为 `curr_date` 参数。当前影响较小（概念板块热度为辅助分析），不阻塞本方案。

### 5.5 akshare 的 "pull extra then tail" 模式（已知限制）

`akshare_provider.py:258-260` 在 `get_index_data` 中采用 `fetch(2*days) → tail(days)` 策略来应对非交易日。这是一种启发式方法，在长假期（如国庆 7 天）可能导致 tail 结果中混合了过多旧数据。本方案不做修改，但建议在该方法的返回中标注数据日期范围。

### 5.6 LLM 注入日期的不确定性（重要）

`cn_tech_analyst.py:109` 只将 `current_date` 注入 system prompt，**不通过代码注入工具参数**。LLM 需要在 tool call 中自行补上 `curr_date` 参数。影响分析：

- **好消息**：如果 State 层的 `trade_date` 已被校正，LLM 在 prompt 中看到的就是校正后的日期，自然会传递给工具
- **风险**：LLM 可能不传 `curr_date`，或传错，导致工具使用默认值（如果工具签名有默认值）或报错
- **对策**：4.2 Step 5 中将关键工具参数设为必填，同时保留 interface 层的防御性校验作为双保险

| `tests/agents/**`（`trade_date = "2026-08-08"`，周六） | **行为有意变化**：从空数据变为周五数据 | 更新测试断言，验证新行为 |

### 8.2 State schema 兼容性

新增字段 `requested_trade_date` 和 `date_correction` 使用 `Annotated` 模式加入 `AgentState`（`agent_states.py:40`）。旧 `init_state` 字典不含这些字段时，`state.get("requested_trade_date", state["trade_date"])` 返回当前日期作为兜底。

### 8.3 缓存影响（重要）

日期校正后，缓存 key 会变化（例如 `trade_date=2026-08-08` 校正为 `2026-08-07`，key 从包含 `08-08` 变为包含 `08-07`）。影响：

- **旧 key 变为孤儿条目**：旧的 `08-08` 缓存条目不会被主动清理，由 TTL 自动过期（`StockDataCache` 的 TTL 为 3600-43200 秒，见 `file_cache.py:93-151`）
- **校正后的 key 可能命中已有缓存**：`08-07` 可能在之前（周五盘后）已被缓存，命中后无需重新请求数据源——这是正确的行为
- **约束**：如 4.2 Step 4 所述，日期校正**必须在缓存查询之前**执行，否则非交易日的错误结果会被缓存并持续返回

### 8.4 环境变量新增

| 变量 | 默认值 | 说明 |

| `TUSHARE_DATA_READY_HOUR` | `20` | Tushare 数据就绪截止时间（Asia/Shanghai 时区） |
