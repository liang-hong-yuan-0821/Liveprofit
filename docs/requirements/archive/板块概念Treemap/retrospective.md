# 复盘

## 做对了什么（可复用）

- **端点能力实测先行于方案定稿**：数据源选型（dc_daily 窗口型 vs ths_daily 全历史 vs 东财直连不可达）全部用真实 token 探测后拍板——避免了一次"方案写完全历史回填、实施时发现端点只回 33 行"的返工；用户"先存 dc"的拍板也建立在实测事实之上。
- **方案评审发现了 echarts 6.1 的机制性坑**（treemap 颜色回调返回值被丢弃），并在实施前用 node SSR 复现验证修复方向（静态逐节点着色）——R1 blocker 提前消化，实施零返工。
- **评审后的 CR 两轮 delta 均换"核验"口径**：第二轮用独立重跑 + SSR 实测坐实新问题（treePathInfo 虚拟根残影），没有重复第一轮的检查。
- **数据量实测驱动契约截断**（top 30 板块 29,062 成分 → top 100 截断 + SQL ROW_NUMBER），避免按直觉低估 11 倍。

## 踩了什么坑（教训）

- **dc_daily 是窗口型端点**（最近 ~33–55 交易日、更早区间 0 行）：历史回填类需求必须实测窗口行为，不能按普通区间端点假设。已沉淀 pitfalls/ai/tushare-endpoints.md。
- **echarts treemap 两个隐蔽行为**：`itemStyle.color` 回调返回值被丢弃（必须静态写 per-node）；`visibleMin` 的阈值过滤仅在 `sort` 为真时生效。均已写入代码注释。
- **测试可证伪性**：Radix Dialog 在 `open=false` 时本就卸载，导致"关闭即卸载"的断言不可证伪——需用 mock 组件的独立用例锁住真实修复点（父组件 selectedNode 清空）。
- **预置测试隔离问题**：contract 套件与 db 套件混跑时后者 caplog 失效（本任务实施中发现，非本任务引入）——跨任务修复候选，见 issues.md。
