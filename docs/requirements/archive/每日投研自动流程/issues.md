# 问题与解决

## 实施前待验证

- 量化21:00起跑与行情水位：15:30可预检/补齐但不提前运行策略；需实测各数据组在21:00的完整率和全策略耗时。22:00只作为数据等待截止，已开始的计算按任务预算完成或失败；休市无新交易日不伪造新量化结果。
- 09:00/21:00 出版时效：逐来源核验抓取间隔、翻页覆盖和模型两轮最慢耗时；最后一秒发布/抓取的新闻不可能保证整点前完成AI。验收须区分整点完整率、partial backlog和后续修订时延，不能用“计划任务准时触发”冒充所有新闻已分析。
- “一周/一个月”当前按未来5/20个交易日设计；需在界面展示起止日期并验证交易日历。日历无法确认时不得假定周末/节假日开市。
- “利好/利空落地”需分别验证来源公告的实施时点和行情反应；当前只有事件后5日、四个指数的历史 CAR，20日及个股/行业兑现须补齐行情、基准、覆盖，缺失时显示未验证。
- 同库部署与共享事务：平台和事件默认可使用同一 PG_* 配置，但各有覆盖 DSN；实际拓扑未经连接验证。首期自动流程需同库且同连接提交，不能仅验证连接字符串相似。
- 新闻源翻页、稳定ID和宕机补齐能力：现有抓取封装不能证明历史覆盖完整，需来源逐项 POC。
- 收盘数据：现有表级 max 日期不足以证明股票覆盖；公共自动补齐框架尚未落地且原范围不含量化 qfq。
- 历史统计：完整5日窗口和实际可用时点要补齐，未满足前不能用于严格历史验证。
- 性能：全市场×策略×组合的 position-sensitive 扫描需测时长；未承诺固定完成时间。
- 模型效果：阈值和事件衰减参数是设计初值，需样本校验与后续影子观察。

## 实施验收与上线边界（2026-09-23）

- **数据库上线验收仍有范围**：本机 PostgreSQL 临时库通过了 news/assessment schema、版本快照、争议/撤回投影、历史向量可用时间和旧事件覆盖计数用例；每日研究与事件审核 API contract 也通过。尚未单独验收从目标部署环境旧 schema 的在线升级、并发初始化、跨数据库拓扑核对及 Dispatcher 租约恢复。
- **一期交付明确为候选排序**：已实现所有已发布策略扫描、90天结构化事件权重、候选股排序、前10候选深研；不生成组合仓位或建议订单，接口标记 `position_planning=out_of_scope`。这符合本次用户确认的范围，组合绑定/仓位规划是后续独立能力，不是当前缺陷。
- **兑现数据有范围限制**：指数与明确股票目标可以按 1/5/20 个完整交易日读取实际收益和基准超额；行业/概念当前成分缺乏可靠历史时点快照，相关事件保持 data_insufficient。兑现快照在新日报重算，不修改旧报告。
- **自动流程依赖平台进程**：需持续运行 backend API、Dispatcher/worker，并保持 `LIVEPROFIT_DAILY_RESEARCH_ENABLED=true`；仅启动事件研究 FastAPI（8100）不会运行新调度。旧 Windows `LiveProfit事件研究每日批处理` 若仍注册，应人工检查并禁用以免重复拉取；代码不会操作操作系统任务计划程序。
- **并行回归失败与隔离**：之前全量前端 370 个测试中 369 通过，1 个现有 `QuantExecutionPanel` 测试因图表查询新传 `cache_only` 参数而失败；该断言与每日研究功能无关，未改动并行中的图表代码。当前定向页面测试 61 项全部通过。早前选跑旧 `tests/event_study/test_app_scheduler.py` 时，13 个用例在 pytest `tmp_path` 创建阶段遇到 Windows `PermissionError`，不是产品断言失败。
- **无真实外部调用**：未连接真实新闻源、行情 provider 或 LLM；按工作区规则未运行 `real_llm`/`real_toolkit` 测试。模型质量、新闻覆盖和实际耗时需要部署后的影子观察。
