# 复盘

方案阶段先核对真实执行顺序，避免把“同一报告含AI和量化”误认为AI已经参与量化决策。

用户询问“旧表能否复用”是在要求解释设计依据，不能直接推断其偏好零新表。应区分可实现性与推荐方案，按业务边界和长期成本独立判断；也不能为了维持两张表，把不同生命周期的控制记录、过程日志和业务事实混装。

实施中最重要的纠偏发生在迟到新闻路径：21:00量化若因新闻积压输出 partial，后续完整批次必须基于父量化批次和新闻批次身份幂等刷新，复用原扫描分数，只重算事件贡献、排序和候选深研。行情水位探测失败时保留原候选与交易日并标记 partial，避免降级路径把有效扫描结果清空。

报告持久化的字段契约必须从写入端和 API/UI 读取端一起核对；将量化区块写入未被日报读取的键，会造成“任务成功但页面无报告”。以端到端合同测试确认报告键、批次来源和刷新父子关系可以捕获此类接线问题。

最终验收覆盖 mock Agent、临时 PostgreSQL 旧结构升级、定向 API/前端回归、候选刷新失败路径与代码审查。部署后还需验证目标数据库在线升级、并发 Dispatcher/租约恢复、新闻源覆盖、真实模型耗时和数据覆盖；提交前需等并行工作区收敛，避免混合共享文件的差异。
