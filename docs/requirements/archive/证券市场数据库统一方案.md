## 一、背景与动机

| 维度 | 现状 | 问题 | 目标 |
|------|------|------|------|
| 数据库分裂 | 同一个 liveprofit 库 public schema 里并存三套市场数据表：① `AI/dataflows/store/schema.sql` 六表（stock_basic/fund_basic/stock_daily/adj_factor/concept/concept_member，全市场个股+基金日线 ~1400 万行）；② `AI/eventStudy/db/schema.sql` 的 assets/market_data/industry_codes（4 指数日线，daily_job 每天拉 2 年窗口，`market_data_collector.py:81-82`）；③ backend ORM 四表 market_assets/market_bars_daily/market_index_factors/concept_hotness_snapshots（[models.py:32-136](Liveprofit/backend/modules/market_data/infrastructure/models.py#L32-L136)，平台读模型） | 同一数据多处重复存：指数日线两份（eventStudy.market_data 4 指数 ~2 年 vs market_bars_daily 7 CN 指数 ~90 天，同源 tushare index_daily）；资产目录三份（eventStudy.assets / market_assets / stock_basic+fund_basic）；日线 schema 三套类型不一（DOUBLE vs NUMERIC、DATE vs TIMESTAMPTZ、volume vs vol、close vs adj_close） | 一个独立的证券市场数据库（同库 `market` schema，表名按 CLAUDE.md 命名规范）：唯一证券主表（instrument）、唯一日线表（instrument_daily）、唯一因子表（factor_daily）、唯一概念/行业体系，所有消费方（平台 API、事件研究、AI 分析）从这一个库读 |
| 采集链分裂 | 三条采集链重复拉同一上游：daily_job 步骤 2 `market_data_collector.collect_index_market_data`（index_daily→eventStudy.market_data）、daily_job 步骤 3 `store.incremental`（daily/adj_factor→store）、backend `market_ingest` worker（index_daily+idx_factor_pro→market_bars_daily/market_index_factors） | 指数日线每天被拉两次入两张表（daily_job 步骤 2 与 market_ingest 各一遍）；个股基金增量与指数采集分属两个入口，新增资产类（如未来 US/KR 指数、个股因子入库）没有统一落点 | 一条统一采集链（中立包 ingest：指数+个股+基金+因子+概念），一个每日增量入口，回填/增量共用同一写入路径 |
| 代码分裂 | store 在 `AI/dataflows/store`（psycopg 直写 + schema.sql）、平台读模型在 `backend/modules/market_data`（SQLAlchemy ORM + alembic）、事件研究行情在 `AI/eventStudy/db`（psycopg + schema.sql）——三套 DAO 重复实现 upsert/查询 | 新增一个数据能力（如个股因子入库）要三处评估落地；平台消费 store 数据要跨包引 AI 代码；连接管理三套（`store/db.py:21-32` 与 `eventStudy/db/connection.py:23-35` 各自 psycopg、backend `bootstrap/database.py` SQLAlchemy） | 新建中立包 `db/instrument/`（项目根）：schema.sql + DAO + ingest 唯一实现，backend 与 AI 都 import 它，无方向性依赖 |
| 历史数据 | 指数日线最深处只有 ~2 年（eventStudy.market_data，且仅 4 个指数）；market_bars_daily 只有 ~90 天；个股日线全历史已回填（store） | K 线图"看所有 K 线"目标（见指数K线图交互优化方案）被数据边界卡住——指数全历史不在任何表中 | 指数日线+因子全历史回填进统一库（index_daily/idx_factor_pro 1990 年起），K 线缩放边界=全历史 |

## 二、架构设计

### 2.1 总体结构

```
liveprofit 库（PostgreSQL 16，同一个实例/数据库，不新开 database——已确认决策）
├── public schema（应用域，保持现状）
│   ├── 事件研究域：events / event_impacts / market_context / predictions / assets(保留，事件域外键)
│   ├── 平台域：analysis_* / watchlist* / portfolio* / macro_information（concept_hotness_snapshots 删除——热点改现场计算，决策 13）
│   └── （原 store 六表、market_bars_daily、market_index_factors、market_assets、industry_codes、market_data 迁移后 DROP）
└── market schema（证券市场数据库，本方案新建；表名按 CLAUDE.md 命名规范）
    ├── instrument        标的主表（指数/股票/基金统一目录；无平台门控列——平台资产目录前端写死，见 2.2）
    ├── instrument_daily  统一日线（指数+个股+基金，DOUBLE PRECISION）
    ├── adj_factor      复权因子
    ├── factor_daily    技术因子宽表（指数∪个股列并集）
    ├── fund_info       基金信息表（fund_basic 差异列）
    ├── stock_info      股票信息表（exchange/market/area 等股票差异列）
    ├── sector          板块字典（同花顺板块体系：概念/行业/特色板块，type 区分；ths/dc 多来源）
    ├── sector_member   板块成分映射
    ├── sector_daily    板块日线（ths/dc 板块指数日行情；热度现场计算的数据底座）
    ├── industry        行业字典（SW2021 等多来源，主键 (source, industry_code) 与 sector 同构）
    └── industry_member 行业成分关系（(source, industry_code, ts_code)；首期空表，采集后续阶段）
```

### 2.2 数据模型设计

**market.instrument**（标的主表，合并 market_assets + eventStudy.assets + stock_basic + fund_basic）：

| 字段 | 类型 | 写入者 | 说明 |
|------|------|--------|------|
| ts_code | VARCHAR(16) PK | 采集/迁移 | 统一证券代码（tushare 风格后缀）：如 `000001.SZ`（平安银行）、`000001.SH`（上证指数）、`158013.SZ`（航天航空ETF）；US/KR 资产用原 symbol（如 `.INX`） |
| name | VARCHAR(128) NOT NULL | 采集 | 名称：如 `上证指数`、`平安银行` |
| instrument_type | VARCHAR(16) NOT NULL | 采集/迁移 | `index` / `stock` / `fund`（**2026-09-13 五轮调整：asset_class 更名 instrument_type**；store 现状靠 `is_fund_ts_code()` 前缀函数分类，store 方案决策 1；统一后显式列，前缀函数退役） |
| list_status | CHAR(1) | 采集 | `L`=上市 / `D`=退市 / `P`=暂停（stock_basic 口径） |
| list_date / delist_date | DATE | 采集 | 上市/退市日期：如 000001.SZ → 1991-04-03 |
| data_source | VARCHAR(32) | 采集 | `tushare` / `akshare`（数据采集来源，从 market_assets 迁入；store 标的不在平台目录，迁移默认 `tushare`） |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT now() | 写入 | 行最后写入时间 |

索引：**PK = ts_code 单主键（全局唯一，无 market 维度）**——**market 列删除定稿（2026-09-13 五轮调整，用户拍板）**：US/KR 资产用原 symbol（`.INX`/KOSPI/KOSDAQ）与 CN 的 6 位数字+.SH/.SZ/.BJ 格式天然不冲突，无需 market 列区分，原 `UNIQUE(market, ts_code)` 防御随之删除；`(instrument_type, list_status)` 供筛选。

**market.fund_info**（基金信息表——fund_basic 差异列，不塞主表；用户 2026-09-13 决策）：

| 字段 | 类型 | 说明 |
|------|------|------|
| ts_code | VARCHAR(16) PK | 基金代码，如 `158013.SZ`（易方达国证航天航空行业ETF） |
| management / custodian / trustee | VARCHAR(64) | 基金管理人/托管人/受托人 |
| fund_type / invest_type / type | VARCHAR(32) | 基金类型（fund_basic 口径三列语义重叠，原样保留） |
| found_date / due_date / issue_date | DATE | 成立/到期/发行日期 |
| issue_amount / m_fee / c_fee / duration_year / p_value / min_amount / exp_return | DOUBLE PRECISION | 发行份额(亿份)/管理费率(%/年)/托管费率/存续期/面值/起购金额/预期收益 |
| benchmark | VARCHAR(128) | 业绩基准描述 |
| status | CHAR(1) | 基金状态：`L`=上市/`I`=发行期/`D`=终止上市（fund_basic.status 原值） |
| market | CHAR(1) | 交易场所（fund_basic.market 原值，**列名沿用 tushare 原名 market**——与 stock_info.market（上市板块口径）跨表同名不同口径，与 tushare 现状一致（stock_basic.market 与 fund_basic.market 同名列不同含义，分属两接口）：`E`=场内/`O`=场外，本表恒 'E'（按 market='E' 过滤拉取） |
| purc_startdate / redm_startdate | DATE | 申购/赎回起始日 |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT now() | 行最后写入时间 |

**market.stock_info**（股票信息表——stock_basic 差异列；**不含 industry 列**：股票行业归属走 industry/industry_member 申万体系（用户 2026-09-13 决策），stock_basic 口径的中文行业名属冗余不迁——申万成分采集落地前行业归属暂缺，AI 分析流现状走 Provider 直连不受影响）：

| 字段 | 类型 | 说明 |
|------|------|------|
| ts_code | VARCHAR(16) PK | 股票代码，如 `000001.SZ` |
| exchange | VARCHAR(8) | 交易所（stock_basic 原值，**用户 2026-09-13 决策：从主表移入本表**——仅股票有交易所口径，基金/指数无此属性）：`SSE`=上海/`SZSE`=深圳/`BSE`=北京 |
| market | VARCHAR(16) | 上市板块（stock_basic.market 原值，**列名沿用 tushare 原名 market**——与 fund_info.market（E/O 场内/场外口径）跨表同名不同口径，与 tushare 现状一致，分表存放无冲突）：主板/创业板/科创板/北交所——如 300xxx.SZ→创业板、688xxx.SH→科创板 |
| area | VARCHAR(16) | 地域（stock_basic 原生字段）：如 `深圳` |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT now() | 行最后写入时间 |

**平台资产目录前端写死（用户 2026-09-12 拍板：取消 platform_assets 表）**：market_assets 的四个平台门控/展示字段——`enabled`（启用开关）、`availability_status`（AVAILABLE/DISABLED/UNAVAILABLE 门控）、`supported_intervals`（周期白名单，首期恒 `["1d"]`）、`display_order`（排序）——是 12 行产品配置而非行情数据，**迁移时直接丢弃、不建 platform_assets 表**；instrument 不携带任何平台门控列（8000+ 个股/基金与平台目录天然无耦合）。平台展示逻辑前端写死（`MarketIndicesPanel.tsx` 新增 `MARKET_INDEX_CATALOG` 常量：12 个指数 `{market, symbol, name, currency, market_timezone, availability}`，组序沿用现状 `MARKET_GROUP_ORDER` US→KR→CN、组内顺序 = 原 display_order 顺序固化；US/KR 5 个指数 availability 恒 `'UNAVAILABLE'` 保持现状"暂不可用"展示；**目录字段名 availability 刻意区别于已删门控列 availability_status（R1 polish 14）**，测试项表述统一用 availability）。连带契约变更见 3.3.1。

**market.instrument_daily**（统一日线，合并 store.stock_daily + market_bars_daily + eventStudy.market_data）：

| 字段 | 类型 | 写入者 | 说明 |
|------|------|--------|------|
| ts_code | VARCHAR(16) NOT NULL | 采集/迁移 | 证券代码，如 `000001.SZ` / `000001.SH` |
| trade_date | DATE NOT NULL | 采集/迁移 | 交易日；停牌日无行（整行缺失，不存 NULL 行） |
| open / high / low | DOUBLE PRECISION | 采集/迁移 | 开/高/低（未复权原值） |
| close | DOUBLE PRECISION NOT NULL | 采集/迁移 | 收盘价；NOT NULL——清洗时 close 为 NaN 的行显式 drop（store 3.3.1 规则沿用） |
| pre_close | DOUBLE PRECISION | 采集/迁移 | 前收盘价；指数行 tushare index_daily 有值则存、AKShare 兜底行 NULL；个股/基金行 store.stock_daily 原值随步骤 1 列直映射迁入 |
| change / pct_chg | DOUBLE PRECISION | 采集/迁移 | 涨跌额/涨跌幅；指数行按上游原值存（不自算）；个股/基金行 store.stock_daily 原值迁入 |

| source | VARCHAR(32) NOT NULL | 采集/迁移 | `tushare` / `akshare`（market_bars_daily.source 迁入；store 行迁移时填 `tushare`） |
| updated_at | TIMESTAMPTZ | 采集/迁移 | 行最后写入时间（统一列名，决策 14；覆盖式写入下 = 最近一次入库——原 market_bars_daily.source_updated_at 语义迁入；store 行迁移时填迁移时刻） |

PK `(ts_code, trade_date)`（含日期列，未来可切 TimescaleDB/分区——沿用 store 决策 3 与 eventStudy schema 注释约定）；索引 `(trade_date, ts_code)`（横截面查询 get_cross_section）。
类型决策：统一 DOUBLE PRECISION（store 决策 2 论证：1400 万行规模 NUMERIC 变长更大聚合更慢；指数行 →DOUBLE 无损——上游 tushare 本身 float；market_bars_daily 迁移精度论证定稿（R1 minor 10）：open/high/low/close NUMERIC(18,4) 无损；**volume 为 NUMERIC(24,4)（models.py:67，与其余列不同精度）**，24 位 > DOUBLE 有效位数，但按实测值域（最大 876,379,505，9 位有效数字）无损——论证以值域为准而非精度位宽）。指数行迁移映射：eventStudy.market_data 的 `adj_close`→`close`（指数无复权）、`ts TIMESTAMPTZ`→`trade_date DATE`、`vol`→`vol`（**该表行情列是裸 `NUMERIC`**，[schema.sql:79-85](Liveprofit/AI/eventStudy/db/schema.sql#L79-L85)，NUMERIC(18,4) 是 market_bars_daily 的精度，[models.py:63-67](Liveprofit/backend/modules/market_data/infrastructure/models.py#L63-L67)——两者迁移均无损入 DOUBLE）；market_bars_daily 的 `volume`→`vol`、`trading_date`→`trade_date`、`asset_id`→`ts_code`（经 market_assets.symbol 映射）。

### 3.1 中立包与 schema

#### 3.1.1 模块设计

- `db/instrument/db.py`：连接唯一入口 `dsn()` + `get_connection()`。**不用 psycopg 无参连接**（实测 libpq 环境变量名是 `PGHOST` 等无下划线变体，而项目 `.env:67-72` 是下划线风格 `PG_HOST/PG_PORT/PG_USER/PG_PASSWORD/PG_DATABASE/PG_SSLMODE`，无参连接读不到、且会绕过默认值与归一化）。`dsn()` 定稿：`PG_CONNECTION_STRING` 优先（测试注入点，先例 `backend/tests/contract/api/test_event_study_review.py:128` 的 monkeypatch 模式）→ 否则按 `PG_HOST/PG_PORT/PG_USER/PG_PASSWORD/PG_DATABASE/PG_SSLMODE` 拼装（默认值 localhost/5432/liveprofit/liveprofit123，与 `AI/eventStudy/collectors/config.py:25-42` 一致）→ host 归一化沿用 backend `bootstrap/settings.py:99-102` 的归一化集合 `("localhost", "::1")` → `127.0.0.1`（PG 仅监听 IPv4 loopback，`::1` 黑洞踩坑）。**注入载体定稿（防 setenv 静默失效）**：`db/instrument/db.py` 模块级 `PG_CONNECTION_STRING = os.getenv("PG_CONNECTION_STRING")` + `dsn()` **调用时读该模块全局**（与 config.py 同模式）；测试注入 = 在 module 级 fixture（契约 conftest.py:48 / 集成 conftest.py:30 均为 module scope，**module 级 fixture 内无法通过 function 级 monkeypatch 生效**，须直接赋值该模块常量）内直接赋值该模块常量、teardown 还原，**勿用 setenv**——config.py 是 import 时快照，setenv 对 db.instrument 若同为快照则注入静默失效、get_bars 回落 PG_* 读真实库。**与 eventStudy config.pg_dsn 的关系**：两处读同一套环境变量、默认值一致，不合并（避免动事件研究全链测试的 monkeypatch 注入点）；差异点 = db.instrument 多 host 归一化（config.py 无），写死在本注释供对照。连接后 `SET TIME ZONE 'Asia/Shanghai'`（与 store/eventStudy 同规则）；**连接参数定稿（既有定稿）**：`psycopg.connect(dsn(), connect_timeout=5)`，与 store/eventStudy 两处先例一致（connection.py:30、store/db.py:27）；`init_schema(conn=None)` 执行 schema.sql（幂等；无参经 get_connection 自建连接、自管关闭——先例 connection.py:38 同签名）。**db.py 的 CLI 入口形态定稿（R2 收尾 1）**：`python -m db.instrument.db --init-schema` 由模块 `__main__` 承接（`if __name__ == "__main__":` 解析 `--init-schema` → 调 `init_schema()`，失败退出码非 0）——run.sh 生产入口依赖此形态，未定义则该行静默 no-op。backend 消费路径与 CLI 路径都经 `db.instrument.get_connection()`（backend 不再用 SQLAlchemy 引擎连市场表）。

### 3.7 后续阶段数据补齐（决策 16：用户 2026-09-13 拍板"所有表都补"）

#### 3.7.1 模块设计

**① 个股因子全历史（stk_factor_pro → market.factor_daily 个股段）**

- 范围：全市场个股（stock_basic 全量 ~5549 只，含退市）各自上市以来全历史。
- 规模：5549 行/日 × 全历史 ≈ 千万级行（与 store 日线回填 1400 万行同量级，store 回填耗时为参照）。
- 上游与路径：stk_factor_pro **按 ts_code + 区间逐只拉取**（路径 b——请求数少、区间查询稳定；先例 = AI 个股报告运行时 `get_stock_factor_df` 的 ts_code 区间查询）；**按 5 年分段**（个股全历史 ~7000 行接近 idx_factor_pro 官方 8000 行上限，分段保险——出处同 3.5.2）；逐段升序归一（端点降序坑）；每批 `_UPSERT_BATCH` 分批写入。
- 写入规则：**ON CONFLICT DO NOTHING**（决策 5 主规则——个股因子无存量可迁、全新数据无覆盖需求；与指数因子行的 DO UPDATE 例外分开）。
- 列集：STOCK_FACTOR_FIELDS 14 因子（ma_bfq_5/10/20/60/250、boll_*、macd_*、rsi_*）→ factor_daily 个股段；**close 列从 instrument_daily 反查填充**（stk_factor_pro 无 close 列，与迁移步骤 4 同模式，做个股因子与日线对齐自检）。
- 断点续跑：按 ts_code 批次 + checkpoint 进度文件（失败清单模式）；~5549 只 × 3 段 ≈ 1.6 万请求，支持多天分批执行（不必一次跑完）。
- 消费方切换（随采集落地）：AI 个股报告改读 market.factor_daily 个股段，stk_factor_pro 运行时直连退役。

**② 板块日线回填（dc_daily / ths_daily → market.sector_daily）**

- 范围：sector 表内板块（dc 概念板块数百个 + ths 概念板块 ~899 个）各自上市以来。
- 规模：数百~千个板块 × 全历史（概念板块指数最早约 2010 年 ≈ 3600 交易日）≈ 百万行级。
- 上游与路径：dc_daily / ths_daily **按 ts_code + 区间逐板块拉取**；**ths_daily 未实测——回填前先做端点能力探测（列名/行上限/截断），探测结论写入采集实现注释**（2.2 端点能力注记的落点）；dc_daily 行序同 sw_daily 降序，先 `_sort_asc_by_trade_date` 归一。
- **分两步（热度启用前置分级）**：① 最小窗口回填——近 20 交易日（热度现场计算启用所需，先跑通）；② 全历史回填——板块层热力图/轮动分析（按需可选）。
- 写入规则：ON CONFLICT DO NOTHING + 断点续跑（按板块批次 checkpoint）。
- 消费方切换（随采集落地）：板块层热力图 `get_concept_daily_returns_matrix` 改读本表（3.3.1 已列）。

**③ 申万行业成分采集（index_member → market.industry_member + industry.count 写回）**

- 范围：31 个申万一级行业（industry 表全量）当前成分。
- 规模：31 行业 × 平均百只级 ≈ 5500 行（与全市场个股数同量级——申万互斥完备）；仅 31 次请求。
- 上游与路径：index_member 按 index_code 逐行业拉取（index_code = industry_code 补 `.SI` 后缀，如 801010.SI）；成分代码 con_code（6 位）补交易所后缀 → ts_code（与 instrument 对齐，同 `_normalize_store_member_code` 模式）。**index_member 端点未实测——采集落地时探测（参数/截断），结论写入实现注释**。
- 写入规则：**全量替换式刷新**（当前成分快照语义，表无历史维度）——upsert 新名单 + DELETE 不在新名单的旧成分（差集删除），同批事务内写回 **industry.count = 该行业成分行数**（2.2 的 count 写回承诺落点）。
- 刷新节奏：申万分类版本级稳定——采集落地时一次性执行 + 版本调整时刷新，不并入每日增量。
- 消费方切换（随采集落地）：股票行业归属补齐（2.2"申万成分采集落地前暂缺"的解除点）；review_dao SW 校验、sector_event_prefetch 行业名解析的 industry 表消费自迁移即生效，成分补齐后个股层行业归属查询可用。

**落地顺序与优先级**：① sector_daily 最小窗口（热度功能启用）→ ② industry_member（个股行业归属补齐，请求量最小）→ ③ 个股因子全历史（AI 个股报告读库，请求量最大）。
