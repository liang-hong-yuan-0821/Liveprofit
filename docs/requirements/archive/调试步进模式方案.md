## 一、背景与动机

### 1.1、现状

- 主体分析流程 = `TradingAgentsGraph.propagate()`（`AI/graph/trading_graph.py`）跑 LangGraph 三层流水线（市场 → 板块 → 个股），由 `python main.py` CLI 进程执行，一次性跑完，无法中途停下来检查中间结果。
- 日志基础设施（2026-08-20 上线）：`@dataprovider_log` 装饰器（`AI/utils/dataprovider_log.py`，43 处接口全在 `AI/dataflows/interface.py`）在每次 dataprovider 调用后写入 `logs/{ts}/{layer}/{seq:03d}_{Node}/{seq:03d}_{接口名}/req.json + res.md|json + meta.json`；`LLMCallbackHandler.on_llm_end`（`AI/utils/llm_callbacks.py`）在每个 LLM 节点输出后写入 `res.md`。
- 查看页面 = Streamlit 日志查看器（`AI/logviewer/app.py` + `logs_reader.py`），与 CLI 进程**相互独立**，仅被动读 `logs/{ts}/` 目录。
- 现有 `debug=True` 只控制流式 trace 输出，无任何"暂停等待人工确认"能力。

### 1.2、目标

新增**调试步进模式**（debug step mode）：开启后，主体流程在每个关键节点暂停，页面展示该节点产物，用户点【确认下一步】后才继续；调试到中途确认没问题后可点【跳过全部】一键放行剩余全部检查点。

- 检查点（三类，用户确认）：
  1. **DP 响应**：每次 dataprovider 调用结果写入日志后暂停；
  2. **LLM 调用前**：每次 LLM 调用发起前（`on_llm_start`，req.md 提示词已写入、API 请求尚未发出）暂停——用户确认后才真正发出请求；
  3. **节点 res**：每次 LLM 调用输出（res.md）写入日志后暂停。
- 开关：环境变量 `LIVEPROFIT_DEBUG_STEP=true`（启动分析进程前设置）；关闭时**一切行为与现状完全一致**（零侵入）。
- 等待策略：**无限等待**（用户确认），不设超时。
- 页面：在现有日志查看器新增"调试步进"区域，显示当前检查点信息 + 内容 + 【确认下一步】/【跳过全部】两个按钮。

## 二、架构设计

```
CLI 分析进程（python main.py）                        Streamlit 日志查看器（独立进程）
┌────────────────────────────┐                      ┌────────────────────────────┐
│ propagate()                │                      │ 调试步进 tab（1s 自动刷新） │
│   └ step_gate.enable(run)  │                      │   └ find_active_checkpoint │
│                            │                      │       ↓ 读 .debug_checkpoint.json
│ LLMCallbackHandler.on_llm_start ─┐                │   显示检查点 + 按钮        │
│   └ checkpoint("llm_req")  ├──┐  │                │   │                       │
│ LLMCallbackHandler.on_llm_end   │ │                │   │                       │
│   └ checkpoint("llm_res")  ├──┘ └──► 写 waiting ──┼──► 确认下一步 / 跳过全部 ──┼──► 改写 status
│                            │      ◄── 0.5s 轮询 ──┼──► （temp+rename 原子写）  │
│ dataprovider_log.wrapper   │                      └────────────────────────────┘
│   └ checkpoint("dp") ──────┘
└────────────────────────────┘
```

两个进程通过共享的 `logs/{ts}/.debug_checkpoint.json` 文件协调：

- 后端：检查点处写 `status="waiting"` 全量载荷 → 每 0.5s 读该文件，`status != "waiting"` 即继续（`confirmed` 放行本步 / `skip_all` 放行后续全部）。
- 页面：轮询发现 `waiting` → 展示 → 按钮点击后读文件改 `status` 字段写回（temp+rename 原子写，防后端读到半截文件）。

不改变现有三层图架构与日志目录约定，仅新增一个 run 根目录下的隐藏文件。LangGraph 的 `interrupt()` 机制只支持节点边界、且要求 checkpointer，无法覆盖节点内部逐次 DP 调用，故不采用。

### 2.1 数据模型设计

`logs/{ts}/.debug_checkpoint.json`（run 根下隐藏文件，`list_layers` 不受影响——它只认子目录；`list_runs` 只认时间戳目录）：

| 字段 | 类型 | 写入者 | 说明 |
|------|------|--------|------|
| `status` | str | 后端/页面 | `waiting`（后端写）→ `confirmed` / `skip_all`（页面写） |
| `seq` | int | 后端 | 本次 run 内检查点全局序号，从 1 递增 |
| `kind` | str | 后端 | `dp` = DP 响应 / `llm_req` = LLM 调用前 / `llm_res` = 节点 res |
| `ts` | str | 后端 | 检查点创建时间 `YYYY-MM-DD HH:MM:SS` |
| `layer` | str | 后端 | market/sector/stock/screening/unknown（`dir` 相对 run 目录路径首段推导，与 3.2.1 一致） |
| `node` | str | 后端 | 节点名（未消毒原始名） |
| `name` | str | 后端 | dp：接口名；llm_req/llm_res：节点名（与 node 相同） |
| `dir` | str | 后端 | 日志目录相对 run 的路径（`/` 归一化），页面据此读取内容 |
| `show_file` | str | 后端 | 页面渲染的目标文件：dp → `res.md`/`res.json`；llm_req → `req.md`；llm_res → `res.md` |

页面读到 `status != "waiting"` 时按历史状态展示（"已确认" / "已跳过全部"），`waiting` 时渲染按钮。

## 三、详细设计

### 3.1 步进门控核心（AI/utils/step_gate.py，新建）

#### 3.1.1 模块设计

模块级状态（LangGraph 节点与 LangChain 回调均为单线程顺序执行，无需锁）：

- `_enabled: bool = False`、`_run_dir: Path | None = None`、`_skip_all: bool = False`、`_seq: int = 0`
- `enable(run_dir: Path) -> None`：置 `_enabled=True`、`_run_dir=run_dir`、`_seq=0`、`_skip_all=False`。由 `propagate()` 在设置 log_dir 处调用。
- `checkpoint(kind: str, *, layer: str, node: str, name: str, dir: str, show_file: str) -> None`（kind ∈ {"dp", "llm_req", "llm_res"}）：
  - `_enabled` 为 False 或 `_skip_all` → 直接返回（零开销快路径）；
  - `_seq += 1`，写 `{run_dir}/.debug_checkpoint.json`（temp+rename），`status="waiting"`；控制台一行：`⏸ [步进] #seq 等待页面确认：{kind} {node}::{name} → {file}`；
  - 轮询：每 0.5s `read_json`（缺失/坏 JSON → 视为仍 waiting，继续等）；`status=="confirmed"` → 返回；`status=="skip_all"` → 置 `_skip_all=True` 返回；
  - 无限等待（用户确认），不设超时；确认后控制台一行 `▶ [步进] #seq 已确认，继续`。
- `active_checkpoint_file() -> Path | None`：返回当前 run 的检查点文件路径（供测试/日志用），未启用返回 None。
- `is_enabled()`：测试辅助。

本模块不导入 llm_callbacks / dataprovider_log（由它们单向导入 step_gate），避免循环依赖。

#### 3.1.2 三方依赖能力评估

本模块不依赖外部库/API（仅 pathlib + json + time）。

#### 3.1.3 风险与验证方式

- 风险：后端轮询与页面写入的竞态 → 双方均 temp+rename 原子写，读侧容忍坏 JSON；`time.sleep` 阻塞节点线程 → 仅步进模式启用时发生，属预期行为；进程异常退出留下 `waiting` 文件 → 页面展示为"等待中"，新 run 会覆盖（文件在各自 run 目录内，互不影响）。
- 验证：`tests/utils/test_step_gate.py`（见 3.4）。

#### 3.1.4 文件变更清单

| 路径 | 改动 |
|------|------|
| `AI/utils/step_gate.py` | 新建，模块化门控核心 |

### 3.2 后端挂钩（4 个文件）

#### 3.2.1 模块设计

1. **`AI/utils/dataprovider_log.py`**：
   - `_write()` 改为返回 `(call_dir, res_file)` 元组（`call_dir` 为落盘目录 Path，`res_file` 为实际结果文件名 `res.md`/`res.json`）；现有测试直接调 `_write` 不受影响（返回值无人消费，不破坏）。
   - `dataprovider_log.wrapper`：`_write` 返回 `(call_dir, res_file)` 后调用 `step_gate.checkpoint("dp", layer=<call_dir 相对 run 目录首段>, node=_current_node.get(), name=fn.__name__, dir=<call_dir 相对 run 目录，`/` 归一化>, show_file=res_file)`；**`_write` 返回 None（日志目录未初始化）时跳过检查点**。layer 从 `call_dir.relative_to(_run.log_dir)` 首段推导（ToolNode 内部无节点上下文的回退场景下，`_current_node.get()` 为空串，`_NODE_LAYER` 查不到，目录首段才是真实层级）。
   - 异常隔离：`checkpoint` 调用包 try/except（步进机制永不干扰数据流与日志落盘）。
2. **`AI/utils/llm_callbacks.py`**：
   - `LLMCallbackHandler._pending` 值从 2 元组扩展为 3 元组 `(dir_name, seq, node)`（`on_llm_start` 写入，内部结构，无外部消费）。
   - `on_llm_start`：req.md + meta.json 写入后调用 `step_gate.checkpoint("llm_req", layer=dir_name.split("/")[0], node=node, name=node, dir=dir_name, show_file="req.md")`。LangChain 回调语义：`on_llm_start` 在 API 请求发出**之前**触发，此处阻塞等待即实现"调用 LLM 前暂停"，用户确认后请求才真正发出。
   - `on_llm_end`：两条分支（纯 text 代 / message 代）都写完后，在函数末尾（entry 存在且 `_run.log_dir` 已初始化时）调用 `step_gate.checkpoint("llm_res", layer=dir_name.split("/")[0], node=node, name=node, dir=dir_name, show_file="res.md")`。
   - 两处均 try/except 隔离。
   - **unknown 过滤**：仅当 `_node_layer(node) != "unknown"`（节点在 `_NODE_LAYER` 表中）时才挂检查点，`on_llm_start`/`on_llm_end` 两处同规则。图外 LLM 调用（`SignalProcessor.process_signal` 决策抽取、`Reflector` 反思——metadata 无 `langgraph_node`，节点名解析为 "unknown"）不产生检查点，检查点边界严格保持"DP 响应 + 图节点 LLM 调用前/后"。
3. **`AI/default_config.py`**：
   - 新增 `"debug_step": os.getenv("LIVEPROFIT_DEBUG_STEP", "false").lower() == "true"`。
4. **`AI/graph/trading_graph.py`**：
   - `propagate()` 中 `log_dir` 计算之后：`if self.config.get("debug_step"): step_gate.enable(log_dir)`（并 trace_step 记录）。
   - `propagate()` 末尾（决策提取完成后、return 之前）调用 `step_gate.disable()` 清理状态：防跨 run 残留；图外 LLM 调用已由 unknown 过滤排除，disable 仅作状态卫生，无行为依赖。

#### 3.2.2 三方依赖能力评估

本模块不依赖外部库/API（沿用现有 handler 机制）。

#### 3.2.3 风险与验证方式

- 风险：`on_llm_end` 的 entry 为 None（run_id 对不上）→ 跳过检查点（不误报）；纯代码节点（如 Screening）无 LLM 回调 → 无 llm_req/llm_res 检查点，属预期（其内 DP 调用仍有 DP 检查点）；全市场模式 `stock_loop` 复用同一子图 → 检查点机制天然覆盖；**工具循环场景**（LLM → 工具调用 → LLM 再汇总）中每次 LLM 调用前后各产生一个检查点（llm_req + llm_res），确认次数随工具循环增加——属预期行为（用户明确要求每次 LLM 调用前暂停）。
- **已识别并规避**：图外 LLM 调用（`SignalProcessor.process_signal`，单票模式 propagate 末尾 1 次 + 全市场模式每只票 1 次；`Reflector` 反思）同样触发 `on_llm_end` 且节点名解析为 "unknown" → 若不过滤会产生 N+1 个用户未确认过的额外暂停点，破坏检查点边界。方案采用 unknown 过滤（见 3.2.1 第 2 条），此类调用不产生检查点。
- 验证：单测（test_step_gate 覆盖 wrapper 集成 + unknown 过滤）+ 用户手动跑一次真实分析验证步进节奏。

### 3.3 页面（AI/logviewer/）

#### 3.3.1 模块设计

- `logs_reader.py` 新增纯函数：
  - `find_checkpoint(run: Path) -> Optional[Dict]`：读 `{run}/.debug_checkpoint.json`，坏 JSON/缺失 → None。
  - `find_active_checkpoint(root: Path) -> Optional[Tuple[Path, Dict]]`：遍历 `list_runs(root)`（最新在前），返回第一个存在检查点文件的 `(run_dir, payload)`；全部没有 → None。
- `app.py` 新增第 5 个 tab「调试步进」，主体用 `@st.fragment(run_every="1s")` 自动刷新（streamlit>=1.40 支持，无需新依赖；tabs 内容每次 rerun 均执行，故停留在其他 tab 时轮询也持续生效）：
  - 无检查点文件 → `st.info`（提示需 `LIVEPROFIT_DEBUG_STEP=true` 启动分析 + 刷新目录）；
  - 有检查点 → 顶部展示 `status` 徽标（⏸ 等待中 / ✅ 已确认 / ⏭ 已跳过全部）+ `seq/ts/layer/node/name` + kind 徽标（`dp` = DP 响应 / `llm_req` = LLM 调用前 / `llm_res` = 节点 res）+ 按 `dir` 读取 `show_file` 内容渲染（复用现有 `_render_res` 与读函数；llm_req 渲染提示词 req.md）；
  - `status == "waiting"` 时渲染两个按钮：【确认下一步】→ 读文件改 `status="confirmed"` 写回（temp+rename）后 `st.rerun`；【跳过全部】→ 改 `status="skip_all"` 写回后 `st.rerun`；
  - **stale 写回防护**：按钮回调先重读文件，比对当前 `seq` 与渲染时 `seq`，不一致（后端已推进到下一个检查点）则**不写**、直接 `st.rerun` 取最新渲染——防止 1s 刷新间隔内对旧内容的连点/双击把 confirmed 写进下一个检查点（"未看内容即被放行"违背诉求）；
  - 已知约束（既有行为，非本方案引入）：CLI 侧 `log_dir` 硬编码为 `logs/{run_ts}`（`trading_graph.py`），不受 `LIVEPROFIT_LOGS_DIR` 影响——若用户设置了 `LIVEPROFIT_LOGS_DIR` 指向其他目录，查看器扫描根与检查点实际位置不一致，步进 tab 将显示"无检查点"，需保持两者一致。

#### 3.3.2 三方依赖能力评估

- `streamlit>=1.40.0`（已在依赖中）：`st.fragment(run_every=...)` 于 1.37 引入，1.40 可用；按钮写入文件为纯 Python。**无新增依赖**。

#### 3.3.3 风险与验证方式

- 风险：fragment 1s 轮询读文件的开销可忽略（单文件读）；两个按钮同时点击竞态 → 原子写 + 后端只认最终 status；旧 run 遗留 waiting 文件 → `find_active_checkpoint` 只取最新 run 的检查点。
- 验证：`tests/utils/test_logs_reader.py` 增补 `find_checkpoint`/`find_active_checkpoint`；`tests/utils/test_logviewer_smoke.py` 增补含 waiting 检查点的 fixture，AppTest 断言 tab 渲染 + 点击【确认下一步】后文件 status 变为 confirmed。
