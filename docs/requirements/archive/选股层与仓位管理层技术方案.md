## 一、背景与动机

### 1.1 现状

用户对系统的原始诉求是四环节闭环：

> 通过市场层规避系统性的风险（外围战争、国外科技指数暴跌、国外指数暴跌等），规避风险后，通过板块层筛选出最近走势比较好或者适合潜伏的板块，再通过个股层先根据板块筛选出走的好的个股（板块内涨幅超过平均），再根据基本面和技术分析看具体的入场时机，再根据总仓位确定交易计划。

现有系统已实现"市场层 → 板块层 → 个股层"三层金字塔，但整体是**单票驱动**架构（`company_of_interest` 由外部预先手动指定，`propagate()` 单次 invoke 整图，`AI/graph/trading_graph.py:231-345`）。对照四环节逐项核对：

| # | 目标环节 | 现状（已核实代码） | 差距 |
|---|----------|------|------|
| 1 | 市场层规避系统性风险 | ✅ 已实现。CN Tech 产出 `market_regime` 三级别环境判定（≤800 字文本块，含仓位建议基调，`AI/marketAgents/analysts/cn_tech_analyst.py:105-138`） | `market_regime` 是**自由文本**，无机器可读熔断信号；判定结果无法与下游流程形成结构化联动开关（如高风险时自动跳过选股/买入） |
| 2 | 板块层筛选走势好/适合潜伏的板块 | ✅ 已实现。3 个 Agent 产出 `sector_shortlist` / `sector_tech_confirm` / `rotation_top_picks`（均为 ≤800-1200 字结构化文本块） | 产出是"结构化文本"而非 `list[str]`，板块名与逻辑/置信度混在同一行内，纯代码无法直接消费 |
| 3 | 个股层"按板块筛出板块内涨幅超过平均的个股" | ❌ **空白**。无"候选板块 → 成分股 → 涨幅排名 → 超均值筛选"能力，无对候选池批量跑分析的编排 | 需新增**选股层**（数据层 + 筛选逻辑 + 图编排改造） |
| 4 | 按总仓位确定交易计划 | ❌ **空白**。`final_trade_decision` 是 LLM 自由文本（`AI/stockAgents/managers/risk_manager.py:93-96`）；置信度/风险评分/目标价/止损位全部嵌在文本里，仅 `signal_processing.process_signal()` 事后二次 LLM 抽取（且无 stop_loss、不回写 state）；全系统**无持仓存储、无总资金配置**（MongoDB 仅 `token_usage` 集合） | 需新增**仓位管理层** + 决策结构化 |

### 1.2 目标

- **选股层**：给定候选板块清单 → 拉取成分股 → 批量计算近 N 日涨幅 → 筛出跑赢板块均值的个股 → 产出 `candidate_stock_pool`
- **个股层循环**：对候选池中每只票独立跑完现有完整分析链路（技术/基本面/新闻/情绪 → 多空辩论 → 研究经理 → 交易员 → 风控辩论 → 风险经理），各自产出 `final_trade_decision`
- **仓位管理层**：汇总多票决策 + 总资金/持仓/仓位上限规则 → 产出 `final_position_plan` 可执行交易计划
- **市场层熔断**：`market_regime` 派生机器可读的 `risk_gate` 开关，高风险时自动阻断买入流程

### 1.3 本方案范围

- 新增选股层、仓位管理层（**均为纯 Python 代码模块，不含任何 LLM 节点**——"从数字里筛数字"和"按规则分配数字"是确定性运算，引入 LLM 只会带来不可复现、延迟和成本）
- 市场层/板块层各增加**一个派生结构化字段**（`risk_gate`、`sector_shortlist_structured`），不改动任何分析师内部 prompt 逻辑（新增不改旧）
- 个股层循环改造：只动编排层，不改个股层子图内部

## 二、架构设计

### 2.1 四层金字塔

```
顶层 Graph（AI/graph/trading_graph.py 的 TradingAgentsGraph）
├── Subgraph: 市场层（已实现 ✅，不动内部逻辑）
│   └── market_regime → ★ 新增派生字段 risk_gate（熔断开关）
├── Subgraph: 板块层（已实现 ✅，不动内部逻辑）
│   └── sector_shortlist / sector_tech_confirm → ★ 新增派生字段 sector_shortlist_structured（list[str]）
├── 选股层（★ 新增，普通函数节点，纯代码，无 LLM）
│   ├── 板块成分股拉取 → 批量涨幅计算 → 超板块均值筛选 + 流动性过滤
│   └── 产出 candidate_stock_pool
├── Stock Layer（个股层，已实现 ✅，不改子图内部）
│   └── ★ 编排层对候选池顺序循环 invoke（每票独立完整分析，各自产出 final_trade_decision）
└── 仓位管理层（★ 新增，普通函数节点，纯代码，无 LLM）
    ├── 汇总 stock_results + 总资金/持仓/仓位规则
    └── 产出 final_position_plan（可执行交易计划）
```

**运行模式**（由现有 `selectedLayer` 参数控制，`AI/graph/trading_graph.py:50-64`）：

| 模式 | selectedLayer | 行为 |
|------|---------------|------|
| 单票模式（现状） | `["market","sector","stock"]`（默认不变） | 与现状完全一致的流程 |
| 全市场模式（新增） | 含 `"screening"`（`"position"` 可选） | Market → Sector → Screening → 池非空时逐票循环 Stock Layer → Position Manager |

### 2.2 数据模型设计（State 字段变更）

现有 `AgentState` 位于 `AI/stockAgents/utils/agent_states.py`（TypedDict + Annotated 仅作类型标注、无 reduce 操作符）。本方案新增 5 个字段：

| 字段 | 类型 | 写入者 | 说明 |
|------|------|--------|------|
| `risk_gate` | `str` | CN Tech Analyst（市场层，派生提取） | `normal` / `caution` / `block`；默认 `normal` |
| `sector_shortlist_structured` | `list[str]` | Sector News/Tech Analyst（板块层，派生提取） | 候选板块名清单（统一东财概念体系，提取时经东财概念全名单过滤）；默认 `[]` |
| `candidate_stock_pool` | `list[dict]` | 选股层 `screener.py` | 候选个股（含 code/name/sector/pct_change/sector_avg_pct/vs_avg/last_close） |
| `stock_results` | `dict[str, dict]` | 个股层循环编排层 | 逐票结果：`code → {final_trade_decision, decision_json, ...}` |
| `final_position_plan` | `dict` | 仓位管理层 `position_manager.py` | 最终交易计划（逐票金额/股数 + 组合汇总） |

**全局态 vs 逐票态**（个股层循环的前提）：`AgentState` 是扁平结构，循环编排时把字段分为两类——

- **全局态**（运行期间单例，逐票共享）：市场层/板块层全部字段、`risk_gate`、`sector_shortlist_structured`、`candidate_stock_pool`、`trade_date` 等
- **逐票态**（每只票独立一份）：`company_of_interest`、`stock_tech_report`、`sentiment_report`、`news_report`、`fundamentals_report`、`investment_plan`、`trader_investment_plan`、`risk_debate_state`、`investment_debate_state`、`final_trade_decision`、`messages`

循环实现方式：以"全局态 + 逐票态覆盖"组装每票的输入 state，invoke 个股层子图后把逐票结果收进 `stock_results`（详见 3.5）。

### 2.3 设计原则

- **新增不改旧**：市场层/板块层/个股层分析师内部 prompt 与报告格式不动；只新增派生字段和新模块
- **选股与仓位分配不用 AI，只用确定性代码**：涨幅排名、超均值筛选、金额分配、上限校验全部可回溯、可复现；选股层与仓位管理层在图编排中是**普通函数节点**（`def node(state) -> dict`），不是 LLM Agent 子图
- **向后兼容**（详见 4.3）：`selectedLayer` 不含 `"screening"` 时系统行为与现状完全一致；新字段均有安全默认值

## 三、详细设计

### 3.1 数据层新增接口

#### 3.1.1 模块设计

新增 2 个接口，遵循既有契约（`AI/dataflows/providers/base_provider.py`：**先在基类加方法签名 → AKShare/Tushare 同步覆写 → `interface.py` 薄封装**；返回 `str` Markdown，不支持时继承 `_not_supported()` 默认返回）：

| 接口 | 签名 | 用途 | 返回格式（供选股层解析，每行一条） |
|------|------|------|------|
| `get_concept_board_names` | `()` | 拉取东财概念板块全名单（供 3.2 清单过滤） | `概念名`（每行一个） |
| `get_sector_constituents` | `(sector_name: str)` | 拉取东财概念板块当日成分股 | `代码|名称` |
| `get_stocks_performance_ranking` | `(codes: list[str], days: int)` | 批量计算近 N 日涨跌幅 + 最新价/成交额，返回含板块内均值 | `代码|近N日涨幅%|最新价|最新成交额`（末行板块均值；名称由选股层从成分股行关联） |

实现要点（数据体系：**统一东财概念，取消申万行业/同花顺概念路径**，双数据源均实测可用，见 3.1.2）：

- **名称体系说明**：EM = 东方财富。本方案消费端板块名**统一为东财概念名**（两种数据源同一体系，`sector_shortlist_structured` 经东财概念全名单过滤，见 3.2）。东财概念名与同花顺概念名部分不一致（实测 EM 无"光模块"等 THS 独有概念）→ 未命中即落选，不做跨体系对齐
- **Tushare**：`dc_index(trade_date=YYYYMMDD)` 一次拉全量东财板块快照（实测约 1031 行 = 概念 504 + 行业 496 + 地域 31，含 `name`/`ts_code`/`idx_type`），取 `idx_type == "概念板块"` 建"概念名 → ts_code"映射（逐日可缓存，供名单接口与成分股接口共用）；成分股 `dc_member(ts_code, trade_date)` 取当日快照
- **AKShare**：概念名单 `stock_board_concept_name_em`（板块层已在用），成分股 `stock_board_concept_cons_em(symbol=name)`（实测存在）
- **价格/成交额不在成分股接口取**：`dc_member` 仅返回 `con_code|name`（无价格列），且成分股接口的时点与涨幅计算口径不易对齐 → 最新价/最新成交额统一在 `get_stocks_performance_ranking` 阶段从个股日线最后一根 K 线取（与涨幅同源），成分股接口只负责"代码|名称"
- **批量涨幅**：复用 `interface.get_china_stock_data`（`AI/dataflows/interface.py:104-121`，带缓存）逐只拉日线，重跑同区间可命中缓存，区间涨跌幅本地计算
- **稳健性**：沿用 `get_industry_sector_performance` 的"连续 3 次失败熔断"模式（`akshare_provider.py:956-985`）；成分股数量大的板块（概念板块可达上百只）**只取前 N 只**（默认 50，一期直接取接口返回顺序，按流通市值/成交额预排序列为二期优化），避免拖慢整条流水线
- **代码规范化**：`dc_member` 的 `con_code` / EM 接口代码均为 6 位数字，统一经 `StockUtils.normalize_code`（`AI/utils/stock_utils.py:63-80`）补 `.SH/.SZ` 后缀，保证与 `company_of_interest` 既有格式一致
- **T-1 一致性**：`dc_member` 必须传 `trade_date`（实测不传返回历史累计成员：光刻胶概念 996 行 vs 当日快照 58 行）；`dc_index` 日期区间参数代理不支持（实测空返回）→ 按 `trade_date` 逐日调用

#### 3.1.2 三方依赖能力评估

本方案数据体系统一为**东财概念**（申万行业、同花顺概念路径已取消）。以下为 **2026-08-15 用项目 token 对 gyzcloud 代理实测**结论：

| 数据需求 | Tushare（gyzcloud 代理端点，**已实测 ✅**） | AKShare 1.18.81（已实测 ✅） | 结论 |
|----------|------------------------|-------------------------------|------|
| 东财概念名单/板块指数 | `dc_index(trade_date=)` 返回全量板块快照（约 1031 行 = 概念 504 + 行业 496 + 地域 31），含 `name`/`ts_code`/`idx_type`/`pct_change`/`turnover_rate`/`leading` 等；⚠️ 日期区间参数返回空（代理不支持）→ 按 `trade_date` 逐日调用；`dc_index(ts_code=)` 单板块历史序列可用 | `stock_board_concept_name_em` / `stock_board_concept_hist_em`（板块层已在用） | 双源可用 |
| 东财概念成分股 | `dc_member(ts_code, trade_date)` ✅ 当日快照（光刻胶概念 58 行）；⚠️ **不传 `trade_date` 返回历史累计成员（996 行）→ 必须传**；仅返回 `con_code|name`，无价格/成交额列 | `stock_board_concept_cons_em(symbol=name)` ✅ 存在 | 双源可用 |
| 批量个股日线 | `get_stock_data`（daily，`:196`）✅ 现有 | `get_stock_data`（qfq，`:167`）✅ 现有 | 双源可用 |

> **体系一致性说明**：东财概念名与同花顺概念名部分不一致（实测 EM 有"白酒/人工智能/半导体概念/人形机器人"，无"光模块"——THS 独有）。Tushare 模式下板块层分析师看到的是申万行业+同花顺概念数据，其清单候选名需经东财概念全名单过滤（见 3.2），未命中即落选，不做跨体系对齐。
>
> **不再需要**：申万行业成分股（`index_member` ❌ 代理不支持，`stock_basic`+`industry` 过滤方案废弃）、同花顺概念成分股（`ths_member` ❓ 未实测，已无必要）。

#### 3.1.3 风险与验证方式

- 风险：清单候选名（THS/申万体系）在东财概念名单中未命中 → 过滤落选（实测部分 THS 概念名 EM 无对等，属预期行为）；`dc_member` 漏传 `trade_date` 返回历史累计成员 → 实现期必传 + 单测断言参数；`dc_index` 日期区间不支持 → 按 `trade_date` 逐日调用；成分股接口限流/超时 → 熔断模式中止该板块

- 验证：单元测试固定 fixture（模拟 provider 返回）验证解析与熔断逻辑；对真实数据源各跑 1-2 个东财概念板块（Tushare/AKShare 各一遍）做冒烟测试，确认字段列名与约定格式一致

- **修改**：`AI/dataflows/providers/base_provider.py`（+3 方法签名，默认 `_not_supported`）、`AI/dataflows/providers/akshare_provider.py`（+3 覆写 + 熔断/截断）、`AI/dataflows/providers/tushare_provider.py`（+3 覆写：`dc_index` 建名映射（按日缓存）+ `dc_member` 取当日成分股）、`AI/dataflows/interface.py`（+3 薄封装）

### 3.2 板块层增强：sector_shortlist_structured

#### 3.2.1 模块设计

选股层是纯代码模块，不能也不应该用 LLM 去解析 `sector_shortlist` 自然语言文本。唯一可行的做法：板块层分析师在生成报告的同时，**用约定的格式行产出一份严格结构化清单**，由代码提取进独立字段：

- **模板约定**：`templates/sector/sector_news_analyst.md` 与 `templates/sector/sector_tech_analyst.md` 的结论块代码块中新增一行 `结构化清单: ["板块A", "板块B"]`（JSON 数组，仅概念板块名，不含逻辑/置信度）
- **提取实现**：各分析师现有的 `_extract_*` 函数（如 `sector_news_analyst.py:128-148`）扩展正则提取该行 → `json.loads` → **经 3.1 的 `get_concept_board_names()` 东财概念全名单过滤（未命中落选）** → 写入 `sector_shortlist_structured`；解析失败或缺失置 `[]`，不影响原字段；名单接口获取失败时跳过过滤（候选名原样进入，选股层按成分股未命中跳过兜底）
- **来源范围**：news 的短线候选/波段主线/长线配置中的板块名 + tech 的"确认板块"名，合并去重
- **体系限定（重要，消费端统一东财概念）**：板块层自身数据体系**不变**（Tushare 模式下 news/tech 看到的行业名是申万一级、概念名是同花顺概念；AKShare 模式下是东财体系，见 `docs/板块层.md`）——本方案消费端只认**东财概念名**：提取时用东财概念全名单过滤清单候选名，未命中即落选。效果：申万行业名全部落选、同花顺概念名仅与东财重合部分保留（实测如"白酒/人工智能"保留、"光模块"落选），实现"取消申万行业、统一东财概念"而不改板块层内部。`rotation_top_picks` 是 THS 打板题材分类（与东财概念非同一体系，`sector_rotation_analyst.py:74-86` 约定禁止跨体系对齐）→ 一期 `sector_shortlist_structured` 仅由 news+tech 产出，rotation 的打板题材名不纳入
- **占位防御**：`rotation_top_picks` 在数据不可用时会写入占位文本（`sector_rotation_analyst.py:104-116`），提取函数需识别并跳过

#### 3.2.2 三方依赖能力评估

本模块不依赖外部库/API（仅改动 LLM 输出格式约定与提取代码）。

#### 3.2.3 风险与验证方式

### 3.3 市场层增强：risk_gate 熔断信号

#### 3.3.1 模块设计

- **产出方式**：纯规则派生，不新增 LLM 调用。`cn_tech_analyst._extract_market_regime`（`AI/marketAgents/analysts/cn_tech_analyst.py:118-138`）提取 `market_regime` 文本块时，顺带按关键词规则生成 `risk_gate` 写入 state

| 判定条件（对 market_regime 文本的规则匹配） | risk_gate |
|------|-----------|
| 市场状态标签 = `系统性风险`，或 短线适合度 = `回避` | `block` |
| 短线适合度 = `谨慎`，或 波段姿态 = `防御` | `caution` |
| 其余情况（含市场层未运行、提取失败） | `normal` |

- **联动消费**：
  - `block` → 选股节点短路，不产出候选池；仓位管理层只输出"清仓/减仓/观望"风险提示计划（不生成买入订单）

  - `normal` → 全流程正常

这一步把"规避系统性风险"从建议性文字变成结构化可执行的流程开关。

### 3.5 个股层循环改造（逐票编排）

#### 3.5.1 模块设计

**现状**：`StockLayerGraph.build()`（`AI/stockAgents/stock_layer_graph.py:77-197`）编译的子图每次 invoke 只处理 `state["company_of_interest"]` 一只票；顶层 `propagate()` 单次 invoke 整图。

**改造方案（一期：propagate 层顺序循环）**：

```
propagate() 全市场模式（selectedLayer 含 "screening"）：
  1. graph.invoke(initial_state)   # Market → Sector → Screening → END，拿到全局态 + candidate_stock_pool
  2. risk_gate == "block" 或池为空 → 直接调用仓位管理层产出风险提示/空计划，结束
  3. 池非空 → for stock in candidate_stock_pool:
       sub_state = 全局态 + {company_of_interest: code, 逐票态字段重置, messages: 初始消息}
       final_state = stock_subgraph.invoke(sub_state)   # 复用同一编译子图对象
       stock_results[code] = {
           "final_trade_decision": final_state["final_trade_decision"],
           "decision_json": process_signal(final_state["final_trade_decision"]),  # 复用现有二次抽取
           "sector": stock["sector"], "last_close": stock["last_close"]
       }
  4. 调用仓位管理层产出 final_position_plan
```

要点：

- **State 拆分**：全局态/逐票态清单见 2.2；逐票 invoke 前必须重置逐票态字段（含 `messages`），防止上一只票的报告/消息历史污染下一只
- **决策结构化复用**：`signal_processing.process_signal()`（`AI/graph/signal_processing.py:24-102`）已实现 LLM 二次抽取 `{action, target_price, confidence, risk_score, reasoning}`——扩展其 prompt 补抽 `stop_loss`（trader 文本中已要求给出止损位，`AI/stockAgents/trader/trader.py:76-81`），循环编排对每票调用一次存入 `stock_results`，**不改** `risk_manager.py` 的输出格式
- **成本/耗时**：候选池上限 10 只时，LLM 调用量约为单票模式的 10 倍；顺序循环总耗时 ≈ 单票耗时 × 池规模（约 10-20 分钟级）。规模预期见 4.1 待确认问题 Q3
- **propagate 返回值语义**：全市场模式 `propagate()` 返回的 `decision` 为默认决策（顶层态不含 `final_trade_decision`，不再二次抽取），逐票决策在 `stock_results[code]["decision_json"]`；单票模式保持原路径不变
- **二期选项（本方案不实施）**：LangGraph `Send` API map-reduce 并行化——需要把逐票逻辑封装成图内节点并重新编译顶层图（Send 只能在图内扇出），调试复杂度显著上升，且受 LLM API 并发速率限制；待顺序循环验证正确性后评估

#### 3.5.2 三方依赖能力评估

一期仅依赖 LangGraph 子图 `invoke()`（现有代码已大量使用，无风险）。二期 `Send` API：LangGraph 原生支持（`langgraph.types.Send`），但按上述原因暂缓。

#### 3.5.3 风险与验证方式

- 风险：逐票态污染（上一票字段残留）→ 重置清单单元测试 + 日志抽查；单票失败导致循环中断 → 逐票 try/except，失败票跳过并记录（`stock_results[code] = {"error": ...}`），不阻断其他票
- 验证：先用 2-3 只票的小池端到端跑通，对比单票模式输出一致性；再放大到 10 只验证耗时与成本

### 3.6 仓位管理层（AI/position/，纯代码）

#### 3.6.1 模块设计

**定位**：流水线收口环节，把多只个股各自独立的决策汇总成一份受总资金和仓位规则约束的可执行交易计划。

**输入**：

- 总资金 `LIVEPROFIT_TOTAL_CAPITAL`（无默认值，未配置时仓位管理层跳过并告警，不阻塞前序流程）
- 已持仓明细（见 4.1 Q1；本方案默认方案：项目根 `data/portfolio.json` 手动维护，字段 `code/name/shares/cost_price`，`last_price` 可选；持仓市值估值口径：`last_price` 有值用 `last_price`，缺省按 `cost_price` 估值。缺失文件视为空仓）
- 仓位规则：`LIVEPROFIT_MAX_POSITION_PCT`（0.8）、`LIVEPROFIT_MAX_SINGLE_STOCK_PCT`（0.1）、`LIVEPROFIT_MAX_SECTOR_PCT`（0.3）、`LIVEPROFIT_POSITION_SIZING_STRATEGY`（`confidence_weighted`）
- `stock_results`（每票 `decision_json`：action/confidence/risk_score/target_price/stop_loss + 池条目的 sector/last_close）
- `risk_gate`（`caution` 时目标仓位上限 ×0.5）

**核心逻辑**（全部确定性数值计算）：

1. 过滤 `action == "买入"` 的候选股
2. 排序：置信度降序，风险评分升序为次要键
3. 分配建议金额：单票金额 = `min(总资金 × LIVEPROFIT_MAX_SINGLE_STOCK_PCT, 按置信度加权份额)`；策略可配置——`equal`（等权）/ `confidence_weighted`（默认，置信度加权 + 硬上限截断）/ `kelly`（简化凯利 `f = p - (1-p)/b`，赔率 `b = (target_price - last_close) / (last_close - stop_loss)`，一期作为可选高级项）
4. 组合校验：同板块合计仓位超 `LIVEPROFIT_MAX_SECTOR_PCT` → 按排序裁剪排名靠后的候选；已有持仓市值 + 新增买入总金额超 `总资金 × LIVEPROFIT_MAX_POSITION_PCT` → 整体按比例缩减或裁剪。**口径说明**：板块上限一期仅统计本次新增订单（已持仓无 sector 字段，不计入同板块市值，后续可给持仓 JSON 加 sector 字段扩展）
5. 产出 `final_position_plan`：

```json
{
  "plan_date": "2026-08-12",
  "total_capital": 1000000,
  "target_position_pct": 0.8,
  "risk_gate": "normal",
  "orders": [
    {"code": "600519.SH", "name": "贵州茅台", "sector": "白酒", "action": "买入",
     "amount": 80000, "shares": 400, "position_pct": 0.08,
     "confidence": 0.75, "stop_loss": 1450.0, "target_price": 1700.0}
  ],
  "summary": {
    "total_new_position_pct": 0.14, "existing_position_pct": 0.30,
    "final_position_pct": 0.44, "cash_reserve_pct": 0.56
  }
}
```

- `risk_gate == "block"` 时：不生成买入订单，输出含"清仓/减仓/观望"建议的风险提示计划
- **展示不需要 LLM**：`final_position_plan` 本身是结构化 JSON，落盘到 `logs/{ts}/reports/`（扩展 `_write_reports`，`AI/graph/trading_graph.py:415-455`）并用 f-string 模板转 Markdown 表格即可

#### 3.6.2 三方依赖能力评估

本模块不依赖外部库/API（标准库数值计算）。

#### 3.6.3 风险与验证方式

- 风险：`decision_json` 抽取失败（LLM 输出异常）→ 该票跳过分配并记入 summary 警告；`last_close` 为 0/异常 → 该票跳过（无法换算股数）；总资金未配置 → 整层跳过 + 显式告警
