# 任务文件夹骨架说明

> **状态**：稳定（2026-09-14，随文档目录重构方案落地）
> **用途**：新建任务文件夹时按本说明建齐骨架；全部骨架文件均有对应模板（本目录 *.模板.md，复制后去掉「使用方式」提示块）。

## 一、骨架文件与职责

| 文件 | 必建 | 职责 | 生命周期 |
|------|------|------|----------|
| README.md | ✅ | 任务总览（目标/状态/负责人/链接）+ 状态块（唯一权威状态载体） | 实施中实时更新；归档时定格 |
| plan.md | ✅ | 方案正文（评审对象） | 评审对象；确认后冻结，修正走 revisions 追加 |
| tasks.md | ✅ | 按业务结果/契约边界/迁移风险拆验收任务；可执行标准、必验风险、状态与result证据链接 | 方案确认后生成；实施中演进；归档随文件夹保留 |
| log.md | ✅ | 时间线日志（日期 + 动作 + 结果） | 倒序追加 |
| decisions.md | ✅ | 关键决策记录（背景→选项→结论→理由） | 倒序追加 |
| issues.md | ✅ | 问题与解决（表象→根因→解决；评审 findings 落点） | 倒序追加 |
| result.md | ✅ | 完整验收证据的唯一记录：范围、实际命令、结果、review、未通过项及门禁 | 各验收任务收尾追加；归档时写最终结论 |
| retrospective.md | ✅ | 复盘（任务级；跨任务主题沉淀进 docs/experience/） | 归档前写 |
| attachments/ | 按需 | 附件、截图、数据 | 按需增删 |

八文件全建，不代表每个检查点全写：实质检查点更新README/tasks/log；验收收尾完整证据写result并在tasks链接。plan/decisions只在范围或设计决策改变时更新；issues只登记需治理的问题；retrospective任务收尾再填。knowledge/experience按既定领域事实和已核实经验写入，不复制阶段验收过程。

## 二、四类文档分工

- **standards/**：强制开发流程及领域规范，按根 AGENTS 触发读取。

- **requirements/**：任务过程记录（本骨架）——一个任务的全部资料聚在一处。
- **knowledge/**：知识沉淀（backend/frontend/ai + 产品基线）——回答"系统现在是什么样"，刻意写入；任务完成后的**可复用结论**才沉淀进 knowledge/（见 [开发流程](../../standards/workspace/开发流程.md)的知识归属规则）。
- **experience/**：经验教训（pitfalls/best-practices）——跨任务主题沉淀，故事与细节只放这里。

## 三、归档

任务完成（Code Review 通过、验收结论固化）后：

1. 把整个文件夹移入 `docs/requirements/archive/<任务名>/`；
2. **同步把文件夹内相对链接整体上移一层**（archive 比 requirements 深一层：`../../X` → `../../../X`、`../archive/X` → `../../archive/X`）；
3. 跑链接检查脚本复查无新增断链；
4. README.md 状态更新为「已完成」、result.md/retrospective.md 填写完毕。

archive/ 内两种形态并存：历史方案平铺文件（旧制度迁入，不拆骨架）+ 未来任务文件夹整体归档。
