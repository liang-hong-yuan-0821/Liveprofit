# 代码验收

> **适用**：选择/维护/运行测试、划分验收、复杂任务独立复核与收尾。
> **规则来源**：承接原根 AGENTS 指引；正文非链接源码路径均以仓库根为基准。
> **入口**：[规范索引](../index.md)；门禁摘要见 [AGENTS.md](../../../AGENTS.md)。

## 验收执行约定（2026-10-01）

- **先定范围**：tasks.md为验收任务列出业务结果、必验风险及定向/关联回归范围；实现中按需检查，任务收尾集中验收。新增独立验收边界须说明业务或风险理由，不按文件数量拆任务。
- **按变更复验**：先跑定向检查，收尾跑一组覆盖受影响调用链的关联回归；涉及共享触发器、schema、锁序、权限或摘要算法时包含共同消费方。失败或review修复后只重验受影响范围；影响扩大才扩大回归。代码、相关依赖、fixture和环境仍适用的已有通过证据可引用，变更使其失效时必须重验，不为凑轮次重复跑全组。
- **保留关键门禁**：事务回滚/幂等、并发、权限、不可变历史、迁移保全等与本任务相关的正确性检查不得省略；DB隔离核查、真实LLM禁跑、生产授权及来源认证规则不变。必验项未通过或未执行，不得记为验收PASS。
- **复核有终点**：复杂验收任务完成后做一次独立Code Review；无待修finding即可收尾，不固定要求第二轮。修复后复核修改点及其交互，沿用最多两轮规则；纯格式/注释和验收记录补充不重启代码review，PASS后业务逻辑变化仍须受影响测试及delta复核。方案评审另按既有触发规则。
- **证据单点记录**：result.md保存完整验收证据，tasks.md只勾选标准并链接证据，README只维护状态/下一步，log每个检查点或验收留一条摘要。plan/decisions只在范围或设计决策变化时更新，issues只登记有治理价值的问题；knowledge只同步持久契约事实，experience只沉淀已核实的新经验，retrospective在任务收尾填写，不每次机械更新八文件。
- **区分检查与验收**：实现检查点、任务软件验收、端到端/部署认证分别标注范围；参数化测试数按需汇报，重点是通过了哪些业务标准和还缺哪些门禁，不累计重复运行数。当前任务的门禁统一登记并引用，不在每次进度中重复展开。

## Code Review 规则

**复杂任务按tasks.md的验收任务聚合启动subagent做code review**；范围为该任务涉及的plan.md变更文件及受影响调用方，辅助模块不各自启动review。已通过的其他任务复用结论；全任务收尾仍核跨任务接口一致性与整体门禁，变化使既有结论失效时再纳入复核。

流程：

1. 任务 README.md 状态更新为 `Code Review`
2. 启动 subagent（type: `claude`），prompt 包含：
   - 任务 plan.md 路径（含变更清单和设计意图）
   - 逐文件对照方案检查：字段命名一致性、接口签名匹配、边界条件处理、向后兼容、缺失占位
   - **代码逻辑正确性**：函数入参/出参是否与调用方匹配、条件分支是否覆盖所有情况、状态流转是否符合设计、是否存在死代码或不可达路径、异常处理是否到位
3. findings 严重度定义复用[方案评审](方案评审.md)（blocker/major/minor/polish）
4. 初轮无待修finding即可收尾；有问题时修复后只复核修改点及交互（最多2轮），不重新全量扫描。纯格式/注释修正不重启review；业务逻辑变化须测试及delta复核
5. Review通过后完成该验收任务记录；还有主线任务时README恢复`实现中`并继续。全部任务与整体门禁完成后才标`已完成`、整合知识文档及归档

> **CR 前主会话自查两类高发缺陷**（2026-09-12 踩坑，见 [docs/experience/pitfalls/workspace/评审循环踩坑.md](../../../docs/experience/pitfalls/workspace/评审循环踩坑.md)）：① 中文枚举子串解析的否定识别做对双向（假否定/漏否定）；② 共享 PG conn 的查询循环每个 except 分支必须 `conn.rollback()`。

> 中小改动不需要 code review。

## 测试规则

#### 测试目录与用例维护（2026-10-01 用户确认）

- **正式测试统一归项目根 `tests/`**：采用 `领域 → 业务模块 → 测试层级 → 功能文件`；领域为 `backend/`、`frontend/`、`ai/`、`data/`，跨域完整业务流程放 `e2e/`，共享辅助代码与样本放 `support/`。实际目录与运行入口见 [tests/README.md](../../../tests/README.md)，模块、代码范围及关联回归索引见 [tests/suites.json](../../../tests/suites.json)。
- **backend 按业务模块归属**：`analysis`、`market_data`、`investment_workspace`、`quant_strategy`、`quant_research`、`event_study`、`daily_research` 等；API/router 和 Worker 是模块内部的测试对象，可在层级内细分 `api/`、`workers/`，不得作为取代业务模块的一级分类。通用启动、配置、Broker 等归 `platform/`，迁移归 `migrations/`。
- **按实际被测行为分类，不照搬旧路径**：公共数据源、采集、转换、持久层归 `data/`；backend/AI 的消费行为归各自领域。如量化执行即使旧路径在 `agents/position`，仍归 backend。每个正式用例只保留一份，跨模块回归通过运行索引复用。
- **测试层级**：`unit/` 检查独立逻辑或组件，`integration/` 检查模块协作及真实隔离资源，`contract/` 检查稳定接口/事件/结构化输出；端到端按根 `e2e/<业务流程>/` 组织。只创建已有测试需要的目录，模块变大才按稳定子功能继续细分。
- **存量修改与增量功能**：修改功能优先更新、补充已有功能测试，保留仍有效的历史断言；新增功能先增加相应模块的用例，形成独立功能边界才新建脚本。文件和用例按功能/行为命名，不按需求日期或临时 bug 编号形成平行测试目录。
- **bug 修复闭环**：复杂 bug 可在 `backend/bugs/<问题标识>/` 放临时复现/诊断脚本；把触发条件和必要边界加入对应正式功能测试，确认修复前失败、修复后通过，完成关联回归且正式测试不依赖临时目录后，删除临时脚本和无用附件。简单 bug 直接补已有测试即可。数据修复/数据库迁移脚本归 `backend/scripts/` 或迁移目录，按执行、回滚、审计要求保留，不套用临时脚本的默认删除规则。
- **辅助代码和 fixture**：跨模块共享 fake、工厂及样本放 `tests/support/`，模块专用辅助代码放模块的 `support/` 或 `fixtures/`；测试脚本不得直接导入另一测试脚本的测试函数、fixture 或 builder，应抽出辅助模块。根 `conftest.py` 只保留轻量配置与执行门禁，DB/Redis/真实 LLM 初始化限制在适用的局部范围。
- **先查文件级索引再维护测试**：按需求关键词使用 `python -m tests.index --query "关键词"`，按实际改动代码使用 `--source <代码文件或目录>`，必要时加 `--module <领域.模块>`；默认先读取候选摘要，按需加 `--details` 或打开对应模块详情，再读取具体断言及 fixture，确认覆盖关系后再修改；不要通读全部模块详情。存量行为优先更新已有用例，缺边界补入原文件；新增独立功能才新建脚本。搜索无结果须在对应模块继续检索源码，不得直接认定没有测试。索引是候选定位入口，不是覆盖充分或执行许可证明。
- **测试说明单一来源与同步**：每个正式测试文件顶部维护 `test-catalog-begin/end` 注释 JSON，必填 `purpose`（被测功能）、`keywords`（业务关键词）、`covers`（仓库内实际被测文件）、`environment`（依赖环境），按需登记 `related_tests`。业务路径由维护者核对登记，不按文件名或导入关系自动认定覆盖。新增、删除或修改测试后运行 `python -m tests.index`，生成 `tests/catalog.json` 摘要及 `tests/catalog/<领域>/<模块>.json` 详情、`docs/knowledge/test/测试索引.md` 导航及 `docs/knowledge/test/测试详情/<领域>/<模块>.md`；收尾运行 `python -m tests.index --check` 检查缺失说明、无效代码/关联路径及过期生成物，禁止手工编辑生成索引。模块级归属与关联回归仍维护 `suites.json`，规则与字段格式见 [tests/README.md](../../../tests/README.md)。
- **按影响范围选择回归**：开发前确定直接测试、受影响调用方及共同消费方；可使用 `python -m tests.run --module <领域.模块> --related` 查看和运行显式关联范围。共享 schema、触发器、锁序、权限、摘要算法、公共 fixture 或依赖变化须扩大到共同消费链；索引及层级筛选不代替当前任务的必验风险与门禁。范围变化同步维护 `suites.json`，验收证据仍按现有 tasks/result 约定记录。
- **运行环境与测试层级正交**：数据库、外部数据源、真实 LLM 和 E2E 用显式标记及入口门禁控制，不另建与 `unit/integration` 平行的 `live/` 目录。默认排除真实依赖与需隔离资源的测试；`--allow-db` 仅在核查具体 fixture/连接隔离后使用，真实 LLM/toolkit 和真实外部源只允许用户手动显式启用，浏览器真实建单分析场景亦受独立门禁约束。禁止只靠用例名称或 `-k` 判断安全。

- **运行任何会执行 DDL、TRUNCATE 或写入的 DB 测试前，必须读测试函数和 fixture，确认连接已显式指向隔离测试库；测试名含 idempotent 也不能当作只读。**


- **自测禁止运行 AI 测试**：Claude 自测（自己跑 pytest 验证改动）时，一律排除依赖真实 LLM 的测试——即 tests/ 中用到 `real_llm` / `real_toolkit` fixture 的集成用例（如 `test_sector_news_analyst.py`、`test_sector_rotation_analyst.py::test_integration_*`），统一用 `-k "not integration"` 排除。这类测试**只能由用户手动调用**，Claude 不得自动运行。
- **`-k "not integration"` 排除不干净，全量自测前必须先检索 `real_llm|real_toolkit` fixture**：部分用真实依赖 fixture 的测试名不含 "integration"（实测 `test_sector_news_analyst.py`、`test_sector_tech_analyst.py` 的全部用例、`test_sector_rotation_analyst.py` 的单元测试以外的集成用例），按名排除不掉 → 真实 LLM 调用 + Tushare 拉取会让全量自测挂起 10 分钟以上。当前根 `tests/conftest.py` 默认按真实 fixture/标记排除，动态请求同样受门禁保护；自测仍须核对具体依赖，仅运行相关模块的 mock/unit 范围，禁止传 `--allow-live`。坑的完整故事见 [docs/experience/pitfalls/ai/testing-llm-exclusion.md](../../../docs/experience/pitfalls/ai/testing-llm-exclusion.md)

## 执行入口与历史规则澄清

[测试运行约定](../../../tests/README.md)负责可执行入口和目录说明；本文件约束验收与执行许可。量化数据行像、前驱与命令封口检查见 [量化开发约束](../backend/量化开发约束.md)，不得因分文件而遗漏。

`-k "not integration"` 仅是历史候选筛选，不能证明真实依赖已排除；必须核查实际 fixture/标记与入口门禁，agent 禁止传 `--allow-live` 或 `--allow-external`，真实调用仅由用户手动显式启用。

评审指定 type:claude 时优先使用该工具；当前环境未提供时记录限制并使用可用的独立审阅 agent，不用主会话自审替代独立复核。
